# P2-1：系统设计 — 从零画出 AI 创作产品的技术蓝图

## 1. 一句话本质

**系统设计在解决一个问题：当一件事不能靠一台机器做完时，怎么把它拆开，让多台机器协作完成，同时让用户感觉什么都没发生。**

这句话可以推导出一切：为什么需要网关（统一入口）、为什么需要队列（解耦速度差异）、为什么需要 CDN（就近服务）、为什么要讨论扩展性（一台机器总有上限）。

---

## 2. 为什么必须这样

先想一个极端：如果你只有一台电脑，装了个图片生成模型，用户来了就直接调用。

这在 10 个用户时完全够用。但：

- 第 11 个用户来了，前 10 个还没跑完——他等多久？
- GPU 跑满时，连登录接口也慢了——一条路堵了，全堵了
- 这台机器崩了——所有人挂掉
- 深夜没人用——GPU 在空转烧钱

这四个问题，逼出了系统设计的四个核心命题：**隔离、解耦、冗余、弹性**。

所有你要学的组件和概念，都是这四个命题的具体解法。

---

## 3. 概念地图

```
用户请求
    │
    ▼
[网关 Gateway]          ← 隔离：统一入口，鉴权、限流、路由
    │
    ▼
[应用服务 App Server]   ← 业务逻辑：解析请求、写数据库、返回响应
    │
    ▼
[任务队列 Queue]        ← 解耦：生成任务扔进去，不阻塞用户
    │
    ▼
[GPU Worker]            ← 真正耗时的活在这里干
    │
    ├──► [对象存储 Storage]   ← 图片存这里（S3 / OSS）
    │
    └──► [CDN]               ← 用户取图时就近拿，不走源站

[数据库 DB]             ← 用户信息、任务状态、生成历史
[缓存 Cache]            ← 热点数据，减少 DB 压力
```

**关键关系**：
- 网关和应用服务之间：同步，毫秒级
- 应用服务和队列之间：**异步解耦**，这是 AI 产品架构的核心拆分点
- 队列和 Worker 之间：Worker 主动拉取，不是被推送

---

## 4. 逐个概念深入

### 网关（Gateway）

解决：外部流量进来前，谁来统一管？

不加网关，每个服务都要自己做鉴权、限流、日志——重复逻辑散在各处，改一次要改十处。网关把这些横切关注点统一拦截。

类比：小区保安亭，进门先查证件，不是每栋楼自己设门卫。

**研发语境**：常见选择是 Nginx、Kong、AWS API Gateway。讨论点通常是"限流策略放在网关层还是业务层"。

---

### 任务队列（Queue）

这是 AI 产品架构里最关键的一个概念，值得多说。

**核心矛盾**：用户发请求（毫秒级响应期望）VS 图片生成需要 10-30 秒。

如果同步处理：用户的 HTTP 连接要挂着等 30 秒，这在工程上极不可靠——网络超时、手机息屏、用户关掉页面，连接断了任务就丢了。

解法：**接单和干活分离**。

```
用户 ──► "收到，任务ID: abc123" （立刻返回）
            │
            └──► 队列：[任务abc123, 任务def456, ...]
                        │
                        └──► Worker 按自己的节奏消费
```

用户拿到 ID 后，前端轮询或 WebSocket 订阅结果。任务状态存在数据库里（pending → processing → done）。

**为什么是队列而不是直接调 Worker**：队列提供缓冲，Worker 挂了任务不丢，重启后继续消费；同时可以控制并发，不会把 GPU 撑爆。

常见队列：Redis Queue、RabbitMQ、AWS SQS。

---

### GPU Worker

GPU Worker 只做一件事：从队列里取任务，跑模型，把结果写到存储，更新任务状态。

**冷启动问题**：GPU 实例从关机到能接任务，可能需要 1-3 分钟（拉镜像、加载模型权重）。如果完全按需启动，第一个用户要等很久。

解法是**预热池**：永远保留几台 warm 实例，峰值来了再拉起新实例。这是成本和体验的 tradeoff，后面详谈。

---

### 存储三层结构

```
热数据（正在生成的）   → 内存/Redis Cache
温数据（近期图片）     → 对象存储（S3/OSS）
冷数据（历史归档）     → 低频存储（更便宜）
```

图片不存数据库，太大了。数据库只存图片的 URL 和元数据。

CDN 站在对象存储前面，用户取图时从离自己最近的节点拿，不走源站——源站带宽贵，CDN 便宜且快。

## 5. 架构演进：MVP → 千人 → 十万人

### 阶段一：MVP（< 100 用户）

```
用户 → 一台服务器（应用 + 队列 + Worker + DB 全在一起）
                │
                └→ 对象存储
```

这时候不需要拆，拆了反而增加运维复杂度。把产品跑起来最重要。

**瓶颈在哪**：GPU 只有一张，同时只能跑一个任务。100 人同时提交，最后一个人等 50 分钟。

---

### 阶段二：千人用（1000 DAU，并发 50-100）

**现在的架构扛不住了**，因为：
1. GPU 单点，队列积压严重
2. 应用服务和 Worker 抢资源，Web 接口也开始变慢
3. 数据库没缓存，热点用户信息反复查询

**演进动作**：

```
用户 → 负载均衡 → 应用服务 × 2（独立部署）
                        │
                        ▼
                    任务队列（独立服务）
                        │
                      ┌─┴─┐
                   Worker  Worker   （2台GPU实例）
                        │
                    对象存储 + CDN
                    数据库 + Redis Cache
```

关键变化：**应用服务和 Worker 拆开**，各自扩展，互不干扰。加了 Redis 缓存减少 DB 压力。

---

### 阶段三：十万人用（100K DAU，并发 1000+）

**现在的架构扛不住了**，因为：
1. 数据库成为单点瓶颈
2. GPU 机器数量多了，手动管理不现实
3. 某台机器挂了，上面的任务怎么办
4. 流量有早晚高峰，固定 GPU 数量要么不够用要么浪费钱

**演进动作**：

```
用户
 │
 ▼
[CDN + 网关]（限流、鉴权、路由）
 │
 ├─► [应用服务集群] × N   ← 水平扩展，无状态
 │          │
 │          ▼
 │     [任务队列]
 │          │
 │          ▼
 │   [GPU Worker 自动伸缩]  ← 根据队列深度自动增减实例
 │          │
 │          ▼
 │   [对象存储] ← [CDN]
 │
 ├─► [数据库集群]（主写从读，读写分离）
 │
 └─► [Redis 集群]（分布式缓存）
```

**水平扩展 vs 垂直扩展**：

| | 垂直扩展 | 水平扩展 |
|---|---|---|
| 做法 | 换更强的机器 | 加更多台机器 |
| 上限 | 有，单机有物理上限 | 理论无限 |
| 代价 | 停机换机器，贵 | 服务必须无状态 |
| 适用 | 数据库（早期） | 应用服务、Worker |

应用服务要能水平扩展，前提是**无状态**——不能把用户 Session 存在本机内存里，要存 Redis。

---

## 6. 研发在争什么

### 争一：队列深度多少触发扩容？

队列里积压 20 个任务就拉起新 Worker？还是 100 个？
- 太激进：GPU 实例频繁启停，冷启动浪费钱
- 太保守：用户等待时间长，体验差

没有标准答案，取决于你的用户能接受多久的等待、你愿意花多少钱。

### 争二：永远保留几台热 Worker？

保留 0 台：零成本，但第一个用户冷启动等 3 分钟  
保留 5 台：每月固定成本，但响应快

这是**成本和 P99 延迟的 tradeoff**。通常看流量曲线，低谷期最低用量作为热备基线。

### 争三：任务失败了重试几次？

重试太少：任务偶发失败就丢了，用户投诉  
重试太多：某类任务稳定失败（比如模型 bug），无限循环消耗资源

常见做法：指数退避重试 3 次，之后进死信队列（Dead Letter Queue），人工排查。

### 争四：限流放在哪一层？

网关层限流（按 IP）VS 应用层限流（按用户账号）VS 队列层限流（控制并发）

通常三层都要，但侧重不同：网关防 DDoS，应用层防用户滥用，队列层防 GPU 过载。

    - [ ] A. 网关限流太严格，部分请求被拒绝
    - [ ] B. CDN 没有配置，图片下载慢
    - [x] C. GPU Worker 数量固定，队列在高峰期积压，没有自动扩容
    - [ ] D. 数据库没有加索引，任务状态查询慢

    ??? success "解析"
        等待时间"忽长忽短"是队列积压的典型症状：早来的任务快（队列短），晚来的任务慢（队列已积压）。GPU 利用率 90% 说明 Worker 已经跑满，但数量没有随负载增长。解法是配置基于队列深度的自动扩容策略。A 是被拒绝不是等待；B 影响图片下载速度，不影响生成等待；D 影响的是状态查询的延迟，不是生成时间。

???+ quiz "产品准备从 MVP 升级架构，研发提议：把应用服务做成水平扩展。你问他：'这需要什么前提条件？'最关键的前提是什么？"
    - [ ] A. 数据库要换成分布式数据库
    - [ ] B. 必须先上 CDN
    - [x] C. 应用服务必须做成无状态，Session 等用户状态不能存在服务器本地内存里
    - [ ] D. GPU Worker 数量要先扩展到 10 台以上

    ??? success "解析"
        水平扩展意味着多台实例同时处理请求，用户的前后两次请求可能打到不同机器。如果 Session 存在某台机器的内存里，用户下次打到另一台机器就找不到了。所以必须把状态外移到 Redis 这样的共享存储。A、B、D 都不是水平扩展的前提条件，而是可以独立演进的优化项。
