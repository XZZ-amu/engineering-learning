# P2-1：系统设计 — 从零画出 AI 创作产品的技术蓝图

---

## 1. 一句话本质

**系统设计在解决一个问题：让请求在正确的地方等待、正确的地方处理、正确的地方存储——而不是随机崩掉。**

换句话说：系统设计就是给数据流画一张交通地图，决定每个路口放什么、能承受多少流量、堵了怎么分流、某条路断了怎么绕行。

---

## 2. 为什么必须这样

假设你没有系统设计，直接把所有逻辑写在一个服务里：

用户上传图片 → 服务器收到 → 立刻调 GPU 生图 → 等待 30 秒 → 返回结果

10 个用户没问题。100 个用户同时发请求呢？服务器同时跑 100 个 GPU 任务——要么显存炸了，要么队列根本不存在，新请求直接报错。用户看到的是：**刚才还好的，现在全挂了。**

更糟糕的是，如果生图逻辑和接收请求的逻辑在同一个进程——GPU 算满的时候，连"你好，收到了"都回不了。

**问题不是你的代码烂，是你没有给不同职责的工作划分车道。**

---

## 3. 概念地图

```
用户请求进来
       │
       ▼
  [网关 Gateway]          ← 保安+收发室：限流、鉴权、路由
       │
       ▼
  [应用服务 App Server]   ← 前台：接单、记录、把任务扔出去
       │
       ▼
  [任务队列 Queue]        ← 候诊室：解耦快慢、削峰填谷
       │
       ▼
  [GPU Worker]            ← 手术室：真正干活，按需启停
       │
       ├─→ [对象存储 Storage]  ← 仓库：存图片/模型/资产
       │
       └─→ [数据库 DB]         ← 档案室：存状态/用户/订单

生成完成后
       │
       ▼
  [CDN]                   ← 就近发货：把图片快速送到用户手里

       贯穿全程
  [消息通知]              ← 叫号系统：WebSocket/轮询告诉用户好了
```

关键结构：**网关→应用服务→队列→Worker** 是一条流水线，每一跳都有特定职责。存储和 CDN 是"侧挂"的资源层。它们不是并列关系，是串联 + 旁挂。

---

## 4. 逐个概念深入

### 网关（Gateway）

解决的问题：如果让所有请求直接打到你的应用服务，你的服务既要验身份、又要限速、又要干活——职责混在一起，一旦某类请求爆量，整个服务都受影响。

网关是第一道门，专门做三件事：**鉴权（你是谁）、限流（你能发多少）、路由（你该去哪）**。

它不处理业务逻辑。它只决定这个请求能不能进来、该去哪个服务。

### 应用服务（App Server）

它是"前台接待"，做的事：接收请求、校验参数、往数据库写一条"任务进行中"的记录、把任务扔进队列、立刻返回"已收到，任务 ID 是 xxx"。

注意它**不等 GPU 算完**。这是最关键的设计决策——如果应用服务同步等 GPU，一个请求占一个线程 30 秒，100 个请求就占满了线程池，第 101 个请求直接被拒。

### 任务队列（Queue）

队列解决的是**速度不匹配**的问题。用户发请求的速度（突发、不可预测）和 GPU 处理的速度（固定、有上限）天然不匹配。

没有队列：用户多了，Worker 扛不住，直接失败。  
有了队列：用户多了，任务排队，慢慢处理，用户等待但不报错。

队列是系统的**缓冲垫**。代价是：用户不能立刻拿到结果，必须异步等待。

常用工具：Redis Queue、Celery、BullMQ。

### GPU Worker

真正做生图的地方。它的设计要点是**无状态**——Worker 本身不存任何数据，只从队列取任务、调模型、把结果存到对象存储、更新数据库状态、完事。

无状态意味着可以随意启停多个 Worker，不需要它们互相知道对方的存在。

### 存储：对象存储 vs 数据库

两个东西解决两种存储需求，不要搞混：

| | 对象存储（S3/OSS） | 数据库（PostgreSQL） |
|--|--|--|
| 存什么 | 大文件：图片、视频、模型权重 | 结构化数据：用户、订单、任务状态 |
| 怎么访问 | URL 直接取 | SQL 查询 |
| 能不能改 | 一般不改，只写入 | 随时更新 |

把图片存进数据库是常见的新手错误——数据库不擅长大文件，会让查询变慢。

### CDN

对象存储在某个数据中心，用户从北京访问杭州的服务器，延迟可能有 50-100ms。CDN 把文件缓存到离用户最近的节点，用户从北京节点取，延迟降到 5ms。

CDN 不是必须的，但图片类产品通常流量大，CDN 是性价比极高的优化。

## 5. 架构演进：MVP → 千人 → 十万人

### MVP 版（你 + 几个内测用户）

```
用户 → [App Server（Flask/FastAPI）] → 直接调 GPU → 返回结果
                        ↓
                   [SQLite/PostgreSQL]
```

**没有队列，没有 Worker 分离，没有 CDN。** 这没问题。MVP 的目标是验证功能，不是承载流量。

扛得住：5-10 个并发请求。  
崩的方式：第 11 个请求进来，GPU 显存不够，直接报错。

---

### 千人版（正式上线，日活几百到一千）

**现在的架构哪里扛不住？**

同时在线几十人，GPU 满了就有人拿不到结果。没有排队机制，失败是随机的——有人运气好秒出图，有人一直报错。用户体验灾难。

**架构变化：加队列 + 分离 Worker**

```
用户 → [网关（Nginx）] → [App Server] → [Redis Queue] → [GPU Worker ×2]
                              ↓                                ↓
                           [PostgreSQL]              [对象存储（OSS）]
                                                             ↓
                                                          [CDN]
```

关键变化：
1. **加了队列**：请求进来不再等，先排队，GPU 慢慢消化
2. **Worker 独立**：GPU 任务跑在单独进程，App Server 不再被拖慢
3. **加了 CDN**：图片访问速度快了

用户侧体验变成：提交 → 收到"排队中" → 等待 → 收到通知 → 查看图片。

扛得住：几十到上百并发。  
新的瓶颈：**App Server 单点**——它挂了整个系统瘫痪。

---

### 十万人版（爆发增长，日活万人以上）

**现在的架构哪里扛不住了？**

- App Server 单点：一台机器挂了，全挂
- GPU Worker 固定数量：高峰期排队几百个任务，低谷期 Worker 闲置烧钱
- 数据库单点：读写全压在一台机器上

**架构变化：水平扩展 + 弹性伸缩 + 高可用**

```
用户
  ↓
[负载均衡 Load Balancer]
  ↙           ↘
[App Server 1] [App Server 2]  ← 水平扩展，任意一台挂了另一台顶上
       ↓
[Redis Queue]
  ↙    ↓    ↘
[Worker] [Worker] [Worker]     ← 按队列长度弹性增减，高峰多起几个
       ↓
[数据库主节点] → [数据库从节点×2]  ← 主写从读，分担读压力
       ↓
[对象存储] → [CDN]
```

**三个新概念从这里长出来：**

**水平扩展 vs 垂直扩展**  
垂直扩展：把一台服务器换成更强的——简单，但有上限，而且单点风险更高。  
水平扩展：多跑几台一样的服务器——有上限吗？理论上没有，加机器就行。  
AI 产品的 GPU Worker 通常做垂直（单卡换多卡），App Server 做水平（多台跑）。

**弹性伸缩（Auto Scaling）**  
队列里积压超过 100 个任务 → 自动多起 2 个 Worker。  
队列空了 30 分钟 → 自动关掉多余的 Worker。  
这是 GPU 成本控制的核心手段。没有弹性伸缩，你要么高峰期扛不住，要么低谷期烧钱。

**冷启动问题**  
Worker 自动关掉后，下次要用需要重新启动——加载模型可能要 30-60 秒。用户提交任务后等了 1 分钟才开始处理，体验很差。  
解法：**保底保留 1-2 个 Worker 永不关闭**，保证队列里的任务立刻有人处理；高峰期再弹性增加。

**熔断（Circuit Breaker）**  
某个下游服务（比如模型 API）持续报错 → 不要一直重试让它更崩，而是"断路"，直接返回降级结果（"服务繁忙，请稍后再试"）。等下游恢复了再重新接通。  
熔断的本质：**主动承认局部失败，防止故障扩散成全局崩溃**。

## 6. 研发在争什么

**争一：队列用 Redis 还是专业消息队列（Kafka/RabbitMQ）？**

Redis Queue：简单、够用、运维成本低。  
Kafka：高吞吐、消息持久化、复杂消费逻辑。  
争的核心是：你的任务量到底有多大？消息丢了能重来吗？早期几乎都应该选 Redis，Kafka 的复杂性在小规模是纯负担。

**争二：GPU Worker 是用自有服务器还是云端按需调用（如 AWS GPU Spot）？**

自有：固定成本，低延迟，但闲置时烧钱，峰值扛不住。  
云端 Spot：按用量付费，弹性强，但冷启动慢，偶尔会被云厂商"抢走"机器。  
这个选择本质上是**成本结构 vs 可预测性**的 tradeoff，没有标准答案，看你的流量曲线。

**争三：异步通知用 WebSocket 还是轮询（Polling）？**

WebSocket：服务端主动推，实时性好，但有连接状态，横向扩展麻烦。  
轮询：客户端每 3 秒问一次"好了吗"，简单粗暴，但浪费请求，延迟感强。  
研发通常会争这个，但对于 AI 生图（30 秒才出结果）——3 秒轮询一次完全够用，过度追求 WebSocket 是提前优化。
