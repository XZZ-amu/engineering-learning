# P1-4: WebSocket 与实时通信

## 1. 一句话本质

**HTTP 是"请求-响应"的寄信模式——客户端问，服务器才能答；实时通信要解决的根本问题是：让服务器能主动开口说话。**

从这句话出发，后面所有概念——长连接、WebSocket、SSE、心跳、断线重连——都是在不同约束下实现"服务器主动开口"的不同方案。

---

## 2. 为什么必须这样（不这样会出什么事）

想象 Mindloop 要做一个 AI 生成思维导图的功能。用户点击"生成"，AI 需要 30 秒处理。**如果只用标准 HTTP：**

用户点击 → 发出一封信 → 等 30 秒 → 服务器回信

这 30 秒里发生了什么？用户完全不知道。界面上只能转圈圈。服务器其实在 5 秒时完成了 20%、15 秒时完成了 60%……但它没办法主动告诉客户端，因为它没有客户端的"地址"——HTTP 连接用完就断了，服务器根本找不到门在哪。

**被逼出来的临时方案——轮询：**

```
客户端每隔 2 秒问一次："好了吗？好了吗？好了吗？"
```

轮询能用，但有两个代价：
1. **延迟**：进度变化最多滞后 2 秒才能显示
2. **浪费**：99% 的请求得到的回答都是"还没好"

真正的问题是：**HTTP 协议本身是无状态的单向会话——服务器不存储连接，说完就忘。** 要让服务器能主动开口，必须改变底层机制。

---

## 3. 概念地图

```
根本问题：服务器如何主动推送消息给客户端？
│
├── 方案 A：不改协议，客户端反复主动问
│   └── 轮询（Polling）
│       ├── 短轮询：每隔 N 秒发一次请求
│       └── 长轮询：服务器"挂住"请求，有消息再回
│
├── 方案 B：HTTP 升级，保持连接，服务器单向推
│   └── SSE（Server-Sent Events）
│       ├── 基于 HTTP，但连接不断
│       └── 服务器 → 客户端，单向
│
└── 方案 C：升级为新协议，双向实时通道
    └── WebSocket
        ├── 握手时借用 HTTP，之后独立协议
        ├── 客户端 ↔ 服务器，双向
        └── 连接管理
            ├── 心跳（Heartbeat）——保持连接活着
            ├── 断线重连（Reconnect）——连接死了怎么办
            └── 消息顺序保证——消息乱序怎么处理
```

这三种方案不是并列的替代品——它们是按"改造程度"排列的，改造越深，能力越强，复杂度越高。

---

## 4. 逐个概念深入

### 轮询：用已有工具凑合

**短轮询**是最直觉的方案：客户端每 2 秒发一个 HTTP 请求问进度。简单，但浪费。

**长轮询**聪明一点：客户端发请求，服务器不立刻回，而是"挂住"这个连接，等到有新消息才回复。客户端收到回复后立刻再发下一个请求。这样延迟接近实时，但本质上还是"一问一答"——只是问的方式变聪明了。

> 研发什么时候选轮询：消息频率很低（比如每分钟一次）、或者你不想引入 WebSocket 的复杂性、或者旧系统只支持 HTTP。

---

### SSE：HTTP 协议的"半步进化"

SSE 是个很优雅的小东西。它本质上还是 HTTP 请求，但服务器回复时，响应头声明"我会持续发数据，别关连接"，然后像水龙头一样源源不断地把消息推过来。

```
对讲机类比：SSE 是广播电台——发射塔（服务器）一直播，你（客户端）一直收，但你不能向电台说话。
```

**SSE 的设计取舍：**
- ✅ 基于 HTTP，天然支持自动重连、消息 ID（断线续传）
- ✅ 简单，前端用 `EventSource` API，几行代码搞定
- ❌ 单向：客户端无法通过同一个通道回话
- ❌ 部分老浏览器和代理服务器会截断长连接

**SSE 是生成进度推送的最佳选择**（后面说为什么）。

---

### WebSocket：真正的双向通道

WebSocket 的第一步借用了 HTTP：客户端发一个特殊的 HTTP 请求，说"我想升级协议"，服务器同意后，这条连接就从 HTTP 协议切换成 WebSocket 协议，变成一条**持久双向通道**，直到任意一方主动断开。

```
握手过程：
客户端 → 服务器：HTTP Upgrade 请求
服务器 → 客户端：101 Switching Protocols（同意升级）
——此后——
客户端 ↔ 服务器：WebSocket 帧，双向，随时可发
```

```
对讲机类比：WebSocket 是真正的对讲机——双方都能随时说话，连接不断。
```

**WebSocket 的设计取舍：**
- ✅ 真正双向，延迟极低
- ✅ 适合高频双向通信：多人协作、聊天、实时游戏
- ❌ 有状态连接，服务器要维护每个用户的连接，水平扩展更复杂
- ❌ 比 SSE 重，需要专门的连接管理逻辑

---

### 连接管理三件套

建立连接不够，**维持连接才是难点**。

**心跳（Heartbeat）**：网络路由器为了节省资源，会悄悄断掉"长时间无数据"的连接。心跳就是客户端或服务器每隔一段时间互相发一个空消息（ping/pong），告诉路由器"我们还在用这条连接，别断"。

**断线重连**：网络抖动、手机切换 WiFi、服务器重启——连接随时可能断。客户端需要检测到断线后，自动发起重连，而不是傻等。策略一般是"指数退避"：断了先等 1 秒重连，失败再等 2 秒，再失败等 4 秒……避免所有客户端同时重连把服务器冲垮。

**消息顺序保证**：在高并发或网络抖动时，消息可能乱序到达。比如"进度 50%"比"进度 30%"先到。解决方式是给每条消息加序号，客户端按序号排列，或者对于进度这种场景，只保留最新的那条。

## 5. 研发在争什么

### 争论一：生成进度用 SSE 还是 WebSocket？

这是个有标准答案的争论，但你得知道判断依据：

**生成进度推送的场景特征：**
- 信息流向是单向的：服务器知道进度，推给客户端
- 客户端不需要通过同一个通道回话（取消操作可以发一个新的 HTTP 请求）
- 是一次性的任务，不是持久连接

**结论：SSE 更合适。** WebSocket 能做但"杀鸡用牛刀"——多了不必要的复杂性。如果研发说"我们用 WebSocket 做进度推送"，不是错，但你可以问：为什么不用 SSE？

**WebSocket 真正适合的场景：**
- 多人协同编辑（你改了文档，我要实时看到，我的光标位置服务器也要知道）
- 聊天室（双向）
- 在线对战游戏

---

### 争论二：推送服务统一用 WebSocket，还是场景分开选？

有些团队倾向于"大一统"：既然 WebSocket 能做所有事，干脆所有实时功能都走 WebSocket，运维只维护一套基础设施。

有些团队倾向于"按需选型"：进度推送用 SSE，聊天用 WebSocket，简单通知用长轮询。

**代价对比：**
- 大一统：实现复杂，但基础设施统一，长期维护成本低
- 按需选型：每种方案学习成本，但每个场景最简单的解法

对于早期产品：按需选型更务实。Mindloop 如果只是做 AI 生成进度，上 SSE 就够，不必为"以后可能要的聊天功能"现在就搭 WebSocket 架构。

---

### 争论三：断线重连后，怎么知道错过了哪些消息？

这个问题研发内部也常常争论。三种策略：
1. **不管**：重连后从当前状态开始，错过的就错过了（进度条场景可以接受）
2. **消息 ID + 断点续传**：SSE 内置支持，重连时带上最后收到的消息 ID，服务器补发错过的
3. **客户端主动拉取**：重连后发一次 HTTP 请求同步完整状态，再开始监听推送

选哪个取决于"错过消息的代价"。进度条错过几帧无所谓；多人协同文档丢失一次编辑操作就是 bug。

**问题一**：用你自己的话，解释"为什么 HTTP 不能让服务器主动推送消息"，以及 WebSocket 是怎么绕过这个限制的。

---

**问题二**：Mindloop 要做两个功能：
- 功能 A：AI 生成思维导图，需要实时显示进度（0% → 100%）
- 功能 B：多人同时编辑同一个节点，互相看到对方的光标位置

研发给你两个方案：
- 方案 X：两个功能都用 WebSocket
- 方案 Y：功能 A 用 SSE，功能 B 用 WebSocket

你会选哪个？理由是什么？

---

**问题三**：研发说"我们的 AI 生成进度推送，用短轮询就够了，每 1 秒问一次"。你觉得这个方案有没有问题？如果用户量从 100 人涨到 10000 人同时生成，会发生什么？
