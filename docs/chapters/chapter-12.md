# WebSocket 与实时通信

## 1. 一句话本质

**HTTP 是"你问我答"，实时通信是"你不问，我也能说"——所有方案都是在 HTTP 的单向结构上，想办法让服务器获得"主动开口"的能力。**

---

## 2. 为什么必须这样

想象 Mindloop 有个功能：用户点击"AI 生成封面图"，服务器要跑 30 秒。

用标准 HTTP 会怎样？

- 前端发请求，然后等
- HTTP 没有"中途告诉你进度"的机制
- 要么等 30 秒一次返回（用户以为卡死了）
- 要么前端每秒问一次"好了吗"（轮询）——你在不停打电话给快递员

轮询能解决，但代价是：每次"问"都是一个完整 HTTP 请求，哪怕对方没什么新消息，你也要打过去建连接、发请求、收响应、关连接。每秒一次，30 秒就是 30 次完整握手。

更深的问题：服务器 **天然没有"主动联系客户端"的地址**。HTTP 只有一个方向——客户端知道服务器在哪（URL），服务器不知道客户端在哪。没有连接存在，服务器想说话，找不到门。

所有实时方案都是在解这同一个问题：**怎么让一个只能"被动接受连接"的服务器，获得"主动推消息"的能力。**

---

## 3. 概念地图

```
根问题：服务器无法主动联系客户端
           │
           ▼
    解法思路分两支
    ┌─────────────────┬─────────────────────────┐
    │  客户端主动来问  │   建立持久通道，主动推    │
    └────────┬────────┘           │              │
             │              单向推送        双向通道
          轮询 Polling      SSE (单工)    WebSocket (全双工)
         （最简单）        （轻量）        （最强）
             │                   │              │
       每隔N秒发请求        连接保持不断     握手一次
       浪费带宽            服务端随时推     双向随时说
       有延迟              无法从客户端推   连接管理复杂

以上三种方案都需要面对：
    │
    ├── 连接管理：心跳检测连接是否存活
    ├── 断线重连：网络抖动后如何恢复
    └── 消息顺序：消息乱序/丢失怎么处理
```

---

## 4. 逐个概念深入

### 轮询（Polling）

不是新技术，就是前端定时发 HTTP 请求。

**它的问题**：浪费资源。30 秒生成过程里，大多数时刻服务器没新消息。你每次问，建立连接、传输数据、关闭连接，全是开销，信噪比极低。

**它的价值**：实现最简单，不需要后端任何额外支持，调试最容易。当事件频率低（比如每 5 分钟刷新一次数据），轮询反而比维护长连接更合理。

> 核心判断：**事件频率高、延迟敏感** → 轮询太贵；**事件频率低** → 轮询够用。

---

### SSE（Server-Sent Events）

SSE 的思路很直接：建立一个普通 HTTP 连接，但不关闭它，服务器用这条连接持续往里塞数据。

**类比**：你打开收音机频道（建立连接），电台一直广播（服务器持续推），你只能听不能说话（单向）。

**它的优势**：
- 基于标准 HTTP，防火墙不拦，CDN 可以透传
- 浏览器原生支持，自带断线重连
- 实现比 WebSocket 简单得多

**它的限制**：单向。服务器推给客户端，客户端只能通过另开 HTTP 请求来"回话"。

**AI 生图进度推送**，SSE 是最合适的方案——服务器在算，客户端只需要接收进度，不需要双向对话。

---

### WebSocket

WebSocket 的设计动机是：HTTP 连接建立时，双方先做一次"协议升级"握手——"我们不说 HTTP 了，换成 WebSocket 协议"——握手完成后，这条 TCP 连接就变成了双向通道，双方都可以随时发消息，就像一直开着的对讲机。

**对讲机 vs 寄信**：HTTP 是寄信（你发一封，等一封回信，一个来回），WebSocket 是对讲机（接通之后，谁想说话按按钮就说）。

**它的代价**：
- 连接管理复杂：需要自己维护连接状态，处理断线
- 服务端资源占用：每个在线用户都占一个持久连接
- 对基础设施有要求：部分代理/负载均衡需要额外配置

**什么时候才值得用 WebSocket**：
- 双向实时通信（聊天、协同编辑）
- 高频双向数据（实时游戏、交易看盘）
- 需要服务器和客户端"随时互相说话"的场景

Mindloop 如果做多人协同编辑（A 改了标题，B 立刻看到），WebSocket 是必选——因为 B 的操作也需要实时传回服务器。

---

### 连接管理：心跳、断线重连、消息顺序

这三个是任何长连接方案都要面对的运维问题。

**心跳（Heartbeat）**：连接建立后，双方周期性互发一个空消息（ping/pong）。如果一段时间没收到心跳，认定连接死了。为什么需要？因为网络中间节点（路由器、NAT）会悄悄丢弃长时间没流量的连接，两端不知道，以为连接还在，实际上消息已经发不出去了。

**断线重连**：网络抖动时连接断了，客户端要能自动重建连接。关键是要做指数退避——不要断了就每秒疯狂重连，应该等 1 秒、2 秒、4 秒、8 秒……逐渐拉长间隔，避免服务器压垮。

**消息顺序**：断线重连期间，服务器可能已经推了几条消息，客户端没收到。解法是给每条消息一个序列号，重连时客户端告诉服务器"我最后收到的是 #42"，服务器从 #43 开始补发。SSE 原生支持这个（`Last-Event-ID` 头）。

## 5. 研发在争什么

### "AI 生图进度推送用 SSE 还是 WebSocket？"

**SSE 派**：生图这个场景是单向的，服务器推进度，客户端只看不说。SSE 够用，实现简单，不需要维护双向通道的复杂逻辑。

**WebSocket 派**：如果 Mindloop 以后还要做聊天、协同等功能，WebSocket 的连接可以复用——建一条通道，所有实时消息都走这里，不用为不同功能维护多条连接。

**核心 tradeoff**：SSE = 简单但单向；WebSocket = 复杂但通用。如果只做进度推送，SSE；如果整个产品有多个实时场景，提前建 WebSocket 基础设施更合算。

---

### "要不要直接轮询，别整那些复杂的？"

这是真实存在的争论。轮询的代码量可能只有 SSE 的五分之一。

对于 Mindloop 这种单机桌面应用，服务器并发量有限，用轮询（比如每 2 秒问一次）未必是错误选择。复杂度有成本，简单有简单的价值。

**判断标准**：并发用户多 + 事件高频 + 延迟敏感 → 轮询成本高，值得用 SSE/WebSocket；并发少 + 事件低频 + 延迟不敏感 → 轮询可接受，别过早优化。

---

### "断线重连的消息要不要保证不丢失？"

对进度推送：不需要。进度是 0→50→100，中间漏掉了 50 没关系，下次收到 100 就够了，消息本质是"最新状态"而不是"事件序列"。

对聊天消息：必须保证。漏掉一条就是漏掉了，用户会发现。

这个区别影响后端存不存消息、用不用消息队列——根问题不同，方案也不同。

## 6. 考考你

???+ quiz "Mindloop 要新增一个功能：多人实时协同编辑笔记，A 修改了标题，B 的界面要在 1 秒内看到变化，同时 B 的光标位置也要实时同步给 A。应该选哪种方案？"
    - [ ] A. 轮询，每秒请求一次最新内容
    - [ ] B. SSE，服务器推送变更事件给客户端
    - [x] C. WebSocket，建立双向通道
    - [ ] D. 普通 HTTP，操作完刷新页面

    ??? success "解析"
        协同编辑是典型的双向实时场景：A 的改动要推给 B（服务器→客户端），B 的光标位置要传给服务器再推给 A（客户端→服务器→客户端）。SSE 只能单向，客户端无法通过 SSE 主动发数据给服务器，所以排除。轮询延迟太高（1 秒内同步需要至少 500ms 轮询间隔，代价大）且双向感很差。WebSocket 建立一条双向通道，双方随时发消息，是这个场景的标准答案。

???+ quiz "以下关于 SSE 和 WebSocket 的说法，哪个最准确地描述了它们的本质区别？"
    - [ ] A. SSE 比 WebSocket 更快，适合高频场景
    - [ ] B. WebSocket 需要特殊浏览器支持，SSE 不需要
    - [x] C. SSE 是单向推送（服务器→客户端），WebSocket 是双向通道（双方随时互发）
    - [ ] D. SSE 不能断线重连，WebSocket 可以

    ??? success "解析"
        核心区别是方向性。SSE 复用 HTTP 连接，只有服务器→客户端这一个方向；客户端想"说话"得另开 HTTP 请求。WebSocket 是协议升级后的双向通道，双方都可以随时发消息。A 错误，速度取决于网络和消息频率，不是协议本身；B 错误，两者都有良好的浏览器支持；D 错误，SSE 原生支持断线重连，反而是 WebSocket 需要自己实现重连逻辑。

???+ quiz "团队在争论 AI 生图进度推送用 SSE 还是轮询（每 3 秒一次）。有人说"轮询代码更简单，别过度设计"，有人说"SSE 体验更好"。以下哪个判断视角最合理？"
    - [ ] A. 永远选 SSE，轮询是落后技术
    - [ ] B. 永远选轮询，复杂度有成本
    - [ ] C. 看团队技术水平，哪个熟用哪个
    - [x] D. 看并发用户数和延迟要求：用户多或要求秒级更新，SSE 更合适；单机工具且用户少，轮询可接受

    ??? success "解析"
        没有"永远正确"的答案，这是 tradeoff 题。轮询的成本是：每次轮询建立完整 HTTP 连接，用户多时服务器压力大；而且有固定延迟（最坏情况 = 轮询间隔）。SSE 的成本是：实现略复杂，需要后端支持流式响应。Mindloop 是桌面单机工具，并发用户极少，3 秒轮询未必是错误选择。但如果是 SaaS 产品有大量并发用户，SSE 的优势就体现出来了。判断依据是实际约束条件，不是技术的"先进性"。
