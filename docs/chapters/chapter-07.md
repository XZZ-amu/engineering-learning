# 文件与存储：图片从生成到用户看到，中间发生了什么

## 1. 一句话本质

**文件存储要解决的问题是：大文件不能和数据放一起，但它们需要被全球用户快速拿到——所以要有专门存的地方（OSS），专门送的网络（CDN），以及把文件变成合适形态的流水线（图片处理/转码）。**

## 2. 为什么必须这样

想象 Mindloop 支持 AI 生图，每张图 2MB。用户生成一万张，就是 20GB。

**如果直接存数据库会发生什么？**

数据库的设计目标是高频读写结构化数据（文字、数字、关系），它的存储单元是行和列，不是字节流。你把一张 2MB 的 JPEG 塞进去：

- 数据库文件急剧膨胀，索引变慢
- 每次查"用户有哪些图"的 SQL，光是扫描行就要把图片二进制带着跑
- 备份一次数据库要传几十 GB
- 用户访问时，图片必须先从数据库读出来，经过你的服务器，再到用户——你的服务器变成了图片搬运工，带宽烧钱，还慢

**如果存服务器本地磁盘会发生什么？**

- 服务器磁盘满了就完了
- 你有多台服务器，图片在 A 上，用户请求落到 B，找不到
- 离北京用户远的服务器，访问延迟高
- 服务器挂了，图片没了

这两条路都是死路。所以才逼出了现在的分工：**数据库存元数据（谁的图、什么时候生成、放在哪），文件存专门的地方。**

## 3. 概念地图

```
用户生成一张 AI 图片
         │
         ▼
    [上传到 OSS]          ← 仓库，存原始文件
    bucket/key/权限
         │
         ├──► [图片处理流水线]   ← 生成缩略图、WebP、裁剪
         │         │
         │         ▼
         └──► [CDN 分发网络]    ← 快递网络，送到离用户最近的节点
                   │
                   ▼
            用户浏览器看到图片
                   
    另一条链：视频
    上传 OSS → 转码 + HLS 切片 + 封面帧提取 → CDN → 播放器
    
    访问控制：
    公开图片 → 直接 CDN URL
    私密图片 → URL 签名（临时链接）
```

## 4. 逐个概念深入

### 对象存储（OSS/S3）：仓库

**解决什么问题**：需要一个能无限堆文件、便宜、高可靠、全球可访问的地方。

类比：就是一个巨大的仓库，里面放无数个盒子（文件），每个盒子有唯一地址（key）。

**三个核心概念**：

- **Bucket**：仓库的一个分区。Mindloop 可能有 `mindloop-images`、`mindloop-videos` 两个 bucket，隔离管理
- **Key**：文件在 bucket 里的唯一路径。比如 `users/uid_123/ai_gen/img_456.jpg`——它不是真实的文件夹结构，只是一串字符串，但约定用 `/` 分隔方便管理
- **权限**：每个 bucket 或文件可以设置"公开读"或"私有"。公开读的文件任何人有 URL 就能访问；私有文件需要签名才能访问

OSS 本质上就是：**给一个 key，存一坨字节；给一个 key，取一坨字节。** 没有别的。

---

### 上传方式：谁来搬货

**直传 vs 服务端中转**是一个 tradeoff。

```
中转方案（慢/贵）：        直传方案（快/省）：
用户 → 你的服务器 → OSS    用户 → OSS（直接）
                           用户上传前先找服务器拿临时凭证
```

**为什么直传更好**：2MB 图片从用户传到你的服务器，再从你的服务器传到 OSS，你的服务器带宽走了两次，而且你的服务器要等上传完成才能响应。直传让用户直接把文件发给 OSS，你的服务器只需要颁发一个"通行证"（临时凭证）。

**分片上传 + 断点续传**：针对大文件（视频）。把一个 500MB 的视频切成 50 个 10MB 的块，并行上传。网断了从第 23 块继续，不用从头来。图片一般不需要，视频必须有。

---

### CDN：快递网络

OSS 是仓库，但仓库只有一个地址（比如在北京）。深圳用户每次看图都要去北京取，延迟高。

**CDN 做的事**：在全国（乃至全球）部署几百个"前置仓库"（边缘节点）。第一个深圳用户请求某张图，CDN 从北京 OSS 取来，顺手存在深圳节点上。之后所有深圳用户直接从深圳拿，速度快 10 倍。

**缓存失效**：图片被 CDN 缓存后，如果你更新了原图，CDN 不知道。解法：**文件名带版本号或 hash**。新图 = 新 key = 新 URL，CDN 自然取新文件。Mindloop 的 AI 图片每次都是新生成的，key 包含唯一 ID，天然没有这个问题。

**什么时候不需要 CDN**：

- 内网系统（公司内部工具），用户都在同一个地方
- 文件很少被访问（私密文件、低频业务），CDN 缓存没有价值
- 临时文件，用完就删

**什么时候必须 CDN**：面向 C 端、图片/视频是核心体验、用户分布全国。Mindloop 如果做 SaaS，AI 图片必须走 CDN。

---

### 图片处理流水线：变形

原始图片存进去了，但不是每个场景都要用原图。

**缩略图**：列表页展示 200×200 的缩略图，不需要加载原始 2MB 图。缩略图可以在上传后立刻生成存一份，也可以用 OSS/CDN 的"URL 参数动态处理"——在 URL 后面加 `?w=200&h=200`，CDN 节点实时裁剪并缓存结果。后者更灵活，不需要存一堆不同尺寸的副本。

**WebP 转换**：同样视觉质量，WebP 比 JPEG 小 30%。手机用户加载速度差异明显。现代 CDN 可以自动检测浏览器是否支持 WebP，支持则返回 WebP，不支持返回 JPEG。

**原则**：原图存 OSS 一份，其他尺寸/格式通过 CDN 的图片处理能力动态生成，而不是存一堆副本。

---

### 视频特有：转码和 HLS

视频比图片复杂，多了两个问题：

**格式不统一**：用户上传 MOV、AVI 等格式，不是所有浏览器都能播。要转成 H.264/MP4 这种通用格式。

**HLS 切片**：一个 1GB 视频文件，用户不会等全部加载完再看。HLS 把视频切成几秒一段的小片段，播放器边下边播，还能根据网速动态切换清晰度（720p/1080p）。

**封面帧提取**：视频上传后自动截第 N 帧作为封面，存成图片，走图片流水线。

这些处理都是异步的：用户上传视频 → 服务器返回"上传成功" → 后台任务队列开始转码（可能需要几分钟）→ 完成后更新数据库里的视频状态为"可播放"。

---

### URL 签名：门票

OSS 上的私密文件，直接访问会 403。签名 URL 是：服务端生成一个带过期时间的特殊 URL，用户用这个 URL 访问，OSS 验证签名有效就放行。

用途：付费内容（没买不能看）、私密文档（只有本人能看）。Mindloop 如果做私有笔记里的图片附件，就该用签名 URL，而不是直接把 OSS key 暴露出去。

## 5. 研发在争什么

**争一：上传走直传还是中转？**

直传更快更省，但有安全顾虑——临时凭证的权限要控制好，否则用户可能上传到不该上传的地方。小团队早期图省事走中转也行，但用户量大了必然要换直传。

**争二：图片处理存副本还是动态生成？**

存副本（提前生成 200x200、400x400 两种尺寸）：请求时直接取，快，但存储翻倍，且需求变了（要 300x300）要重新跑。动态生成：灵活，但首次请求有处理延迟，CDN 缓存前每个尺寸都要算一次。中大型产品基本走动态 + CDN 缓存。

**争三：视频转码在哪转？**

自建 FFmpeg 转码服务器：成本可控，但要维护，高峰期排队。用云厂商的媒体处理服务：按量付费，开箱即用，但贵。早期用云服务，规模大了再自建。

## 6. 完整链路：AI 生图从产生到用户看到

```
① 用户点击"生成"
② 服务端调用 AI 模型，生成 PNG 原图（内存中）
③ 直接上传到 OSS
   key: users/123/gen/img_789.png
④ 触发图片处理：
   - 生成 WebP 版本
   - CDN URL 参数处理缩略图（不存副本）
⑤ 数据库写入一行记录：
   { user_id: 123, oss_key: "users/123/gen/img_789.png", 
     cdn_url: "https://cdn.mindloop.app/...", status: "ready" }
⑥ 前端拿到 CDN URL，发起请求
⑦ CDN 边缘节点：有缓存 → 直接返回；没有 → 回源 OSS 取，缓存后返回
⑧ 浏览器展示图片
```
