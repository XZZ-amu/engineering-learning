# P0-3：文件与存储 — 图片/视频从产生到用户看到

## 1. 一句话本质

**大文件（图片/视频）的挑战在于"体积"：体积决定了它必须被单独存、单独传、单独处理——而不能像数据一样被普通数据库随便塞进去。所有文件存储方案，本质都是在解决"怎么让大体积的东西存得便宜、传得快、展示得对"这三件事。**

---

## 2. 为什么必须这样

先做一个思想实验：假设你不知道 OSS/CDN 的存在，用最朴素的方式处理图片。

**方案 A：存数据库**

把图片 base64 编码后塞进 MySQL 的 `text` 字段。一张 1MB 的图，编码后变 1.3MB。数据库表里放 10 万张图，就是 130GB 的 BLOB 数据。

结果：
- 数据库查询变慢，因为每次读取用户信息都可能带出几十 MB 的图片数据
- 数据库备份变得巨慢
- 没有办法对图片做格式转换、生成缩略图
- 10 万个用户同时请求图片，数据库直接被打死——数据库根本不是为"高并发文件读取"设计的

**方案 B：存服务器本地磁盘**

把图片文件存在应用服务器的 `/uploads` 目录下。

结果：
- 部署两台服务器时，用户 A 上传的图片在服务器 1，用户 B 的请求打到服务器 2——找不到文件
- 服务器磁盘满了怎么办？
- 服务器挂了，图片也没了
- 用户在北京，服务器在上海，每次加载图片都要跨城拉数据

两个方案都是被规模逼死的——**当文件数量从 100 变成 1000 万，这两条路都走不通。**

被问题逼到这里，解法自然浮出：需要一个专门存文件、无限扩容、全球分发的系统。

---

## 3. 概念地图

```
[用户上传 / AI 生成]
        |
        ↓
   [上传方式]
   直传 vs 中转
   分片 / 断点续传
        |
        ↓
  [对象存储 OSS/S3]          ← 仓库：便宜、可靠、无限大
   Bucket / Key / 权限
   URL 签名（防盗链）
        |
        ↓
  [图片处理管道]             ← 加工：让文件以最合适的形态被展示
  缩略图 / 格式转换(WebP)
  裁剪 / 视频转码 / HLS 切片
        |
        ↓
     [CDN]                   ← 快递网络：就近取货，别每次都跑总仓库
   边缘节点 / 缓存失效
        |
        ↓
   [用户浏览器]
```

这不是五个并列功能，是**一条流水线**：存储解决"存哪"，处理解决"怎么变形"，CDN 解决"怎么传快"，权限/签名解决"谁能取"。

---

## 4. 逐个概念深入

### 对象存储（OSS / S3）：仓库

**本质**：一个 key-value 系统。key 是文件路径，value 是文件内容。`images/ai-gen/abc123.jpg` 就是一个 key，对应的 value 就是那张图的二进制数据。

没有目录，没有权限嵌套，只有扁平的 key。"目录"只是 key 名字里的斜杠，是视觉上的分组。

**Bucket**：逻辑上的命名空间，相当于仓库里的一个货架区。`mindloop-dev`、`mindloop-prod` 各一个，开发和生产数据不混。

**为什么比自建便宜**：阿里云 OSS 标准存储约 ¥0.12/GB/月。自建存储服务器，光硬件+运维+机房就不知道多少倍。而且 OSS 自带多副本、自动容灾——文件不会丢。

**URL 签名（防盗链）**：私有文件不能直接访问，需要服务端用密钥生成一个"临时 URL"，过期就失效。

```
https://oss.aliyun.com/bucket/img.jpg?token=xxx&expires=1700000000
```

这样用户分享出去的链接 1 小时后就失效，竞争对手也无法直接盗用你的图片资源。

---

### 上传方式：直传 vs 服务端中转

**服务端中转**：用户 → 你的服务器 → OSS

问题：文件先到你服务器，再转存 OSS，相当于文件走了两遍网络，浪费带宽，而且你的服务器带宽很贵。上传 100MB 视频，你要为这 100MB 的服务器入站流量付费。

**直传（前端直传 OSS）**：用户 → OSS（服务器只负责颁发临时凭证）

流程：
```
1. 前端向你的服务器请求"上传凭证"
2. 服务器生成临时 token，返回给前端
3. 前端拿着 token 直接上传到 OSS
4. 文件不经过你的服务器
```

服务器只做了鉴权，没有碰文件。带宽压力全转到 OSS 那边，而 OSS 的上传流量往往更便宜甚至免费。

**分片上传 + 断点续传**：大文件（比如视频）拆成 5MB 一片分别上传。某片失败只重传那一片，不用从头来。网断了下次从断点继续。

---

### CDN：快递网络

**本质问题**：OSS 是一个仓库，建在某个数据中心（比如上海）。全国用户都跑来上海取货，距离远的人延迟高。

CDN 的逻辑：在北京、广州、成都都建"分仓"（边缘节点）。用户第一次请求时，从上海把文件拉到就近的分仓缓存下来，后续用户直接从分仓取，不用再跑上海。

```
上海 OSS（源站）
    ├── 北京节点（缓存）  ← 北京用户就近取
    ├── 广州节点（缓存）  ← 广州用户就近取
    └── 成都节点（缓存）  ← 成都用户就近取
```

**缓存失效**：如果图片更新了，边缘节点还在用旧版本怎么办？

两个解法：
- 主动刷新 CDN 缓存（调 API 强制清除）
- 更好的做法：文件名带内容 hash，`img-abc123.jpg`，改了内容就是新 key，CDN 自然取新文件，旧文件自然过期

**什么时候不需要 CDN？**：内网系统、只有几十个内部用户、文件不面向公众。CDN 有成本，不是每个项目都要上。

---

### 图片处理管道

**为什么要处理？**：AI 生成的原图可能是 4096×4096 的 PNG，3MB。用户在列表页看缩略图，加载 3MB 纯属浪费，200×200 的 WebP（30KB）就够了。

**缩略图**：不是前端 CSS 缩放（图片还是全量下载了），而是服务端真的生成一张小图。OSS 自带图片处理参数：

```
原图：https://cdn.mindloop.com/img/abc.jpg
缩略图：https://cdn.mindloop.com/img/abc.jpg?x-oss-process=image/resize,w_200
WebP：?x-oss-process=image/format,webp
```

直接在 URL 后面加参数，OSS/CDN 动态处理并缓存结果。

**格式转换（WebP）**：WebP 比 JPEG 小 25-35%，比 PNG 小更多。支持透明通道。浏览器基本全支持了。能用 WebP 就用 WebP，同等质量体积更小。

---

### 视频特有：转码与 HLS

**转码**：用户上传的视频可能是 MOV、AVI、4K 编码……浏览器播放器不一定支持。必须转成 H.264/H.265 的 MP4 或 WebM。

**HLS 切片（`.m3u8`）**：把视频切成一段段 10 秒的小文件，用一个索引文件（playlist）串起来。

好处：
- 可以根据网速自动切换清晰度（720P / 1080P）
- 用户拖进度条直接跳，不用等整个文件下载
- CDN 缓存细粒度更小，热门片段直接命中

所有在线视频平台（B 站、YouTube、抖音）都是 HLS 或类似方案。

## 5. 研发在争什么

**争一：上传时要不要校验文件类型和大小？在哪校验？**

- 前端校验：体验好，但能被绕过
- 服务端校验：安全，但文件已经上传完了才知道不合法，浪费流量
- OSS 回调：文件上传成功后 OSS 回调你的服务器，你再决定是否保留

实际项目通常三层都要：前端做基础体验，服务端做安全校验，OSS 做后置处理触发。

**争二：图片处理在哪做？实时处理 vs 预生成？**

- 实时处理（URL 参数）：灵活，不占存储，适合多种尺寸需求
- 预生成所有缩略图：延迟低（文件已经存好），但上传时要等处理完，且占额外存储
- 极高并发的情况下，实时处理会有压力，预生成更稳

没有标准答案，取决于访问量和尺寸种类的数量。

**争三：CDN 域名和 OSS 域名要不要分开？**

通常 CDN 域名（`cdn.mindloop.com`）和 OSS 源站域名分开，用户只能访问 CDN，不能直接访问源站——避免源站被刷流量，也避免绕过 CDN 的 URL 签名安全机制。但配置更复杂。

## 6. 考考你

???+ quiz "Mindloop 里，AI 生成一张图片后直接返回了服务器本地路径给前端展示。现在要部署第二台服务器，你预见到了什么问题？"
    - [ ] A. 图片会因为格式不对而无法展示
    - [x] B. 部分用户请求打到第二台服务器，找不到图片文件，出现 404
    - [ ] C. 第二台服务器会自动同步第一台的文件，但需要时间
    - [ ] D. 图片加载会变慢，因为两台服务器争抢磁盘 IO

    ??? success "解析"
        本地磁盘不共享。服务器 1 存的文件只在服务器 1 上，打到服务器 2 的请求当然找不到。这就是"存服务器本地"这条路走不通的根本原因——它在水平扩展的那一刻就崩了。解法是把文件存到两台服务器都能访问的地方：OSS。

???+ quiz "用户要在 Mindloop 里查看历史 AI 生成的图片，设计师想给每张图片加 4 种展示尺寸：列表缩略图、画廊预览、原图下载、移动端适配。研发说这个需求"存储成本会翻 4 倍"，但你作为懂行的设计师，可以提出哪个反驳？"
    - [ ] A. 四种尺寸可以存在同一个文件里，不会翻 4 倍
    - [ ] B. 数据库可以存小图，OSS 只存原图，成本不会上升
    - [x] C. OSS 支持 URL 参数实时裁剪，不需要预先存 4 个版本，只存原图即可
    - [ ] D. CDN 会自动生成缩略图，研发不用额外开发

    ??? success "解析"
        主流对象存储（阿里云 OSS、AWS S3 + CloudFront）支持在 URL 后加参数动态裁剪/转码，结果会被 CDN 缓存，后续请求直接命中缓存，不会每次重新处理。所以只存一份原图，通过不同 URL 参数满足不同场景，存储成本不翻倍。D 的描述不准确——CDN 本身不处理图片，是 OSS/图片处理服务做的，CDN 只做缓存。

???+ quiz "Mindloop 打算上线一个功能：付费用户的生成图片只有本人可以访问。下面哪个方案最合理？"
    - [ ] A. 把图片存在数据库里，每次查询时验证权限
    - [ ] B. 给图片文件名加随机字符串，不被猜到就等于安全
    - [ ] C. 在前端做判断，非付费用户不展示图片链接
    - [x] D. OSS 设置私有读，前端展示
