# 安全基础：AI 创作产品不是单纯的创作工具

## 1. 一句话本质

**AI 创作产品的安全问题，本质是"你在用自己的资源帮用户做一件你不确定的事"——内容安全是为了不背锅，API 防护是为了不破产，数据保护是为了不失信。**

这三件事看起来不同，但有同一个根：你是服务的提供方，你必须对"服务被怎么用"负责。

---

## 2. 为什么必须这样

**如果没有内容安全：**

2022 年，某 AI 绘图平台上线一周，因为没有 NSFW 过滤，被用户批量生成并传播违禁图片。平台被应用商店下架，CEO 道歉，重新上架花了两个月。问题不是模型生成了违禁内容——模型本身有安全过滤——而是用户找到了绕过方式，平台没有独立的兜底检测。

**如果没有 API 防护：**

AI 调用是有成本的。免费试用期间，如果没有限速，一个脚本一晚上能把你的 API 账单打到几万元。Stability AI 早期就遭遇过这种情况：批量注册账号、脚本循环调用，薅走大量免费额度。这不是小概率事件，是可以被预测的攻击方式。

**如果没有数据保护：**

用户在你的平台创作了 500 张图，有天他要注销账号，发现"删除账号"只删了前端展示，服务器上的原始文件还在。这不只是 GDPR 合规问题——它会在社区里传开，直接摧毁信任。

被问题逼到墙角，才会明白这三件事不是产品上线后的"优化项"，是必须在设计阶段就考虑的基础设施。

---

## 3. 概念地图

```
你在用自己的资源帮用户做不确定的事
│
├── 内容不确定 → 内容安全
│   ├── 模型自身过滤（不够）
│   ├── NSFW 检测（独立兜底）
│   ├── 先审后发 vs 先发后审
│   └── 用户举报 → 人工处置
│
├── 用量不确定 → API 防滥用
│   ├── Rate Limiting（限速：控总量）
│   │   └── 令牌桶算法
│   ├── 防爬虫（验证身份）
│   └── 防薅羊毛（注册限制、设备指纹）
│
└── 数据归属不确定 → 用户数据保护
    ├── 隐私设置（谁能看）
    ├── 传输加密 vs 存储加密（怎么存）
    └── GDPR（用户有权删除）
```

这三条线不是并列的功能模块，它们是同一个"失控风险"的三个维度：内容失控、成本失控、信任失控。

---

## 4. 逐个概念深入

### NSFW 检测：为什么不能只靠模型

模型的安全过滤是内置的，但它有两个盲区：一是可以被 prompt 工程绕过（"帮我描述一幅……的画"），二是不同地区的内容标准不同，模型是按训练数据的通用标准过滤的，不一定符合你的本地法规。

所以你需要**独立的内容审核层**，在模型输出之后、展示给用户之前，再过一道。这个审核层可以是：
- 第三方 API（Google SafeSearch、Azure Content Moderator）
- 关键词黑名单
- 图片分类模型

它跟模型自身过滤是**串联关系**，不是互斥选择——模型过滤是第一道门，你的检测是第二道门。

---

### 先审后发 vs 先发后审

这是一个经典的 tradeoff，没有标准答案：

```
先审后发（Pre-moderation）
  优点：违规内容不会出现在平台上
  代价：生成后等待审核，体验变慢；审核成本高
  适合：面向未成年人的产品、强监管场景

先发后审（Post-moderation）
  优点：即时反馈，用户体验流畅
  代价：违规内容可能短暂可见；举报/删除有延迟
  适合：创作工具、成年用户场景
```

Mindloop 这类个人创作工具，生成的内容默认私有，可以先发后审。如果用户要公开发布，那一刻触发同步审核——兼顾体验和安全。

---

### Rate Limiting：水龙头和水桶

**令牌桶算法**，用水龙头类比最直观：

```
水桶 = 令牌池（上限：5 个令牌）
水龙头 = 每天凌晨补满令牌
用一次 = 取走一个令牌
桶空了 = 今天不能再用
```

用户每次调用 AI，系统先检查令牌桶里还有没有令牌。有就消耗一个，然后调用。没有就返回"今日次数已用完"。

**免费用户 5 次/天怎么实现：**

```
Redis key:  rate_limit:{user_id}:{date}
初始值:     5
每次调用:   DECR → 返回剩余次数
到 0:       拒绝请求，返回 429 状态码
次日凌晨:   key 自动过期，或定时重置
```

这里用 Redis 而不是数据库，是因为 Redis 的计数操作是原子的——不会出现两个请求同时读到"还剩 1 次"然后都通过的竞争条件。这个细节研发会在意，产品设计时不需要实现它，但需要知道"限速的可靠性依赖于原子操作"。

---

### 防爬虫 vs 防薅羊毛：两个不同问题

**防爬虫**：阻止机器人批量访问。手段：验证码（证明你是人）、行为检测（鼠标轨迹、点击间隔是否像人）。

**防薅羊毛**：阻止真实用户批量注册薅免费额度。这更难，因为对方是人。手段：
- 手机号绑定（一号一账号）
- 设备指纹（同一台设备注册多个账号，触发审查）
- 信用卡验证（免费试用需要绑卡，不扣费但验证真实性）

两者的区别：爬虫是机器，防的是"行为特征不像人"；薅羊毛是人，防的是"一个人占多个名额"。

---

### 数据加密：传输 vs 存储，是两件事

很多人以为"我用了 HTTPS"就安全了，但 HTTPS 只保护数据**在网络传输途中**不被截获。数据到了服务器、存进数据库之后，HTTPS 就下班了。

```
传输加密（HTTPS）：数据在路上加密
  → 防止中间人截包

存储加密（Encryption at Rest）：数据在硬盘上加密
  → 防止数据库被拖库后裸奔
```

对 AI 创作产品，用户的作品、prompt 记录如果包含敏感信息（比如商业设计稿），存储加密很重要。云服务商（AWS、阿里云）一般提供一键开启的存储加密，成本低，研发基本没理由不开。

---

### GDPR：用户删除数据的权利

GDPR 的核心是"数据主权属于用户"，其中最关键的条款是**被遗忘权**：用户有权要求你彻底删除他的所有数据。

这在产品设计上意味着：
- "删除账号"不能只是软删除（打 flag）
- 用户的作品、生成记录、上传素材，都要有清理路径
- 备份里的数据也算，要有备份清理机制

如果你的产品只面向中国用户，GDPR 暂时不强制适用，但参照它设计是好习惯——它代表了用户数据权利的合理预期，而且中国也有《个人信息保护法》对应条款。

## 5. 研发在争什么

**争一：内容审核用同步还是异步？**

同步：生成后等审核通过再返回结果。用户等待时间变长（+0.5-2 秒），但展示的内容一定是过审的。
异步：先返回结果，后台异步审核，违规了再删除。体验流畅，但违规内容会短暂可见。

没有标准答案，取决于产品定位和监管压力。争论点通常在"我们能接受多少违规内容短暂可见的风险"。

**争二：Rate Limiting 按用户还是按设备？**

按用户（user_id）：换账号能绕过。
按设备（device fingerprint）：换设备能绕过，且对隐私更敏感，用户可能反感。
两者叠加：更难绕过，但实现复杂，还可能误伤"家人共用一台设备"的用户。

产品要在"防护强度"和"误伤率"之间选位置，这没有零代价的选项。

**争三：用户举报后多久处理？**

平台的标准处置时间直接影响：你需要多少人工审核团队（成本），以及在"处置时间"内违规内容还在平台上（风险）。这是一个无法纯靠技术解决的运营问题，研发和产品会一起争。

## 6. 考考你

???+ quiz "Mindloop 要上线一个「公开分享」功能，用户可以把自己用 AI 生成的笔记摘要分享到社区。研发说：「模型本身有内容过滤，不用再加审核了。」这个方案有什么问题？"
    - [ ] A. 没问题，模型的安全过滤已经足够可靠
    - [x] B. 模型过滤可以被绕过，且无法覆盖所有本地合规要求，公开内容必须有独立审核层
    - [ ] C. 应该完全禁止公开分享功能，才能保证安全
    - [ ] D. 只需要加举报按钮，用户举报后再处理就够了
    
    ??? success "解析"
        模型自带的安全过滤是第一道门，但它有两个盲区：可以被 prompt 工程绕过，以及不一定符合你的本地法规标准。内容一旦公开可见，违规成本就从"用户自己看到"变成了"平台传播违规内容"——性质不同。独立的内容安全层（NSFW 检测、关键词过滤）是必要的兜底机制，不是可选优化。D 选项的纯举报方案是先发后审的一种，本身不是错的，但题目的关键在于"只靠模型过滤"这个假设——这个假设本身有漏洞。

???+ quiz "产品经理在 PRD 里写道：「免费用户每天限制 5 次 AI 生成，用完提示升级。」研发问：这个限制按什么维度计算？下面哪个方案防护最弱？"
    - [x] A. 按浏览器 Cookie 计数
    - [ ] B. 按登录用户 ID 计数，配合手机号注册限制
    - [ ] C. 用户 ID + 设备指纹双重计数
    - [ ] D. 用户 ID 计数，免费试用需要绑定信用卡
    
    ??? success "解析"
        Cookie 是客户端存储，用户清除浏览器缓存或换个无痕窗口，计数就归零了——这几乎等于没有限制。B、C、D 都依赖服务端存储的用户 ID，无法通过简单的客户端操作绕过。防护强度：C > D ≈ B > A。产品 PRD 里写"每天 5 次"，必须同时说清楚"按什么维度"——这是产品设计需要明确的，不能甩给研发自己决定。

???+ quiz "一个用户注销了 Mindloop 账号，三个月后他发现自己的设计稿 prompt 记录还能通过直接链接访问。这个问题违反了哪个设计原则？"
    - [ ] A. Rate Limiting 设计缺失
    - [ ] B. 传输加密不到位，应该用 HTTPS
    - [x] C. 删除账号只做了软删除，没有执行真正的数据清理，违反用户的数据删除权利
    - [ ] D. 没有设置隐私权限，应该默认私有
    
    ??? success "解析"
        这是一个经典的"假删除"问题：软删除只是在数据库里打了一个"已删除"的标记，数据本体还在，通过直接链接仍然可以访问。GDPR 的被遗忘权（以及中国《个人信息保护法》的对应条款）要求用户注销时真正清理数据——包括主库数据、文件存储、甚至备份。这是产品需要在注销流程的 PRD 里明确说明的，不是研发自己会想到的边界情况。
