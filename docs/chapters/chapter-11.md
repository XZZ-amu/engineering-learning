# P1-3：认证与付费——登录、Token、OAuth、计费、订阅

---

## 1. 一句话本质

**认证与付费，本质是同一件事：系统需要在每次请求时知道"你是谁"、"你有没有资格做这件事"、"你还剩多少额度"——这三个问题的答案必须可信、可查、可回滚。**

从这句话可以推导出所有概念：登录是建立"你是谁"的信任；Token 是携带这个信任的方式；OAuth 是把信任建立的过程委托给别人；权限模型是回答"有没有资格"；计费是追踪和消耗"剩多少额度"；订单状态机是在出错时保证可回滚。

---

## 2. 为什么必须这样

假设没有任何认证机制，你的 AI 生图接口是裸着的：任何人调一次接口就消耗你一次 GPU 算力，你没法知道是谁调的，没法限流，没法收钱，没法退款。

那加个账号密码呢？用户登录一次，之后每次请求都要带密码？密码就会在网络里反复传输，拦一次就全完了。

好，那服务器记住登录状态——这就是 Session。但服务器记了一亿个用户的状态，机器一多就乱了，Session 没法跨机器共享。

那不让服务器记，把状态塞进一个签名的小票给客户端自己拿着——这就是 Token/JWT。

然后用户说：我不想再注册一个账号了，我用微信登录行吗？你需要信任微信说"这个人是谁"——这就是 OAuth。

每个方案都是被具体的问题逼出来的，没有谁是"规矩"。

---

## 3. 概念地图

```
用户发起请求
    │
    ▼
【认证层：你是谁？】
    ├── 登录（密码/手机号）→ 服务器发小票
    │       ├── Session（服务器记状态）
    │       └── Token/JWT（客户端自己拿着状态）
    │
    └── 第三方登录（OAuth）→ 微信/Google 替你证明身份
            └── 最终也颁发 Token，后续流程一样

    │（身份确认后）
    ▼
【授权层：你能干什么？】
    └── RBAC 权限模型
            ├── 角色：免费用户 / 会员 / Pro / 管理员
            └── 权限：能用哪些功能 + 能用多少次

    │（有权限后）
    ▼
【计费层：你还剩多少？】
    ├── 按次计费（用一次扣一次）
    ├── 订阅制（包月，按时间解锁权限）
    └── 积分制（预充值，灵活消耗）
            │
            └── 核心风险：并发超发 / 掉单 → 原子扣减 + 订单状态机
```

这四层是串联关系，不是并列关系。每次请求都要从上往下走一遍。

## 4. 逐个概念深入

### Session vs Token（JWT）

**Session**：用户登录后，服务器在自己内存/数据库里存一条记录（session_id → 用户信息），然后把 session_id 塞进 Cookie 给客户端。下次请求带着 Cookie，服务器查一下，知道是你。

**Token（JWT）**：服务器不存任何东西。把用户信息加密签名，打包成一个字符串（Token）给客户端。下次请求带着 Token，服务器验签，信息直接从 Token 里读出来。

```
JWT 结构（点号分隔三段）：
header.payload.signature
↑编码方式  ↑用户信息  ↑服务器用私钥签的名
```

**核心 tradeoff**：
- Session 状态在服务器，注销立刻生效，但服务器有记忆负担，水平扩展要共享 Session 存储
- JWT 服务器无状态，扩展轻松，但 Token 签发后无法主动作废（除非加黑名单，又变成有状态了）

**Mindloop 场景**：桌面端本地应用，用 JWT 就够了，不需要多台服务器共享状态，Token 存本地，简单直接。

---

### OAuth 2.0

用户点"用微信登录"，发生了什么？

```
用户 → 你的产品："我要用微信登录"
你的产品 → 微信："有个用户要登录，给他一个授权页面"
微信 → 用户："你确认授权给这个产品吗？"
用户 → 微信："确认"
微信 → 你的产品："给你一个临时 code"
你的产品 → 微信："用这个 code 换用户信息"
微信 → 你的产品："用户叫 xxx，openid 是 yyy"
你的产品 → 用户：颁发自己的 JWT，后续流程照常
```

关键洞察：**你的产品永远不知道用户的微信密码，也不需要知道。你只是拿到了微信背书的"这个人存在"的证明**，然后自己决定给他什么权限。

这就是"委托信任"——把身份证明的重活外包给大平台，用户也省了注册一个新账号。

---

### RBAC 权限模型

RBAC = Role-Based Access Control，基于角色的权限控制。

不给每个用户单独设权限（维护噩梦），而是先定义角色，用户绑角色。

```
角色定义（AI 创作产品）：
    FREE    → 每天 5 次生图，标准画质
    BASIC   → 每月 100 次，高画质，无水印
    PRO     → 无限次，最高画质，优先队列
    ADMIN   → 后台管理，看所有用户数据
```

用户换了套餐，只需要改绑的角色，权限自动跟着变。研发不需要改代码。

**每次 API 请求的完整鉴权链**：
1. 验 Token 签名（你是谁）
2. 查用户角色（你是什么级别）
3. 查这个接口需要什么角色（这件事需要什么资格）
4. 查用户剩余额度（你还有没有次数）
5. 全部通过，放行

### C 端付费模型的选择

三种主流模型，各有代价：

| 模型 | 代表产品 | 用户心理 | 研发复杂度 | 适合场景 |
|------|---------|---------|---------|---------|
| 按次计费 | 早期 Midjourney | 用了才花钱，无压力 | 实时扣减，需防并发 | 低频重度用户 |
| 订阅制 | 可灵会员、ChatGPT Plus | 包月了就使劲用 | 订阅状态管理 | 高频用户，稳定现金流 |
| 积分制 | 很多 AI 工具 | 灵活，可叠加 | 积分账本，多种消耗场景 | 功能复杂，不同操作成本不同 |

**混合方案**（Midjourney 实际做法）：订阅制为主 + 快速通道按次计费。订阅给稳定预期，按次给弹性溢出。这是个产品决策，不只是技术决策。

### 计费实现：原子性是生命线

这是整个付费系统最容易出 bug 的地方。

**问题**：用户余额 1 次，同时点了两次生成，两个请求同时查到"余额=1"，都认为可以扣，都扣了，变成 -1。叫**并发超发**。

**解法**：扣减必须是原子操作。

```sql
-- 错误写法（先查后改，有并发窗口）
SELECT quota FROM users WHERE id=1;  -- 查到 1
UPDATE users SET quota = quota - 1 WHERE id=1;

-- 正确写法（一条语句，加条件，原子）
UPDATE users SET quota = quota - 1 
WHERE id=1 AND quota > 0;
-- 检查影响行数，0 行 = 扣失败，直接返回"余额不足"
```

或者用数据库的行锁/乐观锁，或者用 Redis 的原子命令。

**核心原则：永远不要"先查，再在应用层判断，再改"——这个中间窗口是 bug 的温床。**

### 订单状态机

支付流程里最怕"钱扣了，东西没给"或"东西给了，钱没到账"。

每个订单必须有明确的状态，且状态流转必须记录：

```
PENDING（待支付）
    ↓ 用户支付
PAYING（支付中）
    ↓ 微信/支付宝回调通知
    ├→ PAID（已支付）→ 触发：给用户加额度
    └→ FAILED（支付失败）→ 触发：无操作
        
PAID
    ↓ 用户申请退款
REFUNDING（退款中）
    ↓
REFUNDED（已退款）→ 触发：扣回额度
```

**回调是核心**：你的前端不可信（网络断了前端不知道），支付宝/微信会主动 POST 你的服务器告诉你"这笔钱到了"。这个接口必须**幂等**——同一笔订单的回调可能发多次，只能处理一次。

## 5. 研发在争什么

**争 1：用 Session 还是 JWT？**

JWT 听起来更"现代"，但有个真实代价：无法主动注销。用户改了密码，旧 Token 在过期前还有效。移动端强制下线做不到。如果你的产品对安全要求高（比如企业内部工具），Session 可能更合适。Mindloop 这种本地桌面应用，JWT 绰绰有余。

**争 2：积分制还是订阅制？**

订阅制对公司现金流好，但用户月底没用完会有损失感，容易流失。积分制用户心理压力小，但会囤积不续费。Midjourney 一开始是订阅，后来加了"快速时数"的按次模式——这是数据驱动出来的结论，不是拍脑袋。

**争 3：超发了怎么处理？**

强硬派：超发直接报错，不能多给一次。用户体验差，但账面干净。
宽松派：允许少量超发，事后补扣。用户体验好，但对账复杂。AI 类产品一次生成成本高，大多数选强硬派。

**争 4：免费额度怎么重置？**

按自然日（0 点重置）vs 按注册时间滚动 24 小时。自然日对用户直觉友好，但 0 点瞬间大量请求压垮服务器。滚动 24 小时平滑，但用户会困惑。大多数产品选自然日，用缓存硬扛。
