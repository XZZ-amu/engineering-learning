# 认证与付费：让系统认识你，让用户放心付钱

## 1. 一句话本质

**认证解决"你是谁"，授权解决"你能干嘛"，计费解决"你用了多少"——三件事本质上都是在管理"信任的边界"。**

系统默认不信任任何人。每次交互，你都要重新证明身份，系统才决定给你什么权限、扣你多少额度。所有登录机制、Token、OAuth、计费模型，都是这套信任管理在不同场景下的具体解法。

---

## 2. 为什么必须这样

假设没有认证，会发生什么？

- 任何人都能访问任何数据
- 免费用户调 API 不用付钱
- 一个人可以无限薅羊毛

假设认证有了，但没有"保持登录状态"的机制，会发生什么？

- 每刷新一次页面都要重新输密码
- HTTP 是无状态协议，服务器不记得"上一秒你已经登过了"

这就是为什么系统要在"你第一次证明身份之后"，颁发一张通行证——让后续所有请求都带着这张证，而不是每次都重新验身份。

Session 和 Token（JWT），就是两种不同的"通行证"方案，它们的核心差异在于：**谁来保管通行证的真实状态**。

## 4. 逐个概念深入

### Session vs Token（JWT）：谁保管通行证？

**Session（服务器记）**：你登录后，服务器把"你已登录"存到数据库/内存里，给你一个 Session ID。每次请求带这个 ID，服务器去查一下"这 ID 对应谁"。

**Token/JWT（客户端带）**：你登录后，服务器把"你是谁、什么权限、何时过期"打包签名成一个字符串给你。你每次带着这个字符串，服务器直接解密验签，不用查库。

核心 tradeoff：

| | Session | JWT |
|---|---|---|
| 状态存哪 | 服务器 | 客户端 |
| 登出能否即时生效 | 能（删服务器记录） | 难（Token 没过期前还有效） |
| 横向扩展（多台服务器） | 麻烦（要共享 Session 存储） | 简单（每台服务器都能验签） |
| 适合场景 | 传统 Web、需要强控制 | 现代 API、移动端、微服务 |

Mindloop 这种桌面端应用，用 JWT 天然合适——客户端本地存 Token，每次请求带上，服务器无状态验证，扩展轻松。

**一个常见坑**：JWT 被盗怎么办？服务器没法主动让它失效。解法是设短过期时间（比如 1 小时），配合 Refresh Token 自动续期。

### OAuth 2.0：第三方登录是信任转移

你用微信登录一个 AI 创作产品，这里发生了什么？

```
你 → AI产品："我要用微信登录"
AI产品 → 微信："这个用户想登录，你帮我确认身份"
微信 → 你："确认授权吗？"
你 → 微信："确认"
微信 → AI产品："这是 Access Token，用它可以拿到用户基本信息"
AI产品 → 微信："给我这个用户的 openid 和昵称"
AI产品 → 你："登录成功，你的账号已建立"
```

本质：**你不把密码给 AI 产品，而是让微信替你背书**。AI 产品信任微信，微信确认了你是你，AI 产品就信任你。

为什么不直接用微信账密登录？因为那意味着你把微信密码交给第三方，一旦第三方泄露，你的微信就完了。OAuth 的设计让授权可以细粒度（只给读取头像权限），还能随时撤销。

---

### RBAC：角色决定权限

RBAC（Role-Based Access Control）的逻辑：**权限不直接绑定用户，而是绑定角色，用户绑定角色**。

```
用户 → 角色 → 权限
小王 → 基础会员 → [生成图片, 最多100次/月, 标准画质]
小李 → Pro用户 → [生成图片, 无限次, 4K画质, 优先队列]
```

为什么不直接给每个用户配权限？因为用户千千万，角色就几个。改一个角色的权限，所有该角色的用户自动生效。

### C 端计费模型：三种方案的本质差异

以 AI 创作产品为例：

**按次计费（Pay-per-use）**：生成一张图扣 1 积分。心理门槛高，用户每次都在"值不值"的判断里，容易放弃。Midjourney 早期就是这样，后来切换到订阅制。

**订阅制（含额度）**：每月固定付费，换来固定额度或无限使用。用户付了之后反而更愿意用——已经付过了，不用白不用。收入可预期，便于公司做规划。

**积分制**：买积分，按不同功能消耗不同积分。灵活，但复杂。用户需要理解"生成高清图消耗 3 积分，标准图消耗 1 积分"。可灵用的就是这套。

**设计一套 AI 创作产品的付费方案**：

```
免费用户：每天 5 次（重置时间：每日 0 点）
基础会员：¥39/月，100 次/月（月初重置，不累计）
Pro 用户：¥99/月，无限次 + 优先队列 + 4K 输出
```

背后的定价逻辑：免费层用来获客和转化；基础会员覆盖轻度用户，100 次足够但有限制会带来升级冲动；Pro 无限次针对重度用户，"无限"本身就是卖点。

### 计费实现：最容易翻车的地方

**并发超发问题**：用户同时发了 5 个生成请求，每个请求都查了一下"还有 1 次额度"，然后都扣减了——结果用了 5 次，但只有 1 次额度。

解法：**原子操作**。扣减额度必须是"查询+扣减"一个不可分割的动作，用数据库事务或 Redis 的原子命令（`DECR`）实现。

```
错误方式：查余额(1) → 余额>0 → 扣减(0)  ← 5个并发都通过了第一步
正确方式：原子操作：余额-1，结果<0则回滚拒绝
```

**支付回调与订单状态机**：用户付款后，支付宝/微信会发一个回调通知给你的服务器。这里有几个坑：

1. **回调可能重复**：支付宝没收到你的确认，会重发。你的服务器要做幂等处理（同一个订单 ID，只处理一次）。
2. **订单状态机**：订单有严格的状态流转，不能跳跃。

```
待支付 → 支付中 → 已支付 → 已发货（虚拟商品则为"已发放"）
                  ↓
               支付失败
                  ↓
               已关闭
```

**网络断了钱扣了图没出，怎么办？**

这是经典的"分布式一致性"问题。正确做法：

1. 支付成功 → 订单状态变"已支付" → 触发生成任务
2. 生成任务失败 → 不是直接报错，而是写入重试队列
3. 用户看到"生成中"状态，后台在重试
4. 如果最终失败，退回额度/积分，同时通知用户

关键原则：**不能让"扣了钱没给服务"这个状态静默存在**。要么补发服务，要么退款，系统必须有兜底逻辑。

## 5. 研发在争什么

**Session 还是 JWT？**

传统后端偏爱 Session，因为可以即时踢用户下线（删 Session 就行）。现代 API/移动端偏爱 JWT，因为无状态好扩展。争论焦点通常在：这个产品有没有"强制登出"的需求？（比如发现账号被盗后需要立即踢下线）

**额度按什么粒度重置？**

按自然月（每月 1 号）还是按购买日起算 30 天？自然月对用户直觉友好，但月底剩几天买的人会觉得"亏了"。按 30 天对用户公平，但后台计算复杂。Midjourney 用的是自然月。

**免费额度放多少？**

放多了：用户不升级，服务器成本高。放少了：用户体验不到产品价值，不愿意付费。这是一道没有标准答案的增长题，通常靠数据跑出来，不是靠设计定出来的。

**失败生成要不要扣额度？**

如果不扣，用户可以恶意刷（故意失败来浪费你的算力）。如果扣，用户觉得"我没得到服务为什么扣我"。常见折中：超时/系统错误不扣，但内容违规/参数错误扣（因为算力已经消耗了）。

## 6. 考考你

???+ quiz "Mindloop 决定支持「管理员可以随时踢指定用户下线」的需求，研发应该选哪个方案？"
    - [ ] A. JWT，因为前后端分离，更现代
    - [x] B. Session，因为 JWT 无法即时失效，踢人需要等 Token 自然过期
    - [ ] C. JWT + 短过期时间，每小时过期等于变相踢人
    - [ ] D. OAuth，让第三方平台帮管理用户状态

    ??? success "解析"
        B 是对的。JWT 的核心问题是服务器无状态——一旦签发，在过期前无法主动让它失效。「踢用户下线」意味着需要即时撤销登录状态，Session 才能做到（删服务器端的 Session 记录即可）。
        
        C 看起来折中，但"最多 1 小时后才生效"对于安全场景（账号被盗、违规用户）是不可接受的。
        
        实际工程中也有 JWT 黑名单方案，但那本质上是给 JWT 加了状态存储，接近于 Session 的思路了。

???+ quiz "AI 创作产品，用户同时点了 3 次「生成」按钮（网卡了以为没反应），此时账户余额恰好只剩 1 次。以下哪种实现会出 bug？"
    - [x] A. 每次请求先查余额，余额>0 则扣减并生成
    - [ ] B. 用数据库事务：余额-1，若结果<0 则回滚并返回失败
    - [ ] C. 用 Redis DECR 原子操作，结果<0 则把余额加回来并报错
    - [ ] D. 生成队列排队，逐个处理，第 1 个成功后后两个查余额发现不足则拒绝

    ??? success "解析"
        A 是错的，这是经典的并发竞态条件（Race Condition）。3 个请求几乎同时执行「查询」步骤，都看到余额=1，都认为可以执行，然后都进行扣减，最终余额变成 -2，用户生成了 3 次。
        
        B、C、D 都通过不同方式保证了「查询+扣减」的原子性或串行性，不会超发。
        
        这也是为什么计费系统必须对并发格外小心——多扣用户的钱是 bug，但放过超发对业务同样是损失。
