# P0-1: 异步任务与队列

## 1. 一句话本质

**异步的本质：把"等待"从用户的时间轴，转移到后端的任务队列里。**

用户不应该盯着空白屏幕等 30 秒。把任务扔进队列、立刻拿到一个"取餐号"，然后去干别的——后端算完了再通知你或让你来取，这就是异步的全部逻辑。

---

## 2. 为什么必须这样

假设没有异步，你设计了一个"点击生成图片"的按钮：

- 用户点击 → 前端发请求 → 后端开始跑 AI 模型 → 30 秒后返回图片 URL
- 问题一：HTTP 连接默认会超时（通常 30-60 秒），AI 生成可能要 60 秒，**连接直接断了**，什么都拿不到
- 问题二：同时有 100 个用户点击，服务器要同时跑 100 个 AI 任务，**资源被榨干，全部崩溃**
- 问题三：用户网络抖了一下，连接断开，**任务是否还在跑？完全不知道**

同步模式的假设是"处理时间很短"。数据库查询 5ms，可以等。AI 生成 30s，不能等。**时间不确定 + 资源消耗大 = 必须异步。**

---

## 3. 概念地图

```
用户点击"生成"
      │
      ▼
  【提交任务】────────→ 任务队列（Queue）
      │                    │
      │              Worker 排队消费
      │                    │
  返回 task_id         【执行任务】
      │                    │
      │              更新任务状态（状态机）
      │              pending → processing → completed/failed
      │
  前端拿到 task_id 后，怎么知道完成了？
      │
      ├── 轮询（Polling）：定时来问"好了吗好了吗好了吗"
      │
      └── 推送（WebSocket/SSE）：后端完成了主动推消息来
```

所有概念都从同一个问题长出来：**任务不能同步等，那提交之后怎么管？**

- "怎么排队执行" → 任务队列
- "执行到哪了" → 状态机
- "前端怎么知道完成了" → 轮询 vs 推送
- "失败了怎么办" → 超时与重试

---

## 4. 逐个概念深入

### 任务队列：奶茶店模型

你去奶茶店点单。收银员不会盯着你等做好，而是：
1. 给你一张**取餐号**（`task_id`）
2. 把你的订单扔进**备餐区**（队列）
3. 制作员（Worker）**按顺序**取单子做
4. 做好了叫号，你去取

这就是**生产者-消费者模型**：

```
生产者（用户请求）  →  队列  →  消费者（Worker）
```

关键设计逻辑：**队列解耦了提交速度和处理速度。** 100 个人同时下单没问题，制作员按自己的节奏做，不会被一下子撑死。

### 任务状态机

任务从提交到完成，会经历几个明确的状态：

```
pending → processing → completed
                ↘
                 failed
```

- `pending`：已入队，等待 Worker 取走
- `processing`：Worker 正在处理
- `completed`：成功，结果可取
- `failed`：失败，有错误信息

为什么要有状态机？因为前端需要知道"现在到哪了"，也因为系统重启、Worker 崩溃的时候，要能**从状态恢复**——一个 `processing` 的任务在 Worker 挂掉后应该重新变成 `pending`，而不是永远卡着。

这就是 Replicate API 的 `prediction` 对象设计逻辑：你创建一个 prediction，它的 `status` 字段就是这个状态机。

### 获取结果：轮询 vs 推送

**轮询（Polling）**：前端每隔 2 秒发一次请求，问"好了吗？"

```
前端: GET /tasks/123/status  → { status: "processing" }
前端: GET /tasks/123/status  → { status: "processing" }
前端: GET /tasks/123/status  → { status: "completed", url: "..." }
```

简单，好实现，兼容性好。代价是**浪费请求**——任务 25 秒完成，你可能发了 12 次无效请求。

**推送（WebSocket/SSE）**：后端完成后**主动推消息**给前端，前端被动等通知。

```
后端完成 → 推送 { task_id: 123, status: "completed", url: "..." }
```

高效，实时，但**实现复杂**——需要维持长连接，处理断线重连，服务端也要管理连接状态。

**什么时候用哪个？**

| 场景 | 推荐 |
|------|------|
| 任务 < 30 秒，用户量不大 | 轮询，够用，别过度设计 |
| 任务时间不确定，或需要进度更新 | SSE（单向推送，比 WebSocket 轻） |
| 需要双向通信（比如 AI 流式输出） | WebSocket |
| MVP 阶段 | 轮询，先跑起来 |

> **SSE vs WebSocket 一句话区别**：SSE 是服务端单向广播，WebSocket 是双向对话。生成图片只需要服务端告诉你"完成了"，SSE 够了。

### 超时与重试：指数退避 + 幂等性

任务可能失败。网络抖了，AI 服务挂了，Worker 崩了。**不重试，用户直接看到错误；无限重试，可能把下游打挂。**

**指数退避**：失败后等待时间指数增长，避免雪崩式重试。

```
第 1 次失败 → 等 1s 重试
第 2 次失败 → 等 2s 重试
第 3 次失败 → 等 4s 重试
...
```

**幂等性**：同一个任务重试多次，结果和执行一次一样。为什么重要？因为有时候任务**其实成功了**，只是返回超时——如果任务不幂等，重试会执行两次，可能扣两次钱、生成两张图。

设计上的应对：用 `task_id` 做唯一键，后端收到重复的 `task_id` 就直接返回已有结果，不重新执行。

## 5. 研发在争什么

**争一：轮询频率**

2 秒一次？5 秒一次？太慢用户觉得卡，太快浪费服务器资源。有的团队用自适应轮询——开始 1s 一次，多次没结果就拉长到 5s。没有标准答案，看任务平均耗时和用户量。

**争二：用 WebSocket 还是 SSE**

前者能力强但复杂，后者够用但单向。争论背后是：**你的场景真的需要双向通信吗？** 大多数"任务完成通知"场景其实不需要，用 SSE 即可。但如果已经有 WebSocket 基础设施（比如飞书的消息系统），就直接复用，别单独搞 SSE。

**争三：任务队列用数据库还是专用消息队列**

简单做法：用数据库的一张表当队列，轮询取任务。正经做法：用 Redis Queue、BullMQ、RabbitMQ 这些专用工具。数据库方案够用但高并发下有问题（频繁查询锁竞争）；消息队列方案成熟但多一个依赖。**早期产品用数据库假队列完全合理**，不要一上来就引入 Kafka。

## 6. 完整案例：文生图的提交→等待→拿结果

```javascript
async function generateImage(prompt) {
  // 1. 提交任务，拿到 task_id
  const { taskId } = await fetch('/api/generate', {
    method: 'POST',
    body: JSON.stringify({ prompt })
  }).then(r => r.json())

  // 2. 轮询状态，每 2 秒问一次
  while (true) {
    await sleep(2000)

    const task = await fetch(`/api/tasks/${taskId}`).then(r => r.json())

    if (task.status === 'completed') return task.imageUrl
    if (task.status === 'failed') throw new Error(task.error)
    // status === 'pending' 或 'processing'，继续等
  }
}
```

```
用户           前端              后端 API           任务队列        Worker
 │             │                   │                  │               │
 │──点击生成──→ │                   │                  │               │
 │             │──POST /generate──→│                  │               │
 │             │                   │──入队────────────→│               │
 │             │                   │                  │──分配给 Worker→│
 │             │←──返回 taskId─────│                  │               │──开始生成
 │←─显示进度条─│                   │                  │               │
 │             │──GET /tasks/id───→│                  │               │

```
