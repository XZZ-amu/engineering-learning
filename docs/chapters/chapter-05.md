# 异步任务与队列：用户点了"生成"按钮，然后呢？

## 1. 一句话本质

**后端不可能让所有人"占线等待"，所以把"接单"和"做事"拆开——任务队列就是这个拆分的基础设施，异步的所有设计都是为了管理这段"拆开之后的不确定时间"。**

---

## 2. 为什么必须这样

假设你做了一个文生图功能。用户点"生成"，前端发请求，后端调 Stable Diffusion，等模型跑完，返回图片 URL。

听起来很自然——但问题来了：**模型跑一张图要 15 秒**。

如果同步等待，会发生什么：

- 这 15 秒，这条 HTTP 连接一直挂着
- 100 个用户同时点，后端同时挂 100 条连接，服务器撑不住
- 手机网络抖一下，连接断了，任务白跑，用户重提交，双倍资源浪费
- 用户等 15 秒没有任何反馈，以为卡了，疯狂重点按钮

根本问题是：**HTTP 连接是"短暂的通话"，但生成任务是"需要时间的工作"**。两者生命周期不匹配。

解法只有一个：**把"接单"和"做事"拆开**。接单瞬间完成，返回一个任务 ID；做事在后台慢慢跑；用户拿着任务 ID 来查进度。

这就是异步任务队列的本质动机——**不是技术上能做什么，是被问题逼出来的**。

---

## 3. 概念地图

```
用户点"生成"
      │
      ▼
  [生产者] 前端/API层
  把任务塞进队列，立刻返回 task_id
      │
      ▼
  [任务队列] ← 核心基础设施
  Redis / RabbitMQ / 数据库表
      │
      ▼
  [消费者] Worker进程
  从队列取任务，执行，写结果
      │
      ├─── 任务状态机
      │    pending → processing → completed
      │                        └→ failed
      │
      └─── 结果通知方式
           ├── 轮询 (Polling)：前端主动问
           └── 推送 (WebSocket/SSE)：后端主动说

                    中间的不确定时间
                    ├── 超时策略：等多久算失败
                    └── 重试策略：失败了怎么重来
```

所有概念都从"接单和做事拆开"这一根问题长出来的，不是并列的术语集合。

---

## 4. 逐个概念深入

### 任务队列：奶茶店的叫号机

你在喜茶点了一杯芝芝莓莓。收银员给你一张号：**468**。你不用站在吧台等，去坐着刷手机，叫到号了来取。

这就是生产者-消费者模型：

- **生产者**：收银员，接单、分配号码、把订单放进制作队列
- **队列**：厨房看板，存着所有待制作的订单
- **消费者**：制作饮品的店员，从看板取单、做完、叫号

对应到技术：前端提交任务（生产者）→ 任务队列（Redis/数据库）→ Worker 进程处理（消费者）。

**为什么不用数组直接处理，要专门搞个"队列"？** 因为队列能保证顺序、能持久化（服务重启不丢任务）、能让多个 Worker 安全抢任务而不重复处理。

---

### 任务状态机：任务的"身份证状态"

任务从生到死，有几个阶段：

```
pending      →    processing    →    completed
（已提交，等待）    （Worker 在做）     （成功，有结果）
                       │
                       └──→   failed
                              （失败，有错误信息）
```

每个任务的状态存在数据库里。为什么要显式记录状态，而不是"做完就返回"？

因为**任何时候系统都可能挂掉**。Worker 做到一半崩了，下次重启要知道哪些任务是"processing 但实际没完成的僵尸任务"，要重新捡起来跑。没有状态机，就没有可恢复性。

Replicate API 就是这个模型：你提交一个 prediction，它给你返回 `prediction_id`，状态是 `starting`，然后变 `processing`，最后变 `succeeded` 并附上输出 URL。

---

### 轮询 vs 推送：两种"等通知"的方式

**轮询（Polling）**：前端每隔 2 秒问一次"做好了吗？"

```
前端:  做好了吗? → 没有
前端:  做好了吗? → 没有
前端:  做好了吗? → 做好了，URL = xxx
```

实现简单，HTTP 就够，适合**任务量少、等待时间不确定、对实时性要求不高**的场景。代价是有延迟（最多等一个轮询间隔），而且有无效请求浪费。

**推送（WebSocket / SSE）**：后端做完了主动通知前端。

```
前端建立连接，然后等着
后端:  （15秒后）做好了，URL = xxx
```

实时性好，没有无效请求。代价是需要维持长连接，实现复杂，服务器要记住"谁在等哪个任务"。

**什么时候用哪个？**

- 任务时间短（<30s）、用户可能很快离开页面、实现快：用轮询
- 任务时间长、需要进度条、多人协作实时同步：用 WebSocket/SSE
- Mindloop 这类桌面应用做 AI 功能：SSE 是个好选择，比 WebSocket 轻，原生支持流式输出

---

### 超时与重试：系统如何自愈

任务失败了怎么办？直接重试——但如果后端刚好在崩溃恢复中，你立刻重试，所有失败任务同时涌来，把服务器再打死一次。

**指数退避（Exponential Backoff）**：第 1 次失败等 2 秒重试，第 2 次失败等 4 秒，第 3 次等 8 秒……每次失败等待时间翻倍。让系统有喘息机会。

**幂等性（Idempotency）**：重试的前提是"同一个任务跑两遍，结果一样"。生成图片通常幂等（相同 prompt 跑两遍都能出图），但"扣款"不幂等——所以扣款接口要有去重逻辑，不能因为重试扣两次。

**设计超时上限**：不能无限重试。通常设最大重试次数（3 次），超过后把任务标记为 `failed`，记录错误原因，让用户重新提交或告警人工介入。

## 5. 研发在争什么

**争 1：队列用 Redis 还是数据库表？**

Redis 队列：快，轻量，适合高吞吐。代价是 Redis 重启有丢数据风险（取决于持久化配置），运维多一个组件。

数据库表模拟队列：任务天然有持久化，查询灵活，不用额外组件。代价是高并发下数据库压力大，需要靠轮询数据库而非真正的消息推送。

**小项目/vibe coding 阶段**：用数据库表就够，简单可靠。规模上来再换。

---

**争 2：轮询间隔设多少？**

间隔短：用户体验好，但服务器请求量大；间隔长：省服务器，但用户等得久。

一个折中：**自适应轮询**——刚提交任务时每 1 秒问一次，超过 10 秒后降频到每 3 秒。对用户来说前期感知实时，对服务器来说长任务不浪费。

---

**争 3：失败了显示什么？**

"生成失败，请重试"——用户不知道为什么，可能反复重试浪费资源。

"生成超时（60s），模型可能繁忙，建议稍后重试"——透明，帮用户判断。

研发和产品经常在这里分歧：研发想简单统一处理，产品想差异化错误提示。没有对错，取决于用户场景的重要程度。

## 6. 完整案例：提交生成任务的前端伪代码

```javascript
// 1. 提交任务，立刻拿到 task_id
async function generateImage(prompt) {
  const { taskId } = await api.post('/generate', { prompt })

  // 2. 开始轮询，直到完成或失败
  return pollUntilDone(taskId)
}

async function pollUntilDone(taskId, interval = 2000) {
  while (true) {
    const task = await api.get(`/tasks/${taskId}`)

    if (task.status === 'completed') return task.imageUrl
    if (task.status === 'failed') throw new Error(task.error)

    // 还在 pending/processing，等一会儿再问
    await sleep(interval)
  }
}
```

对应的任务状态时序：

```
t=0s   用户点击生成
t=0s   POST /generate → 返回 { taskId: "abc123", status: "pending" }
t=2s   GET /tasks/abc123 → { status: "processing" }
t=4s   GET /tasks/abc123 → { status: "processing" }
t=15s  GET /tasks/abc123 → { status: "completed", imageUrl: "https://..." }
t=15s  前端显示图片
```

## 7. 考考你

???+ quiz "Mindloop 要做一个"AI 续写笔记"功能，调用大模型，通常需要 8-20 秒返回结果。现在需要决定：用轮询还是 WebSocket？"
    - [x] A. 用 SSE（Server-Sent Events）推送，因为时间较长、用户需要感知进度，且 SSE 比 WebSocket 实现更轻量
    - [ ] B. 用轮询，因为实现最简单
    - [ ] C. 用 WebSocket，因为实时性最好
    - [ ] D. 同步等待，20 秒内 HTTP 连接不会超时，可以直接用

    ??? success "解析"
        B 不是最优——8-20 秒的轮询会产生大量无效请求，用户体验也差（感知延迟高）。C 的 WebSocket 实时性好但实现重，对这个场景过度设计。D 最危险：20 秒内 HTTP 不一定不超时（取决于 nginx/CDN 配置），而且用户无任何进度反馈。A 最合适：SSE 天然支持流式输出（可以边生成边显示文字），比 WebSocket 轻，比轮询实时，是 AI 写作场景的标准选择。

???+ quiz "你的生图任务失败了，代码自动重试。但用户反映"被扣了两次生成次数"。根本原因最可能是什么？"
    - [ ] A. 重试间隔太短，服务器压力大
    - [ ] B. 没有做指数退避
    - [x] C. 扣次数的接口没有做幂等性，重试时触发了两次扣费
    - [ ] D. 任务状态机设计有问题，completed 状态没有正确保存

    ??? success "解析"
        A 和 B 是性能问题，不会造成重复扣费。D 描述的是结果保存问题，也不直接导致重复扣费。C 是根本原因：**重试 + 非幂等接口 = 重复操作**。"扣次数"是有副作用的操作，必须在接口层做去重（通常用 task_id 做唯一键，保证同一个任务无论提交几次只扣一次）。这是异步系统设计里最容易踩的坑。
