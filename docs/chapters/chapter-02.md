# P0-2：数据库基础 — 数据怎么存、怎么查，为什么有的查询慢得要命

> **一句话总结**：数据库是应用的"记忆系统"，理解它能让你判断一个功能"从数据角度看难不难"，跟研发讨论方案时不再只能点头。

---

## 开始之前：你已经懂数据库了，只是不知道

打开你手机里的备忘录 App，你写了一条笔记。关掉 App，重新打开，笔记还在——这就是数据库在工作。

数据库解决的核心问题只有一个：**让数据在程序关掉之后还能活着**。

## 一、数据库是什么：把 Excel 讲明白

你肯定用过 Excel。想象这样一张表：

| id | 标题 | 内容 | 创建时间 |
|----|------|------|----------|
| 1 | 今天的想法 | 要多喝水... | 2024-01-15 |
| 2 | 项目计划 | 第一步先... | 2024-01-16 |

数据库里的**表（Table）**，就是这样的 Excel 工作表。  
横向每一行叫**记录（Record）**，纵向每一列叫**字段（Field/Column）**。

**但数据库比 Excel 强在哪里？**

想象你的 Excel 文件要同时被 1000 个人打开修改，还不能互相覆盖；你要在 100 万行数据里瞬间找到某一行；你要确保某个单元格永远不能为空……Excel 会崩溃，数据库可以做到。

数据库额外解决了：
- **并发**：多人同时读写不打架
- **速度**：海量数据里快速查找
- **约束**：数据格式的强制规范
- **关联**：多张表之间的关系

---

## 二、SQL vs NoSQL：两种不同的"文件柜"

这是一个让很多人困惑的概念，但其实只需要记住一个核心区别。

### SQL 数据库（关系型）：严格的表格文件柜

类比：**医院病历室**。每个病人都有统一格式的病历本：姓名、年龄、过敏史……字段固定，格式统一，不能随便加字段。

代表产品：PostgreSQL、MySQL、SQLite（Mindloop 用的就是 SQLite）

**特点：**
- 数据结构提前定好（叫 Schema），不能随意改变
- 表和表之间有严格的关联关系
- 用 SQL 语言查询（所以叫 SQL 数据库）
- 适合"结构清晰、关系复杂"的数据

**适合场景**：订单系统、用户系统、财务数据——任何"字段固定、关系明确"的业务

---

### NoSQL 数据库：灵活的抽屉柜

类比：**设计师的素材抽屉**。每个抽屉随便放，这个放了一张图片、几张草图，那个放了一堆便签、一本书……格式完全不统一，但找起来靠的是你自己的分类逻辑。

代表产品：MongoDB、Redis、Firestore

**特点：**
- 数据结构灵活，每条记录可以有不同的字段
- 通常存储 JSON 格式的文档
- 扩展容量更容易（水平扩展）
- 适合"结构多变、需要极高速度"的数据

**适合场景**：用户行为日志、商品属性（每类商品属性不同）、实时消息

---

### 怎么选？

```
字段固定、关系复杂 → SQL
字段多变、结构灵活 → NoSQL  
需要极快的缓存    → Redis（NoSQL 的一种）
```

**Mindloop 的选择**：SQLite（SQL 的一种）。因为笔记数据结构清晰（标题、内容、时间），而且 SQLite 是文件型数据库，不需要服务器，直接存在用户本地，特别适合桌面端应用。

## 三、表结构设计：Mindloop 的数据长什么样

这是重头戏。一个功能好不好做，60% 取决于表结构设计得好不好。

### 字段类型：数据的"数据类型"

每个字段都要声明它存什么类型的数据，常见的有：

| 类型 | 存什么 | 举例 |
|------|--------|------|
| `TEXT` / `VARCHAR` | 文字 | 笔记标题、内容 |
| `INTEGER` | 整数 | 用户 ID、点赞数 |
| `REAL` / `FLOAT` | 小数 | 评分 4.5 |
| `BOOLEAN` | 真/假 | 是否已删除 |
| `DATETIME` | 时间 | 创建时间 |

为什么要区分类型？因为"100"这个文字和 100 这个数字是不一样的——文字排序是 1、10、100、2，数字排序才是 1、2、10、100。类型错了，查询结果会出乎意料。

---

### 主键：每条记录的"身份证号"

每张表都需要一个**主键（Primary Key）**，用来唯一标识每一行记录。

类比：你有两个朋友都叫"张伟"，但他们身份证号不同——数据库就靠这个区分。

通常主键叫 `id`，是一个自动递增的数字（1, 2, 3...）或者 UUID（一串随机字符串如 `a3f5-b2c1-...`）。

```
notes 表
---------
id (主键，自动递增)
title
content
created_at
```

**为什么不用标题做主键？** 因为两条笔记可能标题一样，而且用户可能改标题——主键一旦设定就不应该变。

---

### 外键和关联关系：表和表之间怎么连

Mindloop 有"笔记"和"标签"，一条笔记可以有多个标签，一个标签可以属于多条笔记。这怎么存？

**错误做法（存在同一个字段里）：**
```
notes 表
id | title    | tags
1  | 今天的想法 | "读书,生活,感悟"   ← 把标签塞在一个格子里
```
这样存的问题：想查"所有带'读书'标签的笔记"时，数据库要把每一行的 tags 字段拆开来搜，慢且复杂。

**正确做法（三张表）：**

```
notes 表（笔记）
id | title    | content

tags 表（标签）
id | name

note_tags 表（关联表，记录谁和谁有关系）
note_id | tag_id
1       | 2       ← 笔记1 关联了 标签2
1       | 5       ← 笔记1 还关联了 标签5
3       | 2       ← 笔记3 也关联了 标签2
```

这里的 `note_id` 和 `tag_id` 就是**外键（Foreign Key）**——它们指向另一张表的主键，建立两张表之间的关联。

这种"多对多"关系需要一张**关联表**来桥接，是数据库设计的经典模式。

**三种关联关系总结：**
- **一对一**：一个用户对应一份用户详情（1:1）
- **一对多**：一个用户可以写多条笔记（1:N）—— `notes` 表里加一个 `user_id` 字段就够了
- **多对多**：一条笔记可以有多个标签，一个标签可以属于多条笔记（M:N）—— 需要关联表

## 四、基本查询：CRUD 是研发嘴里的"增删改查"

你跟研发开会，他说"这个接口做个 CRUD 就行"——这不是骂人，是四个操作的缩写：

| 缩写 | 全称 | 操作 | SQL 关键字 |
|------|------|------|------------|
| C | Create | 新建数据 | `INSERT` |
| R | Read | 查询数据 | `SELECT` |
| U | Update | 修改数据 | `UPDATE` |
| D | Delete | 删除数据 | `DELETE` |

用 Mindloop 举例：

```sql
-- 新建一条笔记（Create）
INSERT INTO notes (title, content) VALUES ('今天的想法', '要多喝水');

-- 查询所有笔记（Read）
SELECT * FROM notes;

-- 查询带"读书"标签的笔记（Read，带条件）
SELECT notes.title 
FROM notes
JOIN note_tags ON notes.id = note_tags.note_id
JOIN tags ON note_tags.tag_id = tags.id
WHERE tags.name = '读书';

-- 修改一条笔记（Update）
UPDATE notes SET title = '新标题' WHERE id = 1;

-- 删除一条笔记（Delete）
DELETE FROM notes WHERE id = 1;
```

你不需要会写这些，但看到这些关键词能知道在干嘛，这就够了。

**关于 `JOIN`**：当查询涉及多张表时，就需要 `JOIN`（连接）。JOIN 的本质是"把两张表按某个共同字段拼在一起"。JOIN 越多，查询通常越慢——这是一个重要直觉。

## 五、索引：为什么同样是查数据，有的快有的慢

### 类比：书的目录 vs 逐页翻

你手里有一本 500 页的菜谱，要找"红烧肉"的做法：
- **没有目录**：从第 1 页开始一页一页翻，翻到第 347 页才找到 → 慢
- **有目录**：翻到目录，"红烧肉 → 347 页"，直接翻过去 → 快

数据库索引就是这本目录。

**没有索引时**，数据库查找一条记录要从第一行扫到最后一行（叫**全表扫描**），100 万条数据就扫 100 万次。

**有索引时**，数据库用一种叫 B-Tree 的数据结构（你不需要懂细节，只需要知道它像一棵平衡的树）快速定位，通常几十毫秒内搞定。

### 什么字段应该加索引？

**经常用来搜索、过滤、排序的字段。**

Mindloop 的例子：
- `notes.created_at` —— 用户经常按时间排序笔记，加索引
- `note_tags.note_id` 和 `note_tags.tag_id` —— JOIN 查询必须经过这两个字段，加索引
- `notes.content` —— 全文搜索内容... 这个比较特殊，普通索引没用，需要全文搜索索引（FTS）

### 索引不是越多越好

索引也有代价：
- **占存储空间**（目录本身也要页数）
- **写操作变慢**（每次写数据，索引也要同步更新）

所以索引是一种**空间换时间**的权衡。

**一个实用判断标准**：如果一个查询"比想象中慢很多"，第一反应是看看查询条件用的字段有没有索引。这是研发排查性能问题最常见的第一步。

## 六、数据库迁移（Migration）：表结构怎么安全地改

### 为什么不能直接改表结构

产品上线后，数据库里已经有真实用户的数据了。这时候要加一个新字段——比如 Mindloop 要给笔记加"置顶"功能，需要加一个 `is_pinned` 字段。

如果直接在数据库里手动修改，有几个问题：
1. 代码还没更新，新代码需要 `is_pinned` 字段，但旧代码不知道这个字段，可能出错
2. 多个开发环境（开发机、测试服务器、生产服务器）要同步改，容易漏掉
3. 没有记录，下次出问题不知道改过什么

### Migration 是什么

Migration 是一个**版本化的数据库变更脚本**，就像 Git 记录代码变更一样，Migration 记录数据库结构的变更历史。

类比：**装修施工日志**。不是直接拆墙，而是先写"施工单 #0023：在卧室北墙开一个门洞"，所有工地按编号顺序执行，可追溯、可回滚。

每个 Migration 文件通常包含两个方向：
- `up`：执行这个变更（加字段、加表...）
- `down`：撤销这个变更（回滚用）

```
# 文件名: 20240115_add_is_pinned_to_notes.sql

-- up: 加字段
ALTER TABLE notes ADD COLUMN is_pinned BOOLEAN DEFAULT FALSE;

-- down: 撤销
ALTER TABLE notes DROP COLUMN is_pinned;
```

所有 Migration 文件按时间戳排列，每次部署时按顺序执行还没执行过的文件——这样三台服务器的数据库结构始终保持一致。

**设计师的直觉**：当你提出"给笔记加一个优先级字段"这类需求时，研发需要写一个 Migration——这不是 10 分钟的事，但也不是什么大工程。如果对方说"数据库改动需要安排一个发布窗口"，
