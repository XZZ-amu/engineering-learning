# 数据库基础：数据怎么存、怎么查

## 1. 一句话本质

**数据库在解决的根本问题：让数据能被可靠地存下来、精确地找出来，同时在大量并发操作下不出错。**

存、找、不出错——这三件事看起来简单，但每一件在规模变大之后都会失控。数据库的所有设计，都是在这三个压力下被逼出来的。

---

## 2. 为什么必须这样（不这样会出什么事）

假设 Mindloop 用 JSON 文件存笔记，每个用户一个文件。一开始跑得很好。

然后出现了这些情况：

- 用户 A 和 B 同时在两个标签页修改同一篇笔记，谁的存档算数？
- 用户有 10 万篇笔记，你想找出所有带"产品设计"标签的笔记——要把整个 JSON 读进内存遍历一遍
- 你想查"今天新建的笔记里，被收藏超过 3 次的"——JSON 根本没法做这种交叉查询
- 服务器崩溃，正在写入一半的 JSON 文件损坏了

这四个问题对应数据库的四个核心能力：**并发控制、索引查询、关联查询、事务可靠性**。数据库不是规范，是被这些真实问题逼出来的解法。

---

## 3. 概念地图

```
根本问题：数据要可靠存、精确找、并发不出错
        │
        ├── 怎么组织数据？
        │       ├── SQL（关系型）── 表 + 行 + 列，结构固定
        │       └── NoSQL ────── 文档/键值/图，结构灵活
        │
        ├── 怎么描述结构？（表结构设计）
        │       ├── 字段 + 类型 ── 每列存什么、存什么格式
        │       ├── 主键 ──────── 每行的唯一身份证
        │       └── 外键 ──────── 表和表之间的关联线
        │
        ├── 怎么找数据？（查询）
        │       └── CRUD ──────── 增删改查，所有操作的原子集合
        │
        ├── 怎么找得快？（索引）
        │       └── 用空间换时间，提前建好"目录"
        │
        └── 结构变了怎么办？（Migration）
                └── 让表结构的变化像 Git commit 一样可追溯
```

所有概念都从同一个根长出来，不是并列的知识点，是同一棵树的不同分支。

---

## 4. 逐个概念深入

### SQL vs NoSQL：不是新旧之争，是场景之争

**SQL（关系型数据库，如 PostgreSQL、MySQL）**：把数据存在有固定列的表里。每一行必须符合表定义的结构。像 Excel，但有严格的类型约束、有跨表关联、有事务保护。

**NoSQL（如 MongoDB、Redis、Firebase）**：数据存成文档（JSON-like）、键值对或图。每条记录的结构可以不一样。

真正的区别不是"哪个更先进"，而是：

| | SQL | NoSQL |
|---|---|---|
| 数据关系复杂 | ✅ 外键天然支持 | ❌ 手动维护很痛 |
| 结构经常变化 | ❌ 改表很麻烦 | ✅ 直接加字段 |
| 需要跨表复杂查询 | ✅ JOIN 很强 | ❌ 通常很弱 |
| 数据量极大、读多写少 | 看情况 | ✅ 容易横向扩展 |

Mindloop 的笔记应该用什么？笔记和标签、用户、文件夹之间有大量关联关系，需要"找出某用户所有带某标签的笔记"这类跨维度查询——SQL 更适合。如果是存用户的临时操作缓存（比如最近打开的文件列表），Redis 这类 NoSQL 反而更合适。

**研发讨论语境**：当有人说"这个数据放 Postgres 还是 Mongo"，背后在问的是"这块数据的关联复杂度高不高、结构稳不稳定"。

### 表结构设计：字段、主键、外键

把 Mindloop 的笔记表想象成 Excel 的一张 Sheet：

```
notes 表
┌────┬──────────────┬──────────┬─────────────┬─────────┐
│ id │ title        │ content  │ created_at  │ user_id │
├────┼──────────────┼──────────┼─────────────┼─────────┤
│  1 │ 产品思考     │ ...      │ 2024-01-01  │   42    │
│  2 │ 竞品分析     │ ...      │ 2024-01-02  │   42    │
└────┴──────────────┴──────────┴─────────────┴─────────┘
```

**字段和类型**：每一列是一个字段，类型决定存什么格式。`id` 是整数，`title` 是字符串，`created_at` 是时间戳。类型不只是格式约束，还影响存储大小和查询速度。

**主键（Primary Key）**：`id` 那一列。每行的唯一身份证，不能重复，不能为空。数据库靠它定位"你说的是哪一行"。类比：身份证号，不是名字。

**外键（Foreign Key）**：`user_id` 那一列。它的值指向 `users` 表的某个 `id`。这就是"关联"。外键的作用是保障引用完整性——如果一个用户被删了，他的笔记怎么处理，数据库会帮你检查，不会让悬空的引用默默留着。

**为什么不把用户名直接存进笔记表？** 因为用户改了名字，你要更新每一条笔记，漏一条就数据不一致。外键让"事实只存一份"，这是关系型数据库的核心原则：**不重复存储同一个事实**。

---

### CRUD：所有操作的原子集合

Create（插入）、Read（查询）、Update（更新）、Delete（删除）。

数据库的所有操作最终都是这四件事的组合。研发说"这个接口是个读操作"，意思是它不会改变数据库里的数据，只是查询。这很重要——**读操作可以大量并发，写操作需要小心同步**。

当研发说"这个功能对数据库压力大"，通常是指：写操作频繁、或查询要扫描大量数据、或涉及多表关联。

---

### 索引：为什么查询有快有慢

Mindloop 有 100 万条笔记，你要找 `user_id = 42` 的所有笔记。没有索引的情况下，数据库要从头到尾扫描 100 万行，对比每一行的 `user_id`。

**索引就是提前建好的目录**。给 `user_id` 建一个索引，数据库就能直接跳到 `user_id=42` 的位置，不用全表扫描。

代价是什么？**空间**（索引本身要占存储）和**写入速度**（每次写入数据，索引也要同步更新）。

所以不是所有字段都要建索引。经验法则：
- 经常出现在"查询条件"里的字段（`WHERE user_id = ?`）→ 建索引
- 经常做排序的字段（`ORDER BY created_at`）→ 建索引
- 很少被查询、但频繁写入的字段 → 不建

**研发说"这个查询很慢，要加索引"**，背后是在说：这个查询目前在全表扫描，加一个索引可以让它从 O(n) 变成 O(log n)。

---

### Migration：表结构怎么安全地改

产品上线之后，你发现笔记需要加一个"优先级"字段。怎么改？

直接改数据库表结构？生产环境有真实用户的数据，改错一步可能数据丢失或服务崩溃。

**Migration 是把表结构的变化写成可执行的脚本，像 Git commit 一样记录和管理**。

```
migration_001: 创建 notes 表
migration_002: 给 notes 加 user_id 字段
migration_003: 给 user_id 加索引
migration_004: 加 priority 字段，默认值为 'normal'
```

这样：开发环境、测试环境、生产环境都能执行同一套 migration，保证结构一致。出了问题可以回滚。新同事拉代码后跑一遍 migration，本地数据库结构和生产一模一样。

Migration 是"数据库结构的版本控制"，和 Git 管理代码变化的逻辑完全一致。

## 5. 研发在争什么

**争一：这块数据用 SQL 还是 NoSQL？**

研发有时候会因此争起来。判断标准回到根问题：这块数据的关联关系复杂吗？结构会频繁变化吗？需要跨多个维度查询吗？三个 yes 指向 SQL，三个 no 倾向 NoSQL，混合情况就看哪个压力更大。没有绝对答案，但有清晰的 tradeoff。

**争二：这个字段要不要建索引？**

索引不是越多越好。有人倾向"能建就建，查询快"，有人说"写入会变慢，索引要维护"。关键看这个字段的读写比：读远多于写，建索引值得；写非常频繁，要谨慎。

**争三：这个关联用外键约束还是在代码层处理？**

严格的外键约束让数据库帮你保证引用完整性，但在某些高并发场景下会成为性能瓶颈。有些团队选择不用数据库外键，改在应用代码里手动检查。两种方案都有生产项目在用，核心 tradeoff 是：你信任数据库层帮你保证数据一致性，还是信任代码层？

**争四：Migration 写法——字段要不要设默认值？**

给已有百万行数据的表加一列，如果新列不允许为空又没有默认值，migration 会失败。研发会争"默认值设什么合理"，本质上是数据模型的设计决策。这个争论出现时，说明这个字段的业务含义还没想清楚。

## 6. 考考你

**Q1：用你自己的话，一句话说清楚数据库在解决什么问题。**

不要背定义。如果你能说出"为什么有了 JSON 文件还需要数据库"，就说明真的理解了。

**Q2：研发说"这个功能要做一个复杂查询，涉及 5 张表的 JOIN，可能有性能问题"——作为设计师你怎么理解这句话？这意味着什么风险，你可以问什么问题？**

提示：JOIN 越多，查询越慢；但是否真的慢，取决于索引怎么设计。你能问的问题是什么？

**Q3：你们在做 Mindloop 的"全局搜索"功能，需要搜索笔记标题和内容。研发说"内容字段没法用普通索引，得用全文索引，或者接一个搜索服务"——他们在争什么？两种方案的代价分别是什么？**

提示：普通索引适合精确匹配，全文搜索是另一个问题。接外部搜索服务意味着多一个系统要维护。

**Q4：产品新需求要给笔记加"提醒时间"字段。研发说"这个 migration 有点麻烦，因为有几百万条历史数据"——他们在担心什么？作为产品，你能提什么降低风险的方案？**

提示：新字段加上去，历史数据的这个字段值是什么？允不允许为空？这个问题的答案由产品逻辑决定，不只是技术问题。
