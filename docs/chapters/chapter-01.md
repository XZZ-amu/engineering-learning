# API 设计：前后端如何说清楚话

## 1. 一句话本质

**API 是前后端之间的合同——它定义了"谁能要什么、怎么要、得到什么"，所有设计决策都在回答：这份合同怎么写，才能在双方独立变化时还能对得上。**

---

## 2. 为什么必须这样

假设没有 API 规范，前端直接读数据库，或者后端每次返回格式都不一样。

会发生什么：

- 后端改了一个字段名，前端炸了，没人知道是谁的锅
- 前端说"你返回 user_name"，后端说"我返回的是 username"，开会半小时
- App 上线了，iOS 用的是旧逻辑，Android 用的是新逻辑，数据不一致

这不是态度问题，是**协作问题**。两个独立运作的系统（前端/后端），要在没有对方的情况下各自开发、测试、迭代，唯一能依赖的就是"合同"。

合同越清晰，双方越能独立行动。合同一旦打补丁，两边都要重新对齐。

RESTful 不是唯一的规范，但它是目前最广泛接受的"写合同的语言"——大家都用它，是因为能少解释。

---

## 3. 概念地图

```
API 合同
│
├── 地址（URL）—— 你在跟谁说话？资源是什么？
│   └── RESTful 约定：资源用名词、层级表示关系
│
├── 动词（Method）—— 你要做什么动作？
│   └── GET / POST / PUT / PATCH / DELETE
│
├── 请求包（Request）—— 你带了什么去？
│   ├── Header：身份证 + 说话方式（认证、格式声明）
│   └── Body：具体内容（新建/修改时才有）
│
├── 响应包（Response）—— 对方给了你什么回来？
│   ├── 状态码：结果一句话定性（成功/失败/在哪）
│   ├── 数据体：具体内容
│   └── 错误信息：失败时说清楚为什么
│
├── 错误码设计 —— 失败有多种失败法
│   ├── HTTP 状态码（系统级）
│   └── 业务错误码（应用级）
│
└── 版本管理 —— 合同改了怎么办
    └── 新合同不影响签了旧合同的人
```

---

## 4. 逐个概念深入

### URL + RESTful：你在跟哪个资源说话

RESTful 的核心一句话：**资源是名词，动作是动词，两个东西分开。**

```
GET  /notes          → 拿所有笔记
GET  /notes/42       → 拿 42 号笔记
POST /notes          → 新建笔记
DELETE /notes/42     → 删 42 号笔记
```

对比非 RESTful：
```
/getNotes
/createNote
/deleteNoteById?id=42
```

后者把"动作"混进了 URL。问题在于，每个人命名方式不同，一个项目里可能出现 `/getUser`、`/fetchProfile`、`/loadUserInfo` 三个接口做的事差不多——没有规律就没有可预测性。

RESTful 的价值不是美观，是**可预测**。研发看到 URL 就知道操作什么资源，不用翻文档。

---

### Method：你要对这个资源做什么

| Method | 语义 | 什么时候用 |
|--------|------|-----------|
| GET | 读 | 查笔记列表、查单篇 |
| POST | 新建 | 创建一篇新笔记 |
| PUT | 整体替换 | 整份笔记全量更新 |
| PATCH | 局部修改 | 只改笔记标题 |
| DELETE | 删除 | 删一篇笔记 |

PUT vs PATCH 是个高频困惑点：

- `PUT /notes/42`：你要把 42 号笔记整个替换，你没传的字段可能被清空
- `PATCH /notes/42`：你只改你传的字段，其他字段不动

Mindloop 里，用户改笔记标题时，用 PATCH 比 PUT 更合理——不然前端还得带着 body 内容一起传，只为了改个标题。

---

### Request 结构：你带了什么去

一个完整请求有三个部分：

**URL**：说清楚你在操作哪个资源。

**Header**：元信息。最常见的两条：
- `Authorization: Bearer <token>` → 证明你是谁
- `Content-Type: application/json` → 告诉后端你发的是 JSON 格式

Header 不是放业务数据的地方，是"快递单"，描述这个请求的性质。

**Body**：具体内容，只有 POST/PUT/PATCH 才有。GET 和 DELETE 没有 Body，参数通过 URL 传。

---

### Response 结构：你拿回了什么

响应也有三层：

**HTTP 状态码**：结果的"一句话定性"。

| 状态码 | 含义 |
|--------|------|
| 200 | 成功 |
| 201 | 创建成功 |
| 400 | 你发的请求有问题 |
| 401 | 你没登录 |
| 403 | 你没权限 |
| 404 | 资源不存在 |
| 500 | 服务器自己出错了 |

**数据体**：成功时的内容，通常是 JSON。

**错误信息**：失败时为什么失败，靠状态码不够——400 "请求有问题"太模糊了。

---

### 错误码设计：失败有很多种失败法

这是最容易设计糟糕的部分。

**系统错误 = HTTP 状态码**，表示协议层的问题：请求格式错了、没登录、资源不存在。

**业务错误 = 自定义错误码**，表示应用逻辑的问题：

```json
{
  "code": 40001,
  "message": "笔记标题不能超过 200 字",
  "field": "title"
}
```

为什么要分开？

因为 HTTP 状态码数量有限，而业务错误无限多。"密码错误"、"账号被封"、"余额不足"都可以是 400，但前端需要分别处理——弹不同提示、跳不同页面。

设计原则：**状态码说"发生了什么类型的错误"，业务码说"具体哪里错了"，message 说"给用户看什么"。**

Mindloop 场景：用户保存笔记，后端返回 400 + `{ code: 40003, message: "同步冲突，该笔记已在其他设备修改" }`——前端根据 40003 触发"冲突合并"逻辑，而不是简单报错。

---

### 分页、筛选、排序：查列表的约定

列表接口永远需要解决三件事：太多数据怎么切、怎么过滤、怎么排序。

通常通过 URL 查询参数传：

```
GET /notes?page=2&limit=20&tag=工作&sort=updated_at&order=desc
```

- `page` + `limit`：第几页，每页多少条
- `tag=工作`：筛选条件
- `sort=updated_at&order=desc`：按更新时间倒序

响应里通常附上总数，方便前端渲染分页组件：

```json
{
  "data": [...],
  "total": 156,
  "page": 2,
  "limit": 20
}
```

这些不是规定，是约定。但团队内保持一致比用哪种方案更重要。

### API 版本管理：合同改了怎么办

用户设备上还装着旧版 App，旧版 App 还在调旧版接口。这时候你能直接改接口吗？

不能。你改了，旧版 App 就炸了。

解法是并行维护：

```
/v1/notes   → 旧合同，继续有效
/v2/notes   → 新合同，新客户端用
```

什么时候需要新版本？**当你的改动是"破坏性变更"时**——改了字段名、删了字段、改了结构。

加字段通常不需要版本，因为旧客户端会忽略它不认识的字段。

版本管理的成本是维护两套逻辑。所以版本不是越多越好，而是**破坏性变更发生时的止损手段**。

## 5. 研发在争什么

**争一：用 HTTP 状态码还是全返回 200 + 业务码**

有一派风格：所有接口都返回 200，错误信息全放 Body 里。
```json
{ "success": false, "code": 40001, "message": "..." }
```

这样 HTTP 层永远"成功"，业务层自己判断。

争议在于：这违背了 HTTP 语义，监控、日志、网关工具都依赖状态码来判断健康度——全返回 200 让这些工具失效。但有些团队觉得这样前端写起来更一致。

没有对错，有代价。如果你们有完善的监控体系，遵守 HTTP 语义更合适。

---

**争二：版本放 URL 里还是放 Header 里**

```
# URL 版本
GET /v2/notes

# Header 版本
GET /notes
Accept: application/vnd.app.v2+json
```

URL 版本直观、好调试、好复制粘贴。Header 版本更"纯粹"（URL 代表资源，版本是表现形式）。

绝大多数团队用 URL 版本，因为实用。Header 版本更符合 REST 哲学，但日常使用摩擦大。

---

**争三：PATCH 还是只用 PUT**

团队刚开始设计 API 时，有时会图简单，所有更新都用 PUT。代价是前端每次都要带完整数据，带宽浪费，也容易误清空字段。

PATCH 更精确，但要求后端做"合并逻辑"，稍复杂。数据量小的场景可以容忍用 PUT，涉及大内容的资源（比如笔记正文）建议用 PATCH。
