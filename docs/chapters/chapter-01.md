# P0-1: API 设计 — 前后端怎么"对话"

> **一句话总结**：API 是前端和后端之间的合同，RESTful 是这份合同的通用写法规范——学懂它，你就能听懂研发在说什么，也能问出让他们刮目相看的问题。

---

## 先问你一个问题

你在用 Mindloop 的时候，点击"保存笔记"，这个动作背后发生了什么？

前端（你看到的界面）需要把内容"交给"后端（负责存数据的服务器）。但它们怎么交？用什么格式？出错了怎么说？——这就是 API 设计要解决的问题。

---

## 一、API 是什么？用餐厅来理解

想象你去一家餐厅：

| 餐厅角色 | 对应 API 角色 |
|--------|-------------|
| 你（顾客） | 前端 / 客户端 |
| 菜单 | API 文档 |
| 服务员 | API 接口 |
| 厨房 | 后端服务器 |
| 食物 | 返回的数据 |

你不需要知道厨房怎么做菜，你只需要**按照菜单点餐**，服务员就会把你的需求传递给厨房，再把菜端回来。

API 就是这个"服务员"——它定义了：
- 你能点什么（有哪些接口）
- 怎么点（用什么格式发请求）
- 会给你端什么上来（返回什么数据）
- 点错了怎么说（错误码）

---

## 二、RESTful 是什么？为什么大家都用它

REST 不是一个技术，是一套**约定俗成的规矩**。就像全世界餐厅都默认"举手示意服务员"——这不是法律规定，但大家都这么做，因为它好用。

RESTful 的核心思想只有一句话：**用"名词"表示资源，用"动词"表示操作。**

### 名词 = 你要操作的东西

```
/notes          → 笔记（集合）
/notes/123      → ID 为 123 的那篇笔记
/users/456/notes → 用户 456 的所有笔记
```

URL 里只写名词，**不要写动词**：

```
❌ 错误写法（非 RESTful）
/getNotes
/createNote
/deleteNote?id=123

✅ 正确写法（RESTful）
/notes          （配合不同 HTTP 方法来区分操作）
```

### 动词 = HTTP Method（请求方法）

这五个方法，对应了你对资源的所有操作意图：

| HTTP Method | 类比 | 含义 |
|------------|------|------|
| GET | 点菜单查菜 | 获取数据，不改变任何东西 |
| POST | 下单 | 创建新资源 |
| PUT | 整份换掉 | 完整更新（全量替换） |
| PATCH | 改一道菜 | 部分更新（只改某些字段） |
| DELETE | 退菜 | 删除资源 |

**Mindloop 真实案例：**

```
GET    /notes          → 获取所有笔记列表
GET    /notes/123      → 获取 ID=123 的笔记
POST   /notes          → 创建一篇新笔记
PATCH  /notes/123      → 修改笔记 123 的某些内容（比如只改标题）
DELETE /notes/123      → 删除笔记 123
```

## 三、一个请求的完整结构

每次前端给后端发请求，就像你填一张点餐单，这张单子有四个部分：

### 1. URL（去哪里）

```
https://api.mindloop.app/v1/notes/123
```

分解来看：
- `https://api.mindloop.app` → 餐厅地址
- `/v1` → 第 1 版菜单（版本号，后面详说）
- `/notes/123` → 要操作的具体资源

### 2. Method（做什么）

就是上面说的 GET / POST / PATCH / DELETE。

### 3. Header（随单附注）

Header 是一些"元信息"，不是主菜，但很重要。常见的有：

```
Content-Type: application/json     → 告诉后端"我发的是 JSON 格式"
Authorization: Bearer eyJhbGci...  → 身份验证 Token（证明你是你）
Accept-Language: zh-CN             → 希望返回中文
```

类比：就像你点餐时额外说"我对花生过敏"、"帮我打包"——这些不是菜品本身，但服务员需要知道。

### 4. Body（要说的主体内容）

GET 请求通常没有 Body（查数据不需要带内容）。  
POST / PATCH 请求需要 Body 来携带你要提交的数据：

```json
// PATCH /notes/123 的 Body
{
  "title": "重新命名的笔记标题",
  "content": "更新后的正文内容..."
}
```

## 四、响应结构——服务员端菜回来

后端返回的数据也有固定结构。一个规范的响应长这样：

### HTTP 状态码（第一眼先看这个）

状态码是一个 3 位数，含义约定俗成：

| 状态码范围 | 含义 | 类比 |
|----------|------|------|
| 2xx | 成功 | 菜上来了 |
| 3xx | 重定向 | 这道菜换地方取 |
| 4xx | 你的问题 | 你点了菜单上没有的菜 |
| 5xx | 服务器的问题 | 厨房着火了 |

最常用的几个：

```
200 OK           → 成功
201 Created      → 创建成功（POST 后常见）
400 Bad Request  → 你发的数据格式有问题
401 Unauthorized → 没登录 / Token 无效
403 Forbidden    → 登录了但没权限
404 Not Found    → 找不到这个资源
500 Internal Server Error → 服务器内部炸了
```

### 响应 Body（实际数据）

成功时的标准结构：

```json
// GET /notes/123 成功返回
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 123,
    "title": "我的第一篇笔记",
    "content": "正文内容...",
    "createdAt": "2024-01-15T10:30:00Z",
    "updatedAt": "2024-01-16T08:00:00Z"
  }
}
```

## 五、错误码设计——出错了怎么说清楚

这是很多产品设计师忽略的细节，但却直接影响用户体验。

### 系统错误 vs 业务错误

HTTP 状态码只是"大方向"，但有时候不够精确。比如同样是 400，可能是：
- 用户名格式不对
- 密码太短
- 邮箱已被注册

后端需要用**业务错误码**来区分：

```json
// 注册失败的返回示例
{
  "code": 10023,        // 业务错误码（公司自定义）
  "message": "该邮箱已被注册",
  "data": null
}
```

**好的错误码设计长这样：**

```
// 分段管理，一看就知道是哪个模块出了什么问题
10000-19999 → 用户模块
  10001 → 用户不存在
  10002 → 密码错误
  10023 → 邮箱已注册

20000-29999 → 笔记模块
  20001 → 笔记不存在
  20002 → 无权限访问该笔记
  20003 → 笔记内容超出长度限制
```

**作为产品设计师，你需要关心的是：**

每个错误码对应什么用户提示语？这是前端要展示给用户看的！研发往往只关心错误码，但你要推动大家定义清楚每个错误对应的产品文案。

## 六、API 版本管理——为什么要有"v1"

想象 Mindloop 上线了 v1 版本，已经有 10 万用户在用。现在你要重新设计笔记的数据结构，加了几个新字段、删了旧字段——但如果直接改，老用户的客户端就会崩掉。

**版本管理就是为了让新旧版本共存，互不影响。**

类比：餐厅推出了新菜单（v2），但老菜单（v1）还在，老顾客可以继续点。

### 常见的三种版本管理方式

**方式一：URL 路径（最常见，最推荐）**
```
https://api.mindloop.app/v1/notes
https://api.mindloop.app/v2/notes
```
优点：直观，一眼看出版本。

**方式二：Header 里带版本**
```
GET /notes
API-Version: 2
```
优点：URL 干净，缺点：不直观。

**方式三：域名区分**
```
https://api-v1.mindloop.app/notes
https://api-v2.mindloop.app/notes
```
缺点：运维成本高，一般不用。

**实际工作中你会遇到的问题：**  
研发说"这个接口要 breaking change，我们要升版本"——这意味着改动会破坏现有使用方式，需要发新版本。你作为 PM/设计师要判断：老版本要维护多久？什么时候下线？这涉及用户迁移计划。

## 七、分页、筛选、排序的常见约定

当你要获取笔记列表，不可能一次返回几千条——需要分页和筛选。这类参数通常放在 URL 的 **Query String**（问号后面）：

### 分页

```
GET /notes?page=2&pageSize=20
```

或者用另一种风格（offset/limit）：

```
GET /notes?offset=20&limit=20
```

返回的数据会带上分页信息：

```json
{
  "code": 0,
  "data": {
    "list": [...],
    "total": 158,      // 总条数
    "page": 2,
    "pageSize": 20
  }
}
```

### 筛选

```
GET /notes?tag=工作&status=published
```

### 排序

```
GET /notes?sortBy=updatedAt&order=desc   // 按更新时间降序
GET /notes?sortBy=title&order=asc        // 按标题升序
```

**Mindloop 完整例子：**  
用户想看"标签为'工作'、按更新时间从新到旧、第 2 页"的笔记：

```
GET /v1/notes?tag=工作&sortBy=updatedAt&order=desc&page=2&pageSize=20
```

## 快速回顾

| 概念 | 一句话记忆 |
|-----|----------|
| RESTful | 名词做 URL，动词用 Method |
| HTTP Method | GET查 POST创建 PATCH改 DELETE删 |
| 状态码 | 2成功 4你的锅 5服务器的锅 |
| 业务错误码 | 比状态码更精准，直接决定用户看到什么提示 |
| 版本管理 | URL 里加 /v1 /v2，让新旧版本共存 |
| 分页排序 | 放在 URL 问号后面的 Query String |

**题目一（选择题）**

产品需求：用户可以"收藏"一篇笔记。研发同学提出了以下两种 API 设计方案，你认为哪个更符合 RESTful 规范？

```
方案 A：POST /notes/123/favorite
方案 B：GET /favoriteNote?id=123
```

A. 方案 A  
B. 方案 B  
C. 两个都对  
D. 两个都不对

<details>
<summary>点击查看答案</summary>

**答案：A**

方案 A 符合 RESTful：用名词（`favorite`作为资源）+ 用 POST 表示"创建收藏"这个操作。  
方案 B 错在两点：①URL 里有动词 `favoriteNote`；②用 GET 做了创建操作（GET 不应该修改数据）。

</details>

**题目二（简答题）**

你在跟研发 review Mindloop 的"删除笔记"接口，研发给出了这样的设计：

```
POST /deleteNote
Body: { "noteId": 123 }
返回: { "result": "ok" }
```

请指出这个设计有哪些不符合规范的地方，并写出你认为正确的版本。

<details>
<summary>点击查看答案</summary>

**至少有 3 个问题：**

1. **Method 用错了**：删除操作应该用 `DELETE`，不是 `POST`
2. **URL 有动词**：`/deleteNote` 不符合 RESTful，应该是名词
3. **返回结构不规范**：`{ "result": "ok" }` 没有标准的 `code` / `message` 结构

**正确版本：**
```
DELETE /v1/notes/123
返回: 
{
  "code": 0,
  "message": "删除成功",
  "data": null
}
```

</details>
