# P2-2：性能与体验优化

## 1. 一句话本质

**"快"不是一个技术指标，是一个管理"等待"的设计系统——真正的目标不是消灭等待，而是让用户感知不到等待，或者觉得等得值。**

---

## 2. 为什么必须这样

想象 Mindloop 的画廊页加载了 800 张 AI 生成的封面图。

如果什么都不做：浏览器要同时发出 800 个图片请求，内存里同时维护 800 个 DOM 节点，GPU 要渲染一个几万像素高的画布，用户滑动时每一帧都要重新计算布局——结果是白屏 5 秒、滑动掉帧、手机发热、甚至标签页崩溃。

但用户的真实需求是什么？他只想**现在看到屏幕里的这 12 张**。

所以所有优化手段都在回答同一个问题：**怎么只做用户现在需要的那部分工作，同时让他感觉什么都准备好了？**

这就引出了两条并行的思路：
- **少做**：只渲染/加载/计算当前需要的
- **提前做**：预测用户下一步，提前偷偷准备好

---

## 3. 概念地图

```
根问题：用户感知到"慢"和"卡"
│
├── 实际上慢（真实耗时长）
│   ├── 前端：渲染太多东西
│   │   ├── 虚拟列表 → 只渲染视口内的 DOM
│   │   └── 图片懒加载 → 只加载视口内的图
│   │
│   └── 后端：接口响应慢
│       ├── N+1 查询 → 批量处理
│       └── Redis 缓存 → 热数据不查数据库
│
└── 感知上慢（实际不慢，但用户等得难受）
    ├── 等待期间没有反馈 → 骨架屏
    ├── 等待高清图 → 渐进式加载（先模糊后清晰）
    ├── 等待服务器确认 → 乐观更新
    └── 没有预见性 → 预加载
            │
            └── 缓存策略（浏览器缓存 / Service Worker）
                → 把"已经做过的工作"复用，下次不用重做
```

两条线不是独立的。真实产品里要同时优化。但**诊断问题时要先分清：是真的慢，还是感知上慢**——解法完全不同。

---

## 4. 逐个概念深入

### 虚拟列表：DOM 不是免费的

浏览器每个 DOM 节点都有内存开销，每次滑动都要重新计算哪些节点可见、重新布局。800 个节点和 12 个节点，计算量差 60 倍。

虚拟列表的做法：DOM 里永远只有视口内的 N 个节点，滑动时把顶部消失的节点"搬到"底部复用，只更新内容。用户感觉在滑一个无限长的列表，实际上 DOM 只有那几十个节点在反复横跳。

**设计含义**：如果你设计了一个"无限滚动"画廊，研发不会傻乎乎地渲染所有卡片——但这意味着卡片高度最好固定，或者研发能预先知道高度。如果每张卡片高度都不一样（比如瀑布流），虚拟列表实现难度会暴增。

### 图片懒加载：请求也不是免费的

不在视口内的图，先用占位符替代，进入视口前 100px 再发请求加载。节省的不只是带宽，还有服务器压力和首屏时间。

**懒加载 vs 预加载**：懒加载是"进视口前才加"，预加载是"预测你要看，提前加"。两者组合使用：屏幕内懒加载，同时悄悄预加载下一屏。

### 骨架屏：把"空白等待"变成"有形等待"

用户最难忍受的不是等，是对"还要等多久"没有预期。白屏让人以为页面坏了；骨架屏（灰色块占位）让人知道"内容正在来的路上"。

**骨架屏 vs Loading 转圈**：转圈适合操作反馈（保存中…），骨架屏适合内容加载。骨架屏的形状应该接近真实内容的布局——如果骨架屏是三行文字，但实际加载出来是图片网格，反而增加视觉跳动感（layout shift），体验更差。

### 渐进式加载：先模糊后清晰

AI 生成图常见做法：先传一张超低分辨率的模糊版（几 KB），立刻显示，再异步加载高清版替换。用户感觉"图片一下子就出来了"，只是慢慢变清晰。

这是在**管理感知**，不是在优化真实速度。高清图还是要花同样时间加载，但用户的等待焦虑大幅降低。

### 乐观更新：假设成功

用户点赞，如果等服务器返回再改 UI，有 200-500ms 的延迟感。乐观更新：**先把 UI 改了，假设请求会成功**，如果失败再回滚并提示。

适用条件：失败率极低的操作（点赞、收藏、已读）。不适用于：支付、提交表单——因为失败需要用户立刻感知并处理。

**设计要考虑的**：乐观更新失败时怎么回滚？回滚动画够不够自然？用户会不会在回滚瞬间困惑？

### N+1 查询：后端最常见的性能坑

查 10 张图的作者信息：错误做法是先查 10 张图（1 次），再对每张图分别查作者（10 次）= 11 次查询。正确做法：批量查，1+1 次搞定。

N+1 是后端问题，但**设计导致 N+1**：如果设计一个展示"图片+作者头像+作者粉丝数+作者最新作品"的卡片，而这些数据来自 4 个不同来源，研发没处理好就会变成 N×4 次查询。复杂卡片设计时可以主动问研发：这些字段能一个接口返回吗？

### Redis 缓存：热数据不查数据库

数据库查询慢（磁盘 I/O），Redis 是内存，快 100 倍。把频繁访问的数据存 Redis，下次直接读缓存。

**适合缓存的**：热门模板列表、用户设置、不常变的配置。**不适合缓存的**：实时库存、消息未读数——需要实时准确。

缓存有"失效"问题：数据更新了但缓存还是旧的，用户看到旧数据。这是研发要处理的，但作为设计师你需要知道：**某些功能数据会有几秒到几分钟的延迟**，别设计成"立刻反映"的交互。

### 队列优先级：不是所有任务平等

AI 生图是计算密集型任务，服务器同时只能处理有限个。如果 100 个用户同时提交，后面的要等。怎么排队？

- **会员优先**：付费用户插队，商业逻辑
- **小图优先**：100×100 的缩略图比 2000×2000 的大图快很多，优先出小图，用户先看到预览
- **重试优先**：失败重试的任务比新任务优先，减少用户挫败感

**设计含义**：等待页面的文案和进度条要诚实——"预计 30 秒"但实际等 3 分钟，比一开始说"预计 2 分钟"体验差得多。能否把队列位置透明化？

### 浏览器缓存 & Service Worker：已做的工作不重做

浏览器缓存：图片、JS 文件加载一次后存本地，下次访问直接用缓存，不重新请求。

Service Worker 更强：即使断网，也能用缓存的内容展示页面（离线访问）。Mindloop 如果要做桌面端 PWA，Service Worker 可以让用户断网后还能浏览已加载的内容。

## 5. 研发在争什么

**争一：骨架屏要不要做得跟真实布局一模一样？**

精确骨架屏：用户体验好，但每次改版都要同步更新骨架屏，维护成本高。通用骨架屏（几个灰块）：维护成本低，但内容加载出来时视觉跳动。没有标准答案，取决于产品迭代速度。

**争二：乐观更新的回滚逻辑值不值得做？**

乐观更新失败率可能只有 0.1%，但回滚逻辑要写额外代码，还要设计失败 Toast。有些团队认为不值得，直接等服务器返回。这是工程成本和体验质量的权衡。

**争三：缓存时间设多长？**

缓存太短：反复查数据库，失去意义。缓存太长：用户看到过期数据。热门内容 5 分钟缓存？用户配置 1 小时缓存？没有通用答案，要看数据的"新鲜度要求"。

**争四：预加载激进程度？**

预加载下一页能提升体验，但用户可能根本没翻到下一页——白白消耗了流量和服务器资源。对流量敏感的用户（手机流量）可能反感。激进预加载 vs 保守预加载，是体验和成本的 tradeoff。

## 6. 考考你

???+ quiz "Mindloop 画廊页有 800 张图，产品经理说"滑动很卡"。研发排查后发现 DOM 里有 800 个节点，每个节点都包含一张图片。最优先应该做哪个优化？"
    - [ ] A. 把图片压缩成更小的文件，减少加载时间
    - [ ] B. 加骨架屏，让用户在加载时有视觉反馈
    - [x] C. 引入虚拟列表，只渲染视口内的节点
    - [ ] D. 开启 Service Worker 缓存，第二次访问更快

    ??? success "解析"
        题目症状是"滑动卡顿"，根本原因是 DOM 节点过多导致渲染和布局计算量爆炸。虚拟列表直接解决这个问题——把 DOM 节点从 800 个降到视口内的约 20 个，滑动立刻变流畅。

        A（压缩图片）优化的是加载速度，不解决渲染卡顿。B（骨架屏）优化的是"感知等待"，不解决实际卡顿。D（Service Worker）优化的是二次访问速度，对 DOM 渲染没有帮助。

???+ quiz "用户在 Mindloop 里点击"收藏"一张图，200ms 后收藏图标才变色（等服务器返回后更新）。研发提议改成乐观更新。以下哪个场景最不适合用乐观更新？"
    - [ ] A. 点赞某张图
    - [ ] B. 把图片添加到收藏夹
    - [x] C. 用积分兑换会员月卡
    - [ ] D. 将图片标记为"已读"

    ??? success "解析"
        乐观更新的前提是：失败了可以无痛回滚，用户不会因为"以为成功了"而造成实质损失。

        点赞、收藏、已读标记：失败概率低，回滚只是 UI 变回去，用户顶多轻微困惑，无实质损失。

        积分兑换会员：这是资产转移——如果系统先告诉用户"兑换成功，会员已到账"，但服务器实际扣款或开通失败，回滚时用户会产生强烈挫败感和不信任感，甚至以为被骗。这类涉及资产、支付、不可逆操作的场景，必须等服务器确认再更新 UI。

???+ quiz "设计师设计了一个"AI 生图"等待页，要求显示精确进度条（从 0% 到 100%）。研发说"做不到精确进度，只能显示预计时间"。最可能的原因是什么？"
    - [ ] A. 后端没有记录任务开始时间
    - [ ] B. AI 生图任务在队列中，排队位置随时变化，且单次生图耗时不可预测
    - [x] B. AI 生图任务在队列中，排队位置随时变化，且单次生图耗时不可预测
    - [ ] C. 前端无法接收服务器推送的进度更新

    ??? success "解析"
        这题考的是队列优先级和任务不确定性的理解。AI 生图有两个不确定因素：①队列里的排队位置会因为新增任务、会员插队、任务失败重试等实时变化
