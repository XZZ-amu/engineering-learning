# P2-2：性能与体验优化

## 1. 一句话本质

**性能优化的本质是：用户感知到的速度 ≠ 实际速度，所有优化手段都在操控这两者之间的差距——要么真的更快，要么让用户觉得更快。**

从这句话可以推导出后面所有概念：懒加载是"只处理用户能看到的"，骨架屏是"让等待有内容填充"，乐观更新是"先给用户结果再同步"，缓存是"把上次的答案提前备好"，队列优先级是"插队让用户先感知到响应"。所有手段，要么减少实际耗时，要么压缩感知耗时。

---

## 2. 为什么必须这样

想象 Mindloop 的灵感画廊页，里面有 800 张 AI 生成的图。

**如果没有任何优化：**
- 页面打开，浏览器同时请求 800 张图，网络带宽打满，每张图都在排队等
- 每张图占 1-5MB，总计可能 2GB 的资源
- 用户的 DOM 里有 800 个 `<img>` 节点，滑动时浏览器要重新计算所有节点的布局
- 用户等 10 秒，看到页面，滑动卡成 PPT

**结果不是"有点慢"，是产品直接不可用。**

更微妙的问题：用户点了"点赞"，请求发到服务器要 300ms 才返回，这 300ms 里点赞按钮没有任何反应。用户以为没点到，再点一次——最终点了两下变成取消。

这些问题不是设计风格问题，是工程必须解决的生存问题。

---

## 3. 概念地图

```
用户感知速度 = 真实速度 + 感知操控
        │                    │
        │                    └── 骨架屏（等待期有内容）
        │                    └── 乐观更新（操作即时反馈）
        │                    └── 预加载（下一步已备好）
        │
        └── 减少实际耗时
                │
                ├── 前端：少渲染
                │       └── 懒加载（只渲染视口内）
                │       └── 虚拟列表（只存在视口节点）
                │
                ├── 前端：少请求
                │       └── 浏览器缓存（本地存已有资源）
                │       └── Service Worker（离线也能跑）
                │
                └── 后端：少计算
                        └── Redis 缓存（热门数据不重查）
                        └── 批量处理（N+1 查询问题）
                        └── 队列优先级（关键任务先跑）
```

两条主线：**减少实际耗时**（真的更快） + **感知操控**（让用户觉得快）。大多数优化方案会同时涉及两条线。

---

## 4. 逐个概念深入

### 懒加载 & 虚拟列表：只处理用户能看到的

**懒加载**：图片只在进入视口时才开始下载。用户在页面顶部，第 500 张图的请求根本不发出去。

**虚拟列表**：更激进的版本。不只是延迟加载，而是 DOM 里永远只存在视口附近的 20-30 个节点，滑动时动态替换内容。即使列表有 10000 条，浏览器的计算压力始终是 "30 个节点"。

**区别**：懒加载省的是网络请求，虚拟列表省的是渲染计算。Mindloop 画廊页同时需要两者——图片要懒加载，卡片列表要虚拟化。

研发讨论虚拟列表时常见的坑：卡片高度不固定（AI 图比例各异），虚拟列表实现复杂度会翻倍。这时你作为设计师，统一卡片比例，是在帮研发解决工程问题。

---

### 骨架屏 & 渐进式加载：让等待有内容

等待是不可消除的，但空白感可以消除。

**骨架屏**：在数据加载期间，用灰色占位块模拟页面结构。用户的感知是"页面已经在了，内容还在来的路上"——这比盯着白屏焦虑好得多。

**渐进式加载**：图片先显示低分辨率模糊版本，再替换为高清版。Mindloop 生成的图可以先返回缩略图，高清图继续加载。用户看到内容了，不会感到空白。

**感知速度 vs 实际速度**：这是骨架屏和渐进加载背后的核心逻辑。实际加载时间没变，但用户感知的等待时间缩短了。有研究表明，骨架屏能让用户感知速度提升约 20%，而工程成本很低。这是纯粹的"感知操控"。

---

### 缓存：把上次的答案提前备好

缓存的本质是：同样的问题，第一次回答需要计算，之后把答案存起来直接返回。

**浏览器缓存**：用户第二次打开 Mindloop，CSS、JS 文件直接从本地读取，不重新下载。研发控制缓存时效——改动了代码，就要让旧缓存失效。

**Service Worker**：比浏览器缓存更可控的方案，可以实现离线访问。Mindloop 的历史作品页，即使断网也能看本地缓存的内容。

**Redis 缓存**（后端）：热门模板、常用参数存在内存数据库里。用户调用"吉卜力风格"生成参数，第一次从数据库查，之后直接从 Redis 读，响应时间从 50ms 降到 1ms。

缓存的代价是**一致性问题**：缓存的数据和真实数据之间有时间差。研发需要决定缓存多久失效——时效太短，缓存没意义；太长，用户看到过期数据。这是个 tradeoff，不是有标准答案的问题。

---

### N+1 查询问题：后端性能的经典陷阱

这个问题很具体，但值得理解，因为你在设计列表页时会触发它。

**场景**：Mindloop 的"我的项目"页，要展示 20 个项目，每个项目显示创建者头像和名称。

**N+1 问题的写法**：
```
查询20个项目 → 1次查询
对每个项目，查询创建者信息 → 20次查询
总计：21次数据库查询
```

**批量处理的写法**：
```
查询20个项目 → 1次查询
把20个创建者ID一起查 → 1次查询
总计：2次数据库查询
```

10 倍的查询次数差距，在列表项多的时候直接影响接口响应时间。你设计一个复杂的列表卡片（包含用户头像、标签、统计数字），每增加一个数据字段，就可能引入新的 N+1 问题。这不是要你避免复杂设计，而是设计后主动问研发："这些字段怎么取，有没有性能问题？"

---

### 队列优先级：关键任务先跑

AI 生成图片是耗时任务，在 Mindloop 里可能要 10-30 秒。如果所有请求放在一个队列里先来先服务：

- 免费用户的批量生成占满队列
- 付费用户的单张生成等在后面

**队列优先级**解决这个问题：付费用户的任务插到更前面，小尺寸图比大尺寸图先处理（因为快，能快速释放资源）。

对设计的影响：你设计的"批量生成"功能，每次生成 50 张图，是在给后端队列系统施加很大压力。研发可能会限制批量数量，或者把批量任务降低优先级。理解这一点，你和研发讨论功能边界时，就不会只是说"用户需要批量"，而能说"我们怎么平衡批量体验和队列压力"。

---

### 乐观更新 & 预加载：感知速度的两个利器

**乐观更新**：用户点了收藏，UI 立刻显示"已收藏"状态，然后后台异步同步给服务器。99% 情况请求会成功，1% 失败再回滚。代价是偶尔需要处理失败状态，但换来了即时反馈。

反面：如果等服务器返回再更新 UI，用户每次操作都感受到 200-500ms 的延迟。在高频操作（滑动点赞、连续收藏）上，这会让产品感觉"发呆"。

**预加载**：预测用户下一步，提前请求资源。用户在看 Mindloop 的图片详情页，大概率会查看下一张。可以在用户还没点"下一张"时，就悄悄开始加载它。用户点击时，图片已经在本地了。

预加载的风险：预测错了就是浪费带宽。预加载策略需要基于数据——用户真实的操作路径是什么？这需要产品埋点和分析支撑，不能靠猜。

## 5. 研发在争什么

**争一：骨架屏 vs Loading Spinner**

骨架屏开发成本更高，每个页面都要单独设计占位结构。Spinner 简单但体验差。争的不是"哪个更好"，而是"这个页面的用户等待时间多久、频率多高"——等待超过 1 秒的高频页面，骨架屏的投入才值得。

**争二：缓存时效设多久**

Redis 缓存模板数据，缓存 1 分钟 vs 缓存 1 小时。1 分钟：数据新鲜，但缓存命中率低，还是要频繁查数据库。1 小时：命中率高，但如果模板数据更新了，用户可能看到旧版本。这个 tradeoff 没有标准答案，取决于数据更新频率和用户对数据新鲜度的敏感程度。

**争三：乐观更新的失败处理**

乐观更新失败时怎么回滚？用户已经看到了"收藏成功"，再显示"收藏失败"，体验更差。研发有时会认为某些操作不适合乐观更新（比如支付），有时会因为回滚逻辑复杂而放弃。设计师需要明确：哪些操作对实时性要求高，哪些可以接受偶发的状态不一致。

**争四：虚拟列表的复杂度代价**

虚拟列表在卡片高度不固定、卡片内有展开/折叠交互时，实现极其复杂，容易出 bug。研发可能会提议"限制列表最多显示 200 条，超出分页"。这是以功能约束换性能保证。哪个更重要？看产品定位。

## 6. 画廊页滑动卡顿：完整排查思路

这是一个综合问题，能把所有概念串起来。

Mindloop 画廊页滑动卡顿，你和研发怎么排查？

```
卡顿
 ├── 帧率低（滑动不流畅）→ 渲染问题
 │   ├── DOM 节点太多？→ 是否用了虚拟列表？
 │   ├── 每帧触发了重排重绘？→ CSS 动画用了什么属性？
 │   └── 图片解码压力大？→ 图片尺寸和格式对了吗？
 │
 └── 加载慢（图片半天不出来）→ 网络/资源问题
     ├── 同时请求太多？→ 懒加载有没有做？
     ├── 单张图太大？→ 有没有压缩和格式优化？
     └── 缓存没命中？→ 用户第二次进来还是慢？
```

作为设计师，你能贡献的判断：
- "我们的卡片高度是固定的吗？" → 影响虚拟列表实现难度
- "画廊是用 CSS Grid 还是瀑布流？" → 瀑布流的渲染计算更重
- "我们有没有要求首屏图片优先加载？" → 这是懒加载策略的一部分
