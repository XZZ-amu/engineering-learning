# 数据库基础：数据是怎么被"放好"和"找到"的

---

## 1. 一句话本质

**数据库在解决一个问题：让数据以某种结构存下来，之后能被快速、准确地找回来——哪怕数据量大到人脑无法直视。**

注意这句话里有两个动作："放好"和"找到"。后面所有概念——表结构、主键、外键、索引、SQL——都是这两个动作的具体解法。

---

## 2. 为什么必须这样

**如果用 Excel 存数据，会发生什么？**

Mindloop 有 10 万个用户，每个用户有几十篇笔记。你把所有数据存在一张 Excel 表里：

- 你想找"某用户最近 50 条笔记"——你得从 100 万行里筛。Excel 转圈转到你关机。
- 你想改某个用户的邮箱——你得改 37 行，改漏一行就数据不一致。
- 两个人同时在改同一份文件——文件损坏。
- 数据长什么格式完全没约束——有人在"创建时间"列填了"昨天"。

Excel 的本质是"给人看的格子"，不是"给程序用的数据结构"。数据库解决的是：如何让程序高效、安全、并发地操作海量数据。

---

## 3. 概念地图

```
根本问题：数据量大时，如何可靠地放好和找回数据？
│
├── 放好（结构设计）
│   ├── 选什么容器？        → SQL vs NoSQL
│   ├── 表长什么样？        → 字段、类型
│   ├── 如何唯一标识一行？  → 主键（Primary Key）
│   └── 表和表如何关联？    → 外键、关联关系（一对多/多对多）
│
└── 找回（查询与性能）
    ├── 如何描述"我要什么"？ → SQL 查询（SELECT/WHERE/JOIN...）
    └── 如何找得更快？       → 索引（Index）
                              └── 改结构时如何不翻车？ → 数据迁移（Migration）
```

这不是两条独立的路，而是一体两面：**你怎么"放"，决定了你能怎么"找"**。

---

## 4. 逐个概念深入

### SQL vs NoSQL：不是技术优劣，是数据形状不同

**SQL（关系型数据库，代表：PostgreSQL、MySQL）**

数据像一张张有固定列的表，表与表之间有关联关系。每行必须符合预定义的结构。

适合：数据之间关系复杂、结构稳定、需要事务保证（转账不能转一半）。

**NoSQL（文档型数据库，代表：MongoDB）**

数据像 JSON 对象，每条记录可以有不同的字段。结构灵活，可以嵌套。

适合：数据结构多变、每条记录差异大、不需要复杂关联查询。

**Mindloop 的选择逻辑：**

Mindloop 的笔记有固定的用户、创建时间、标签关联——关系清晰，用 SQL。但如果是存"AI 生成参数"（每次生成的参数字段可能完全不同），可以用 NoSQL 或 SQL 里的 JSON 字段来存。

> 核心判断：**数据之间的关系多 → SQL；数据自身的结构多变 → NoSQL**。大多数产品数据库是 SQL，只有特定场景引入 NoSQL。

### 表结构设计：提前把"放好"想清楚

以 AI 创作产品为例，核心表结构：

```
users（用户表）
  id          整数，主键，自动递增
  email       字符串，唯一
  created_at  时间戳

works（作品表）
  id          整数，主键
  user_id     整数，外键 → users.id
  title       字符串
  style_tag   字符串（如 "油画风格"）
  created_at  时间戳

generations（生成记录表）
  id          整数，主键
  work_id     整数，外键 → works.id
  prompt      文本
  model_used  字符串
  cost_tokens 整数
  created_at  时间戳

favorites（收藏表，多对多关系）
  user_id     整数，外键 → users.id
  work_id     整数，外键 → works.id
  created_at  时间戳
```

**几个关键概念：**

**主键（Primary Key）**：每行的唯一标识符。就像身份证号——不能重复，不能为空。通常是自增的整数 `id`。你用它来"精准找到这一行"。

**外键（Foreign Key）**：`works.user_id` 指向 `users.id`，意思是"这个作品属于哪个用户"。外键是表与表之间的关联线。数据库会保证：你不能给一个不存在的用户创作作品（引用完整性）。

**关联关系：**
- **一对多**：一个用户有多个作品（users → works）。用外键实现，外键放在"多"那侧。
- **多对多**：一个用户可以收藏多个作品，一个作品可以被多个用户收藏。必须用一张**中间表**（favorites）来存两侧的 id。

**字段类型为什么要想清楚：** 把用户年龄存成字符串，你就没法做"按年龄排序"。把价格存成浮点数，可能因为精度问题算出 $0.1 + 0.2 = 0.30000000000000004。类型不只是格式，是约束，也是性能。

### 基本查询：用 SQL 描述"我要什么"

SQL 的本质是"对数据集的声明式描述"——你说要什么，数据库决定怎么找。

```sql
-- 查某用户最近 50 张作品
SELECT id, title, style_tag, created_at
FROM works
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 50;

-- 按风格标签筛选作品
SELECT * FROM works
WHERE style_tag = '油画风格'
AND created_at > '2024-01-01';

-- 热门排行榜：按被收藏数降序
SELECT w.id, w.title, COUNT(f.user_id) AS favorite_count
FROM works w
JOIN favorites f ON w.id = f.work_id
GROUP BY w.id, w.title
ORDER BY favorite_count DESC
LIMIT 20;
```

**理解这几个关键字的逻辑：**

- `WHERE`：过滤条件，"我只要满足这些条件的行"
- `JOIN`：把两张表的行按关联关系拼在一起——没有 JOIN，你只能从一张表查
- `GROUP BY`：把多行合并成一行（通常跟 `COUNT`、`SUM` 配合）——"按某个维度汇总"
- `ORDER BY` + `LIMIT`：排序后取前 N 条

### 索引：找得快的秘密

**类比：** 你有一本 800 页的书，要找所有提到"Claude"的地方。没有目录——你只能从第 1 页翻到第 800 页。有目录——你直接跳到相关页码。

索引就是数据库替某列建的"目录"。没有索引，数据库就要**全表扫描**——一行一行检查。有索引，直接跳到目标位置。

**无索引 vs 有索引的差距有多大？**

```
works 表有 500 万行

无索引：WHERE user_id = 42
→ 数据库扫描 500 万行，比较每行的 user_id
→ 耗时：可能 3-8 秒

有索引（在 user_id 上建索引）：
→ 数据库通过 B 树结构直接定位 user_id = 42 的所有行
→ 耗时：几毫秒
```

**什么时候加索引？**

- 经常出现在 `WHERE` 条件里的字段（如 `user_id`、`style_tag`）
- 经常用于 `JOIN` 的外键字段
- 经常用于 `ORDER BY` 排序的字段

**但索引不是越多越好。** 每次写入数据（新增、修改、删除），数据库都要同步更新所有索引。索引太多 → 写入变慢 → 存储占用增加。

> 判断规则：**高频查询的过滤/排序字段，加索引。低频查询或写多读少的场景，慎加。**

### 数据迁移（Migration）：为什么改表结构要小心

你上线了，`works` 表有 200 万行数据。产品说要加一列 `category`（作品分类）。

问题来了：

1. **旧数据怎么办？** 新加的列，旧的 200 万行都是空值。如果代码要求这列不能为空，直接崩。
2. **加列期间怎么办？** 某些数据库对大表加列会锁表，几分钟内用户无法写入数据。
3. **新旧代码并存怎么办？** 发布期间可能有旧代码和新代码同时在跑，旧代码不认识新字段。

这就是为什么改表结构不是"改一行配置"，而是一个需要计划的操作，叫**数据迁移（Migration）**。

Migration 是一段描述"表结构如何变化"的代码，可以执行（apply）也可以回滚（rollback）。它的存在，是为了让表结构的变化像 Git commit 一样可追溯、可协作、可撤销。

## 5. 研发在争什么

**争一：要不要提前"过度设计"表结构？**

有人说：早期别想太多，先跑起来，表结构以后可以改。有人说：表结构改起来代价极高，应该提前设计好。

真相：早期确实不该追求完美，但**有些结构决策一旦错了，代价极高**——比如主键选型（用自增 id 还是 UUID）、时区存储方式、核心关联关系。这些值得早期想清楚，其他的可以迭代。

**争二：加多少索引合适？**

"所有 WHERE 字段都加索引"听起来很安全，但对写多读少的表（比如生成记录表，每秒几十次写入）会让写入性能恶化。索引策略必须看读写比例。

**争三：复杂查询用 SQL 写还是在代码里处理？**

热门排行榜，可以用一句复杂 SQL 算，也可以查出原始数据再用 Python 处理。SQL 做在数据库里更快（数据不用传输），但复杂 SQL 难维护。争的是性能和可维护性的权衡——通常：**能在数据库完成的聚合，就在数据库做**，但别让 SQL 承担业务逻辑。

**争四：需要"软删除"吗？**

删除一条作品，到底是从数据库里物理删掉，还是加一列 `deleted_at` 标记为已删除（软删除）？软删除保留了历史数据、可以撤销、便于审计，但所有查询都要加 `WHERE deleted_at IS NULL`，容易漏写导致 bug。
