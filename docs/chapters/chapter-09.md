# P1-1: AI 工程基础 — 模型调用、Prompt 结构、采样参数、工作流

---

## 1. 一句话本质

**AI 生图模型在做一件事：把"描述"翻译成"像素"——但翻译过程是有随机性的，你的工作是用参数控制这个随机性，让它收敛到你想要的方向。**

所有东西从这句话往外推：prompt 是你给的描述，采样参数是控制翻译过程的旋钮，LoRA/ControlNet 是缩窄可能性的约束，ComfyUI 是把多次翻译串成流水线。

---

## 2. 为什么必须这样（如果不控制随机性，会出什么事）

假设你让模型画"一个女人坐在咖啡馆里"——运行十次，你会得到十张完全不同的图：光线不同、风格不同、人脸不同、甚至咖啡馆消失了变成餐厅。

这不是 bug，这是模型的工作方式：它从噪声里"猜"出一张符合描述的图，猜的起点是随机的，猜的路径是随机的，所以结果千变万化。

**这就是问题所在**：你想要的不是"千变万化"，你想要的是"可重现、可调优、可交付"。

所以整个参数体系存在的理由就一个：**驯服随机性，让它变成可控的创作工具。**

---

## 3. 概念地图

```
根本问题：描述 → 像素，翻译过程有随机性
│
├── 控制"翻译的材料"
│   ├── 基础模型（SD / FLUX）        ← 决定世界观，能画什么风格
│   ├── LoRA                          ← 注入特定角色/风格的记忆
│   └── ControlNet                    ← 注入构图/姿势的硬约束
│
├── 控制"翻译的指令"
│   ├── 正向 prompt                   ← 告诉模型画什么
│   ├── 反向 prompt                   ← 告诉模型不要什么
│   └── 权重语法                      ← 哪些词更重要
│
├── 控制"翻译的过程"
│   ├── seed                          ← 随机起点（可复现）
│   ├── steps                         ← 翻译走多少步（精度 vs 速度）
│   ├── cfg/guidance scale            ← 翻译多严格遵守指令
│   └── sampler                       ← 用什么路径走这些步
│
└── 控制"翻译的编排"
    └── ComfyUI 工作流                ← 把多次翻译串成有依赖的流水线
```

这张图的核心关系是：**材料决定天花板，指令决定方向，过程决定路径，编排决定复杂度。**

## 4. 逐个概念深入

### 模型推理：摄影棚类比

把一次生图想象成在摄影棚拍一张照片：

- **相机（基础模型）**：决定你能拍什么风格——胶片机、数码单反、手机，出来的感觉不一样
- **指令（prompt）**：你告诉摄影师"拍一个穿红裙的女人，逆光，咖啡馆"
- **布光参数（采样参数）**：光圈、快门、ISO——控制拍摄过程的质感
- **拍多少张（steps）**：拍 5 张毛片挑一张 vs 拍 50 张精修

**GPU 为什么贵？** 因为每一"步"推理都是几亿次矩阵运算，steps=20 意味着这个过程要走 20 遍。GPU 是专门做矩阵乘法的硬件，没有它，一张图要算几分钟。这就是为什么本地跑模型要显卡，云端调用要按次收费。

---

### Prompt 结构：你在跟一个懂很多但很字面的人说话

模型不理解意图，只匹配语义。"美丽的女人"和"一个站在窗边的女人，阳光打在她侧脸上"——后者出来的图好得多，因为前者给的信息太少，模型只能猜。

**正向 prompt 的结构**（从高权重到低权重排列）：
```
[风格/品质词], [主体描述], [场景/背景], [光线/色调], [镜头/构图]

例：
masterpiece, highly detailed, 
a young woman sitting in a cafe,
warm afternoon light, bokeh background,
35mm portrait lens, shallow depth of field
```

**反向 prompt** 是告诉模型"翻译时跳过这些词"：
```
ugly, deformed, blurry, watermark, extra fingers, bad anatomy
```

为什么要有反向 prompt？因为模型的训练数据里有大量低质量图，不明确排除，它有概率"往那个方向猜"。

**权重语法**：`(词:1.5)` 表示这个词权重提高到 1.5 倍，`[词]` 表示降权。用得太重会让画面失真，一般调到 1.2-1.4 就够。

---

### 采样参数：四个旋钮，各管一件事

**Seed（随机种子）**
随机起点编号。同一 seed + 同一参数 = 完全相同的图。这是"可复现性"的来源。
用法：找到一张满意的图，记住它的 seed，然后在这个 seed 基础上微调其他参数。

**Steps（步数）**
模型从噪声"雕刻"出图像要走多少步。步数少（10步）= 轮廓粗糙但快；步数多（50步）= 细节丰富但慢。
**实践上 20-30 步是甜蜜点**，再多收益递减。

**CFG / Guidance Scale（引导强度）**
控制模型有多严格地遵守你的 prompt。
- CFG=1：模型自由发挥，可能完全忽略你说的内容
- CFG=7：正常遵守
- CFG=15+：过度遵守，画面开始扭曲、过饱和

类比：CFG 是摄影师听你话的程度。太低他自己乱拍，太高他卡文字卡死了，反而照片很奇怪。

**Sampler（采样器）**
从噪声走向图像的"路径算法"。不同 sampler 在同样 steps 下收敛速度不同。
- `DPM++ 2M Karras`：主流选择，速度快质量好
- `Euler a`：有更多随机变化，适合探索
- `DDIM`：适合需要精确控制的场景（如 img2img）

**大多数时候你不需要换 sampler**，除非你在榨干 steps 性能。

---

### 模型类型：三层叠加关系

```
基础模型（SD / FLUX / 可灵）
    ↓ 叠加
LoRA（角色/风格记忆，±10-30% 的影响）
    ↓ 叠加
ControlNet（构图/姿势的硬约束）
```

**基础模型**：决定世界观。SD 1.5 写实度低，SDXL 更强，FLUX 当前生图质量最高。换模型 = 换底层世界观，影响巨大。

**LoRA**：轻量级"记忆注入"。想让模型画固定风格（比如宫崎骏风）或固定角色（比如你产品的 IP 形象），就训练一个 LoRA，叠上去。LoRA 不改模型本体，只微调输出方向。
*什么时候用 LoRA：需要风格一致性、角色一致性的时候。*

**ControlNet**：给模型加"骨架约束"。你有一张参考姿势图，ControlNet 能让模型严格按照这个姿势生成，哪怕换了人换了风格。
*什么时候用 ControlNet：需要控制构图、姿势、边缘轮廓的时候。*

**三者关系**：没有 LoRA 和 ControlNet，prompt 只能"说说而已"，模型爱怎么解释怎么解释。叠上它们，你拿到的是越来越精确的控制权。

---

### ComfyUI 工作流：为什么节点式编排比"一键生图"强

单次调用的天花板：你输入 prompt，得到一张图。想改一个细节，全部重来。

ComfyUI 把生图流程拆成有依赖关系的节点：

```
[加载模型] → [编码 prompt] → [采样] → [解码] → [保存]
                                ↑
                          [ControlNet 节点]
                                ↑
                          [参考图输入]
```

**为什么这样更强？**

1. **局部可变**：只改采样节点的 seed，其他全不动——你在做"控制变量实验"
2. **流程可复用**：同一个工作流，换掉模型节点，其他节点不变——批量出不同风格
3. **复杂逻辑可组合**：先生成一张草图，把草图输入 ControlNet，再生成精图——这种"图生图"的链式逻辑，单次调用做不到

对 Mindloop 这种产品：如果要给用户提供 AI 生图功能，工作流意味着你可以把整套参数固化成模板，用户只需要填 prompt，后端跑固定工作流——这就是"产品化 AI 能力"的方式。

### 部署方式：自建 vs API，谁更适合你

| | 自建（RunPod/本地） | API（Replicate/云厂商） |
|---|---|---|
| 启动成本 | 高（配置环境、管模型） | 低（注册即用） |
| 单次成本 | 低（跑满 GPU 很便宜） | 高（按次计费） |
| 延迟 | 低（本地） | 有网络延迟 |
| 可控性 | 完全可控 | 受制于 API 限制 |
| 适合场景 | 高频调用、需要定制模型 | 原型验证、低频使用 |

**早期产品用 API，跑通后高频场景迁移自建**——这是主流路径。

## 5. 研发在争什么

**争一：用哪个基础模型**
SD 系列生态好（LoRA/ControlNet 资源多），FLUX 质量更高但生态还在建设，可灵对中文语义理解更好。没有绝对答案，取决于你的内容类型和现有资产。

**争二：steps 设多少**
有人说 20 步够了，有人坚持 40 步。本质是**质量 vs 成本的 tradeoff**——如果你一天要跑 10 万次生图，步数从 40 降到 20，成本直接减半。

**争三：workflow 复杂度**
节点越多越灵活，但维护成本越高，报错越难 debug。简单产品用简单调用，复杂产品才值得投入工作流工程。

**争四：自建 vs API**
产品早期几乎全用 API，但一旦日调用量上去，API 费用会成为主要成本项。什么时候迁移自建，没有通用答案，取决于工程团队的运维能力。
