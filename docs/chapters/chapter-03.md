# 网络协议：一次请求的完整旅程

## 1. 一句话本质

**HTTP 是一问一答的协议——浏览器问，服务器答，所有问题都是围绕"这次对话怎么让双方都理解对方、信任对方、不重复说废话"展开的。**

从这句话可以推导出一切：状态码是答话里的"语气词"，缓存是"上次说过了不用再说"，HTTPS 是"怎么确认对方不是骗子"，WebSocket 是"打破一问一答、改成持续通话"。

---

## 2. 为什么必须这样

想象没有 HTTP，浏览器和服务器要通信，会发生什么？

两台机器不认识彼此。A 发了一段字节流给 B，B 不知道这是在请求文件还是发消息，不知道这次请求结束没结束，不知道用中文还是英文回。

更麻烦的是：如果每次加载 Mindloop 的 logo 图，都要重新下载一次，用户网络一差就转圈。如果登录信息传输被中间人截获，密码就明文暴露。如果服务器挂了，浏览器不知道是"你的请求有问题"还是"我这边出错了"。

这些问题——**怎么说清楚、怎么不重复说、怎么安全说、怎么知道说成了没有**——就是 HTTP 这套协议要解决的全部。

---

## 3. 概念地图

```
一次请求的完整链路
│
├── 找到对方在哪
│   └── DNS 解析（域名 → IP）
│
├── 建立连接
│   ├── TCP 握手（确认双方都在）
│   └── TLS 握手（HTTPS 专属，确认对方是真的）
│
├── 发起对话
│   ├── 请求头（我是谁、我要什么、我能接受什么格式）
│   └── 请求体（POST 时附带的数据）
│
├── 收到回答
│   ├── 状态码（这次对话的结果：成了/你错了/我错了/去别处）
│   ├── 响应头（告诉浏览器怎么处理这个回答）
│   └── 响应体（真正的内容）
│
└── 优化对话
    ├── 缓存（这个答案上次说过，直接用）
    └── WebSocket（别问答了，咱持续通话）
```

这不是并列的知识点清单——是一条时间线，从"开口"到"听完"，每个环节解决一个不同的问题。

---

## 4. 逐个概念深入

### DNS：找地址

你输入 `mindloop.app`，浏览器不认识这串字母。互联网只认 IP 地址（比如 `104.21.3.89`）。

DNS 就是电话簿——把域名翻译成 IP。这一步失败，后面全没有。

**慢在哪**：第一次访问要查 DNS，通常几十毫秒。之后有缓存，很快。你在浏览器网络面板里看到"DNS Lookup"这一栏，就是这个时间。

---

### TCP 握手：先确认双方都在线

找到 IP 之后，浏览器和服务器要"建连"——三次握手，本质是：
```
浏览器：我要说话了（SYN）
服务器：收到，我也准备好了（SYN-ACK）
浏览器：好，开始（ACK）
```

为什么要三次？一次两次不够——因为需要双方都确认"我能发、我也能收"。这是可靠传输的代价。

---

### HTTPS：怎么确认对方不是骗子

HTTP 是明文——中间任何节点都能看到你传了什么。HTTPS 加了 TLS，在 TCP 握手之后、正式说话之前，再加一轮 TLS 握手。

TLS 握手做两件事：
1. **验证身份**：服务器出示证书（CA 机构签发），浏览器验证"这确实是 mindloop.app 不是假冒的"
2. **协商密钥**：用非对称加密交换一个临时对称密钥，后续通信用这个密钥加密

类比：见面时先查身份证，确认是本人，然后商量一个暗语，以后用暗语说话。

**设计 tradeoff**：TLS 握手增加了延迟（又多了几个来回），但现代 HTTP/2 和 HTTP/3 把这个代价压缩得很小，安全成本已经不是问题。

---

### 状态码：对话结果的语气词

状态码的结构设计很有逻辑性——第一位数字就告诉你"谁的问题"：

```
2xx  成功了
3xx  去别处（重定向）
4xx  你的问题（客户端错误）
5xx  我的问题（服务器错误）
```

逐个看：

| 状态码 | 意思 | 研发场景 |
|--------|------|---------|
| **200** | 成功 | 最普通的成功 |
| **301** | 永久跳转 | `http://` 跳到 `https://`，浏览器会记住，下次直接去新地址 |
| **304** | 没变，用缓存 | 浏览器问"这个文件变了吗"，服务器说"没变，用你本地的" |
| **400** | 请求格式错了 | 你发的数据格式不对，服务器看不懂 |
| **401** | 没登录 | 需要身份验证但没提供 |
| **403** | 没权限 | 登录了，但你没资格看这个 |
| **404** | 找不到 | URL 对应的资源不存在 |
| **500** | 服务器崩了 | 服务端代码出错，研发去看日志 |

**401 vs 403 的区别**经常混淆：401 是"你是谁我不知道"，403 是"我知道你是谁，但你不能来这里"。Mindloop 用户没登录访问私密笔记返回 401；登录了但试图访问别人的笔记返回 403。

**4xx vs 5xx 的重要性**：出了问题，研发第一步就是看状态码——是前端传错了数据（4xx）还是后端自己炸了（5xx）？责任归属不同，排查方向不同。

---

### 请求头和响应头：对话里的元信息

头部（headers）是附在请求/响应里的"元信息"，不是正文内容，但告诉对方"怎么理解这段话"。

几个最常见的：

**请求头：**
- `Authorization: Bearer xxx` — 我的登录凭证，API 认证常用
- `Content-Type: application/json` — 我发的是 JSON 格式
- `If-None-Match: "abc123"` — 上次你给我的这个文件版本号，它变了吗？（缓存协商用）

**响应头：**
- `Cache-Control: max-age=3600` — 这个资源可以缓存 1 小时
- `Content-Type: text/html` — 我返回的是 HTML，你知道怎么渲染
- `Set-Cookie: session=xxx` — 我给你设置一个 cookie，下次带上来

你在浏览器开发者工具的 Network 面板，点开任意一个请求，Headers 标签里就是这些。

---

### 缓存：为什么刷新没用

这是最容易让设计师困惑的部分："我明明改了设计稿导出的图，为什么页面还是旧的？"

缓存的逻辑是：**浏览器把上次下载的资源存在本地，下次不一定重新下载。** 服务器通过响应头控制这个行为。

**两种缓存模式：**

```
强缓存（不问服务器）
  Cache-Control: max-age=3600
  → 1 小时内直接用本地，连请求都不发
  → 状态码显示 200（from cache）

协商缓存（问服务器变了没）
  请求带 If-None-Match 或 If-Modified-Since
  → 服务器说"没变" → 304，浏览器用本地
  → 服务器说"变了" → 200，返回新内容
```

**为什么刷新有时没用**：强缓存期间，普通刷新（F5）会发请求但带缓存头，服务器说"没变"返回 304。强制刷新（Ctrl+Shift+R）才会忽略缓存头强制重新下载。

**Mindloop 场景**：Mindloop 的 JS/CSS 打包文件名会带 hash（`main.a3f9b2.js`），内容变了 hash 就变，URL 就变，等于"每次都是新文件"，可以设超长强缓存。但 `index.html` 不能缓存——因为它里面引用了哪个 hash 文件。

这是个经典设计决策，后面会展开。

---

### WebSocket：打破一问一答

HTTP 的本质是"一问一答，答完断开"。但如果 Mindloop 要做实时协作——A 改了一句话，B 的屏幕要立刻更新——用 HTTP 怎么办？

**轮询（Polling）**：B 每秒问服务器"有新内容吗？"——大量无效请求，浪费资源。

**WebSocket**：建连一次，之后保持长连接，双向随时发消息——服务器有更新主动推给客户端，不需要客户端一直问。

```
HTTP：  浏览器问 → 服务器答 → 连接关闭（重复）
WS：   握手建连 → ←→←→←→ 双向持续通信 → 关闭
```

WebSocket 建立在 HTTP 之上——先用 HTTP 握手升级协议（`Upgrade: websocket`），然后"升级"成 WebSocket 连接。

**什么时候用**：实时聊天、协作编辑、实时通知、股票行情。不需要实时的场景不要滥用——维护长连接有成本。

## 5. 研发在争什么

**缓存策略怎么设**

最常见的分歧：静态资源要不要带版本号？

- 带 hash（`main.a3f9b2.js`）：可以永久强缓存，但每次发布文件名变了，需要构建工具支持
- 不带 hash，依赖协商缓存：实现简单，但每次刷新都要发请求问"变了没"，多一个网络来回

大多数现代项目选前者。但如果是 API 接口的缓存策略，就复杂得多——缓存时间太长用户看到旧数据，太短缓存没意义。

**HTTP/1.1 vs HTTP/2**

HTTP/1.1 一次连接只能处理一个请求（排队）；HTTP/2 支持多路复用（同一个连接并行处理多个请求）。

争论通常是：老项目升不升级 HTTP/2？代价是需要 HTTPS（HTTP/2 强制要求），但好处是明显减少请求排队延迟。

**实时功能用 WebSocket 还是 SSE（Server-Sent Events）**

SSE 是服务器单向推送，实现简单；WebSocket 双向，但实现复杂。

如果只是"通知用户有新消息"，SSE 够用；如果要双向交互（实时协作），WebSocket。选错了，要么过度设计，要么功能不够。
