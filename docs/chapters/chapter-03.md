# P0-3: 网络协议 — 一个请求的完整旅程

> **一句话总结**：HTTP 是浏览器和服务器之间"说话的规矩"，理解它能让你看懂请求慢在哪、卡在哪，跟后端对话时不再一脸懵。

---

## 先想一个场景

你在 Mindloop 里点了"同步笔记"按钮。

页面转了一圈，笔记更新了。

这 0.3 秒里，发生了什么？

大多数人的答案是："发了个请求，数据回来了。"

但如果研发跟你说："这个接口 P99 延迟 800ms，问题在 DNS 解析阶段"——你听懂了吗？

这篇教案就是为了让你能听懂这句话。

---

## 第一部分：一次 HTTP 请求的完整旅程

### 类比：寄一封快递信

HTTP 请求就像寄快递。你（浏览器）要给朋友（服务器）寄一件东西，中间要经历这几步：

1. **查地址簿**：你只知道朋友叫"小明的笔记服务器"，但快递员需要实际地址。这步叫 **DNS 解析**。
2. **打电话确认收件**：在寄件之前，快递员要先打个电话确认对方能收货。这步叫 **TCP 握手**。
3. **装箱寄出**：把你要说的话（请求内容）装进快递箱寄出去。这步叫 **发送 HTTP 请求**。
4. **收到回复**：朋友拆开包裹，写了回信寄回来。这步叫 **收到 HTTP 响应**。

### 每一步拆开看

#### Step 1：DNS 解析（查地址簿）

你在浏览器输入 `api.mindloop.app`，但网络世界认的是 IP 地址（比如 `104.21.33.42`）。

DNS 就是互联网的"电话本"——把域名翻译成 IP 地址。

```
你输入：api.mindloop.app
DNS 查询后：104.21.33.42
```

**这步慢了会怎样？** 你打开页面第一个白屏就会很长。有时候你清了缓存、换了网络，第一次打开特别慢，DNS 可能是原因之一。

#### Step 2：TCP 握手（确认能通话）

找到 IP 之后，浏览器要跟服务器建立连接。TCP 握手是一个"三次确认"的过程：

> 浏览器："喂，你在吗？"（SYN）  
> 服务器："在！你能听见我吗？"（SYN-ACK）  
> 浏览器："能听见！开始说正事。"（ACK）

这三步完成，连接建立，可以开始传数据了。

**为什么需要三步？** 这是为了确认双方都能发、都能收。就像电话接通之前要确认信号。

#### Step 3：发送 HTTP 请求

连接建立后，浏览器发出请求。一个请求长这样：

```
POST /api/notes/sync HTTP/1.1
Host: api.mindloop.app
Content-Type: application/json
Authorization: Bearer eyJhbGci...

{"note_id": "123", "content": "今天的会议记录..."}
```

拆解一下：
- **第一行**：方法（POST）+ 路径（/api/notes/sync）+ 协议版本
- **中间几行**：请求头（Header）——告诉服务器"我是谁、我发的是什么格式、我有没有登录"
- **空一行之后**：请求体（Body）——真正要发送的内容

#### Step 4：收到 HTTP 响应

服务器处理完，发回来：

```
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache

{"status": "synced", "updated_at": "2024-01-15T10:30:00Z"}
```

结构跟请求类似：状态行 + 响应头 + 响应体。

## 第二部分：HTTPS 是什么？加密是怎么回事

### 类比：寄信 vs 寄密封信

普通 HTTP 就像寄明信片——快递员（路上的任何网络节点）都能看到你写的内容。

HTTPS 就像把信装进一个特制锁盒——只有收信人有钥匙能打开。

**加密的过程（TLS 握手）简单说：**

1. 服务器出示"身份证"（数字证书，证明"我真的是 api.mindloop.app"）
2. 双方商量一个"临时密码"（只有这次通话用，下次换一个）
3. 之后所有内容都用这个密码加密传输

所以 HTTPS 比 HTTP 多了一步 TLS 握手，这也是为什么 HTTPS 请求稍微慢一丁点——但现代浏览器优化得很好，基本感知不到。

**怎么确认是 HTTPS？** 看浏览器地址栏左边的锁图标，或者 URL 开头是 `https://`。

## 第三部分：状态码——服务器的"表情包"

状态码是服务器告诉你"这次请求结果怎么样"的方式。分五类：

| 范围 | 意思 | 类比 |
|------|------|------|
| 2xx | 成功了 | 快递签收 ✅ |
| 3xx | 去别的地方找 | 转寄通知 📦 |
| 4xx | 你搞错了 | 地址写错了 ❌ |
| 5xx | 我这边出问题了 | 快递站着火了 🔥 |

### 高频状态码逐个解释

**200 OK** — 一切正常，数据在响应体里。
> Mindloop 同步笔记成功，返回 `{"status": "synced"}`。

**301 Moved Permanently** — 永久跳转，以后都去新地址。
> 你访问 `http://mindloop.app`，服务器说"我永久搬到 `https://mindloop.app` 了，以后直接去那边"。浏览器下次会自动用新地址，不再问服务器。

**304 Not Modified** — "你上次拿的那份还是最新的，不用重新下载。"
> 这是**缓存机制**的核心，后面会细说。

**400 Bad Request** — 你发的请求格式有问题，服务器看不懂。
> 比如 JSON 格式写错了，漏了一个引号。

**401 Unauthorized** — 没有登录，不知道你是谁。
> Mindloop 同步时 Token 过期了，服务器说"你谁啊？先登录"。

**403 Forbidden** — 知道你是谁，但你没权限。
> 你登录了，但你想访问别人的私密笔记，服务器说"我认识你，但你不能看这个"。

**404 Not Found** — 你要的东西不存在。
> 请求一个已经删除的笔记 ID，服务器说"找不到这篇笔记"。

**500 Internal Server Error** — 服务器内部出错，跟你无关。
> 数据库崩了，服务端代码有 bug，都会返回 500。

**实际用途**：当你在 Mindloop 里点了按钮没反应，打开开发者工具的 Network 面板，第一眼看状态码——是 4xx（前端/请求问题）还是 5xx（后端问题），这直接决定你跟谁沟通。

## 第四部分：请求头和响应头里的关键信息

Header 就像快递单上的附加信息——不是货物本身，但快递员和收件人都要看。

### 你最常见到的请求头

```
Authorization: Bearer eyJhbGci...    // 登录凭证（Token）
Content-Type: application/json       // 我发的是 JSON 格式
Accept: application/json             // 我希望收到 JSON 格式
```

### 你最常见到的响应头

```
Content-Type: application/json       // 我返回的是 JSON
Cache-Control: max-age=3600         // 这个响应可以缓存 1 小时
Set-Cookie: session=abc123          // 帮我记一下这个 Cookie
```

**跟研发对话时**：如果接口返回了数据但前端显示不出来，让研发看看响应头里的 `Content-Type` 对不对；如果每次数据都是旧的，看看 `Cache-Control` 是不是设置了太长时间。

## 第五部分：缓存机制——为什么刷新有时候没用

### 类比：图书馆的借阅复印件

你去图书馆查资料，管理员说"这本书昨天有人查过，我复印了一份放柜台，你直接拿"——这就是缓存。

下次你来，管理员先看复印件还有没有用，有用就直接给你，不用重新去书架取。

### HTTP 缓存怎么工作

服务器在响应头里告诉浏览器："这个资源可以缓存多久。"

```
Cache-Control: max-age=86400    // 缓存 24 小时，24小时内别来问我
Cache-Control: no-cache         // 每次都来问我，但我可以告诉你"没变"
Cache-Control: no-store         // 不许缓存，每次都重新取
```

### 304 Not Modified 是怎么回事

`no-cache` 不是"不缓存"，而是"缓存了，但每次用之前先确认一下还有没有过期"。

流程是这样的：

```
第一次请求：
浏览器 → 服务器："给我 notes.js"
服务器 → 浏览器："给你，最后修改时间是 Jan 15 10:00"
（浏览器把文件存下来）

第二次请求：
浏览器 → 服务器："给我 notes.js，我上次拿的是 Jan 15 10:00 的版本"
服务器 → 浏览器："没变，304"（不用传文件内容，省流量）
浏览器："那我用本地存的那份就行了"
```

### 为什么"强刷新"有时候有用

- 普通刷新（F5）：浏览器还是会带上缓存信息去问服务器
- 强制刷新（Ctrl+Shift+R）：浏览器完全忽略缓存，重新取所有资源
- 清除缓存：彻底删掉本地存的旧文件

**Mindloop 的实际场景**：你更新了 Mindloop 的 UI，但用户说"我怎么还是旧版？"——这是因为浏览器缓存了旧的 CSS/JS 文件。解决方案是在文件名里加版本号（比如 `app.v2.js`），这样浏览器认为是新文件，不会用旧缓存。这叫**缓存破坏（Cache Busting）**。

## 第六部分：WebSocket——"保持通话"模式

### HTTP 的局限：只能你问我答

普通 HTTP 就像发短信——你发一条，我回一条，每次都是独立的对话。

如果你想做"实时协作编辑"（多人同时编辑同一篇笔记），HTTP 不够用：你没办法让服务器"主动"推消息给你。

老办法是**轮询**：每隔 1 秒问一次服务器"有新内容吗？"——很浪费，大多数时候都是白问。

### WebSocket：打一个不挂断的电话

WebSocket 就是把短信改成电话——连接建立之后，双方随时可以说话，不需要每次都重新连。

```
// 建立连接（握手只做一次）
ws://mindloop.app/realtime

// 之后任意一方都可以随时发消息：
服务器 → 浏览器："用户 A 刚改了第三段"
浏览器 → 服务器："用户 B 加了一个标签"
```

**适合 WebSocket 的场景**：
- 实时协作编辑（Notion、飞书文档）
- 聊天（Slack、微信网页版）
- 实时通知（"你有新消息"）
- 实时数据看板（股票价格、监控大屏）

**不适合 WebSocket 的场景**：
- 普通的"点击按钮，拿数据"——用 HTTP 就够了，不需要保持长连接

**对 Mindloop 的意义**：如果你们要做"多人协作笔记"，后端就需要引入 WebSocket；如果只是单人同步，HTTP 完全够用。这是功能设计阶段就要跟研发确认的事。

## 整体回顾：一次 Mindloop 同步请求的完整旅程

```
你点了"同步"按钮
    ↓
1. DNS 解析：api.mindloop.app → 104.21.33.42（查地址）
    ↓
2. TCP 握手：确认服务器在线、能通信（三次握手）
    ↓
3. TLS 握手：协商加密密钥（因为是 HTTPS）
    ↓
4. 发送请求：
   POST /api/notes/sync
   Authorization: Bearer xxx
   {"note_id": "123", ...}
    ↓
5. 服务器处理：验证身份 → 查数据库 → 准备响应
