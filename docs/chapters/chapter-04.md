# 认证与权限：服务器怎么知道你是谁，以及你能干什么

---

## 1. 一句话本质

**认证与权限解决的是同一个根问题：HTTP 是无记忆的，服务器每次收到请求都不知道对面是谁——所有登录机制，都是在给"无状态的通信"打上"有状态的标记"；所有权限模型，都是在说这个标记对应的人能碰什么。**

---

## 2. 为什么必须这样

想象 HTTP 是一个失忆的服务员。你点了菜、报了姓名，他转身就忘了。下一秒你再叫他，他完全不认识你。

这不是比喻，是事实。HTTP 协议本身不保存任何状态。每个请求对服务器来说都是陌生人。

那如果没有登录机制，会发生什么？

- 你在飞书登录，切换页面，服务器问：你是谁？
- 你在 Mindloop 保存笔记，服务器问：这条笔记该存给谁？
- 你打开别人的私有笔记链接，服务器问：……我没法判断你有没有权限，那就都给你看吧。

所有混乱都来自同一个缺失：**没有跨请求识别身份的机制**。

所以"登录"这件事，本质不是验证密码。密码只是你第一次证明"我是我"的手段。真正的工程挑战是：**验证通过之后，怎么让服务器在后续每次请求里都认出你——而且不能被人伪造。**

---

## 3. 概念地图

```
根问题：HTTP 无状态，服务器不记得你是谁
│
├── 解法一：服务器记住你（Session）
│   └── 服务器存状态，给你一张"号码牌"
│
├── 解法二：你自己带着证明（Token / JWT）
│   └── 服务器不存状态，你每次带着"身份证"来
│
├── 解法三：让别人帮你证明（OAuth）
│   └── "微信担保我是我"，服务器信任微信
│
└── 解决了"你是谁"之后 → 解决"你能干什么"
    └── 权限模型（RBAC）
        ├── 用户 → 角色
        └── 角色 → 权限
```

认证（Authentication）= 你是谁  
授权（Authorization）= 你能干什么  
这两件事经常被混在一起说，但它们是先后两步。

---

## 4. 逐个概念深入

### Session：服务器记住你

你登录成功，服务器在自己的内存/数据库里存一条记录：`session_id: abc123 → 用户 ID 42`，然后把 `abc123` 这个号码牌发给你的浏览器（存在 Cookie 里）。

之后你每次发请求，浏览器自动带上这个 Cookie，服务器查一下自己的记录，找到你是用户 42，认证通过。

**代价**：服务器要存所有在线用户的状态。用户多了是个负担；如果你有多台服务器，用户 A 的 Session 存在服务器 1，请求却打到了服务器 2，服务器 2 不认识他——要么做 Session 同步，要么用粘性路由，都是麻烦。

**适用**：单台服务器、传统 Web 应用、对安全性要求高且可控的场景。

---

### Token / JWT：你自己带着证明

服务器不存状态。登录成功后，服务器把你的身份信息打包，**用自己的私钥签名**，生成一段字符串（Token）发给你。

之后你每次请求带上这个 Token，服务器用自己的密钥验签——签名对了，就相信里面的内容。

JWT（JSON Web Token）是最流行的 Token 格式。它分三段：

```
头部（算法）.载荷（用户信息）.签名
```

载荷里可以装：用户 ID、角色、过期时间。这些内容**是明文的**（Base64 编码，不是加密），任何人解码都能看到，但篡改了签名就对不上，服务器会拒绝。

**代价**：Token 签发出去，服务器就不再管它了。你想让某个 Token 立刻失效（比如用户被封号），很难——服务器不存状态，它不知道哪些 Token 该作废。只能等它自然过期。

**适用**：前后端分离、移动端 App、多服务架构（微服务）。Mindloop 的 Electron 客户端跟后端通信，用 JWT 比 Session 自然得多。

---

### Token 过期与刷新机制

Token 不能永不过期，否则一旦泄露就永久有效。但 Token 过期太短，用户要频繁重新登录，体验差。

解法：**双 Token 机制**。

- **Access Token**：短命（15 分钟到 1 小时），用来实际访问接口
- **Refresh Token**：长命（几天到几周），只用来换新的 Access Token

Access Token 过期了，用 Refresh Token 静默换一个新的，用户无感知。Refresh Token 本身如果泄露或要作废，服务器可以在数据库里标记它失效（因为 Refresh Token 的操作频次极低，存一下是可以接受的）。

---

### OAuth：让别人帮你证明

"用微信登录"背后发生了什么？

你的核心诉求是：不想再注册一个账号。飞书/某个工具想要你的用户信息但不想自己处理账号体系。微信有你的真实身份。

OAuth 就是一套标准协议，让三方协作：

```
用户 ←→ 你的应用 ←→ 微信（授权方）
         "我要登录"    "你允许这个应用获取你的信息吗？"
                      允许 → 微信给应用发一个 code
                      应用拿 code 换 Token
                      应用拿 Token 获取用户信息
                      应用用这个信息创建/匹配本地账号
```

关键点：**你的应用拿到的不是微信密码，而是微信颁发的访问凭证**。微信只告诉你"这个用户是 openid: xyz"，其他都不给，也不需要给。

对设计师的意义：做第三方登录时，后端需要先去微信/GitHub 开发者平台注册应用、拿到 AppID 和 Secret，这有审核周期。不是画了按钮就能上线的。

---

### RBAC：权限不绑人，绑角色

知道你是谁之后，下一个问题：你能看哪些内容，能做哪些操作？

最直觉的做法：给每个用户单独配置权限。100 个用户就要配 100 次。用户职位变了，还要重新配。不可维护。

RBAC（Role-Based Access Control，基于角色的权限控制）的思路：**把权限挂在角色上，把角色分配给用户**。

```
用户 张三 → 角色：编辑
用户 李四 → 角色：管理员
用户 王五 → 角色：只读

角色 编辑   → 可以：读、写笔记；不能：删除用户
角色 管理员 → 可以：读、写、删除、管理用户
角色 只读   → 可以：读笔记
```

Mindloop 里的典型场景：工作区的"所有者""协作者""访客"就是三个角色。你设计共享功能时，要想的不是"这个人能不能做这件事"，而是"这个角色被赋予了哪些权限，这个人是什么角色"。

这个分层思路会让权限变更成本从 O(用户数) 降到 O(角色数)。

---

### CSRF：Cookie 的副作用

Session 方案依赖 Cookie。Cookie 有个特性：浏览器访问某个域名时，会**自动带上**该域名的所有 Cookie。

攻击者可以构造一个恶意页面，让你的浏览器在你不知情的情况下，向你登录着的网站发请求——浏览器会自动带上 Cookie，服务器以为是你本人操作。这就是 CSRF（跨站请求伪造）。

Token 方案（JWT 放在请求头里）天然免疫 CSRF——浏览器不会自动在请求头里加 Token，必须 JavaScript 主动取出来发，而恶意网站的 JS 无法读取你的 Token。

## 5. 研发在争什么

**Session vs Token，怎么选？**

Session 的拥护者说：Token 无法即时吊销，安全性有隐患；Session 在服务端完全可控。Token 的拥护者说：Session 有扩展性瓶颈，多实例部署麻烦；Token 无状态，天然适合分布式。

**没有标准答案**，关键看：你的服务是单体还是分布式？需不需要即时踢用户下线？如果 Mindloop 只是一个桌面端 + 一台后端服务器，Session 完全够用；如果以后要做 Web 端 + 移动端 + 桌面端同时在线，Token 更合适。

**RBAC 够用，还是要上 ABAC？**

ABAC（基于属性的权限控制）更细粒度："这个用户可以访问他自己创建的笔记，但不能访问别人在同一工作区创建的笔记"。比 RBAC 更灵活，实现成本也高得多。

研发争论时问自己：我们的权限边界是按身份划分（谁是管理员）还是按资源归属划分（谁创建的）？后者才需要 ABAC。大多数产品从 RBAC 起步就够了。

**JWT 载荷放多少信息？**

放越多，每次请求的包就越大；放太少，服务器要频繁查数据库补充信息。角色、用户 ID 放进去是标配；把完整的用户档案都塞进去是过度设计。
