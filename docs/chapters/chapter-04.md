# P0-4: 认证与权限 — 登录机制、Token/Session、OAuth、RBAC

> **一句话总结：** 认证解决"你是谁"，权限解决"你能做什么"——理解这两件事的实现原理，你设计功能时就不会再画出让研发抓狂的方案了。

---

## 先聊聊为什么设计师要懂这个

你有没有遇到过这种情况：设计了一个"管理员可以查看所有用户数据"的功能，研发说"这个要改数据库结构，两周"；或者设计了"用微信登录后自动绑定手机号"，研发说"不行，OAuth 流程不是这样的"……

这些卡壳，不是研发在刁难你，是你的方案碰到了认证和权限的技术边界。懂了今天的内容，你就能在设计阶段提前绕开这些坑。

---

## 第一部分：登录的本质——服务器怎么"记住"你

### 🏠 生活类比：小区门禁

想象你住在一个有门卫的小区。每次你想进门，门卫都要确认你是住户。但门卫不可能每次都去翻花名册——那太慢了。

所以小区发给你一张**门禁卡**。你刷卡，门开了。门卫不需要认识你这个人，他只需要认识这张卡。

这就是登录的本质：

1. **第一次**：你用用户名 + 密码证明你是你（门卫翻花名册确认你是住户）
2. **之后每次**：服务器给你一个凭证（发给你门禁卡），你每次请求都带着这个凭证

这个凭证，就是我们接下来要讲的核心概念。

### 🔧 技术解释：HTTP 是没有记忆的

HTTP 协议本身是**无状态的**——每次请求对服务器来说都是陌生人。你登录之后发的第二个请求，服务器默认不知道那还是你。

所以工程师发明了两种方案来让服务器"记住"你：**Session** 和 **Token**。

---

## 第二部分：Session vs Token——两种"门禁卡"

### Session：门卫记在小本本上

**类比：** Session 就像你进小区时，门卫在他的小本本上写了一条记录："203室的王明，进来了，流水号 #00123"。然后给你一张写着 `#00123` 的小纸条。

你下次进来，把纸条给门卫，门卫查小本本，找到 `#00123` 对应的是 203 室的王明，放行。

**技术实现：**
- 你登录成功 → 服务器在数据库/内存里存一条 Session 记录（包含你的用户 ID、登录时间等）
- 服务器给你返回一个 `Session ID`，存在你浏览器的 Cookie 里
- 你每次请求，浏览器自动带上这个 Cookie
- 服务器收到请求 → 用 Session ID 查数据库 → 找到你是谁 → 处理请求

**缺点：**
- 门卫的小本本会越来越厚（服务器要存所有人的 Session，占内存）
- 如果你有两个门（两台服务器），小本本不共享，就乱了（分布式扩展难）

---

### Token：把信息写在卡上

**类比：** Token 更像是你们小区换了个更智能的方案——不记小本本了，直接在门禁卡上**写入信息**：持卡人是 203 室王明，有效期到 2025年12月31日，有管理员权限。

门卫不需要查小本本，直接读卡就能知道你是谁、能做什么。

**技术实现：**
- 你登录成功 → 服务器生成一个 Token（里面包含你的信息），返回给你
- Token 存在你的浏览器本地（localStorage 或 Cookie）
- 你每次请求，在 Header 里带上这个 Token：`Authorization: Bearer <token>`
- 服务器收到请求 → **不需要查数据库**，直接解析 Token 里的信息 → 处理请求

**优点：**
- 服务器不用存状态，100 台服务器都能处理你的请求
- 天然适合手机 App、前后端分离的架构

---

### 对比总结

| | Session | Token |
|---|---|---|
| 信息存在哪 | 服务器端 | 客户端（Token本身） |
| 服务器压力 | 需要存储和查询 | 几乎没有 |
| 适合场景 | 传统 Web、后台系统 | 前后端分离、移动端、微服务 |
| 强制下线 | 容易（删 Session 记录） | 麻烦（需要黑名单机制） |

> **Mindloop 怎么用的？** Mindloop 是 Electron 桌面端应用，后端 API 用的是 Token（JWT）方案。因为桌面端没有浏览器 Cookie 的天然支持，用 Token 更简单，存在本地文件里就行。

## 第三部分：JWT——Token 里装了什么

JWT 是 **JSON Web Token** 的缩写，是目前最流行的 Token 格式。

### 🎫 类比：火车票

一张火车票上印着：出发站、目的地、座位号、乘客姓名、有效日期，还有一个防伪二维码。

JWT 就像这张票——**信息公开印在上面，但防伪机制保证了没人能伪造**。

### JWT 的结构：三段话

JWT 长这样（用点分隔的三段）：

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOiIxMjMifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk
     Header（头）        Payload（信息）          Signature（签名）
```

**Header**：声明这是个 JWT，用了什么加密算法

**Payload（最重要）**：解码后是一个 JSON，存着用户信息：
```json
{
  "userId": "123",
  "email": "wang@mindloop.app",
  "role": "admin",
  "exp": 1735689600  // 过期时间（Unix时间戳）
}
```

**Signature**：用服务器的私钥对前两段加密生成的签名

关键点：**Payload 是 Base64 编码，不是加密——任何人都能解码看到里面的内容。** 但没有服务器私钥，就没法伪造一个合法的签名。

> 所以规则是：JWT 里可以放用户 ID、角色这些不敏感的信息，**绝对不能放密码**。

## 第四部分：OAuth——第三方登录是怎么实现的

你在 Mindloop 里点"用 GitHub 登录"，这背后发生了什么？

### 🏨 类比：酒店代泊车服务

你把车交给酒店代客泊车，但你不会把车钥匙直接给服务员——你只给他一张**代客泊车票**，这张票只允许他停车，不允许他开走你的车，而且只有今晚有效。

OAuth 就是这个机制：**你授权第三方（Mindloop）访问你在 GitHub 的部分信息，而不是把 GitHub 账号密码交给 Mindloop**。

### OAuth 流程（用 GitHub 登录 Mindloop 为例）

```
你点击"GitHub 登录"
    ↓
Mindloop 把你跳转到 GitHub 的授权页面
    ↓
你在 GitHub 上点"同意授权 Mindloop 读取我的邮箱和用户名"
    ↓
GitHub 给 Mindloop 一个临时的"授权码"（Authorization Code）
    ↓
Mindloop 后端拿这个授权码，去 GitHub 换一个"访问令牌"（Access Token）
    ↓
Mindloop 用这个 Access Token 调用 GitHub API，获取你的用户名和邮箱
    ↓
Mindloop 在自己的数据库里创建（或找到）你的账号，完成登录
```

**关键理解：**
- 你的 GitHub 密码**全程没有经过 Mindloop**
- Mindloop 拿到的 Access Token 权限是有限的（你点同意时授权了什么就只能做什么）
- 这就是为什么你能"用 GitHub 登录"但 Mindloop 并不知道你的 GitHub 密码

> **为什么设计师要理解这个？** 当你设计"第三方登录后自动填充手机号"这个需求时，研发会告诉你：GitHub 的 OAuth 根本不提供手机号，你能拿到的只有邮箱和用户名——这不是研发不想做，是 OAuth 协议的限制。

## 第五部分：权限模型——谁能做什么

认证（Authentication）解决了"你是谁"，权限（Authorization）解决"你能做什么"。

### RBAC——基于角色的权限控制

**类比：公司职级**

公司里不会给每个人单独写一份"这个人能做什么、不能做什么"的清单——太麻烦了。而是定义几个**职级**（角色）：实习生、员工、经理、总监，每个职级有对应的权限，人员套职级就行了。

这就是 RBAC：**Role-Based Access Control**

```
用户 → 被分配角色 → 角色拥有权限

王明 → admin（管理员角色）→ 可以删除笔记、管理用户、查看所有数据
李华 → member（普通用户）→ 只能看/编辑自己的笔记
张伟 → viewer（只读用户）→ 只能查看被分享的笔记
```

### Mindloop 的权限设计

假设 Mindloop 要支持团队协作，权限设计可能是这样的：

| 操作 | owner | editor | viewer |
|---|---|---|---|
| 查看笔记 | ✅ | ✅ | ✅ |
| 编辑笔记 | ✅ | ✅ | ❌ |
| 删除笔记 | ✅ | ❌ | ❌ |
| 邀请成员 | ✅ | ❌ | ❌ |
| 修改空间设置 | ✅ | ❌ | ❌ |

**设计师要注意的问题：**

当你设计一个功能时，要想清楚：**这个操作对哪些角色可见？** 不只是"能不能用"，还有"能不能看到入口"。

比如"删除团队空间"这个按钮——对 viewer 是压根不显示，还是显示但置灰？前者研发实现简单，后者用户体验更好（知道有这个功能但自己没权限），但要多一层判断逻辑。这是你需要跟研发商量的决策。

## 第六部分：Token 的生老病死——过期和刷新

### Token 为什么要过期？

类比：游乐园的手环。手环上印着今天的日期，明天就失效了。这样即使有人捡到你的手环，也用不了多久。

Token 同理：**如果 Token 永不过期，一旦被盗，攻击者可以永久冒充你。** 所以 Token 都有有效期。

### 但过期太频繁，用户要一直重新登录……

解决方案：**双 Token 机制**

```
登录时，服务器返回两个 Token：

Access Token（访问令牌）
- 有效期短：15分钟 或 2小时
- 用于每次 API 请求

Refresh Token（刷新令牌）
- 有效期长：7天 或 30天
- 只用于换新的 Access Token
```

**流程：**
1. 你用 Access Token 正常使用 Mindloop
2. 2小时后，Access Token 过期
3. App 自动用 Refresh Token 去服务器换一个新的 Access Token
4. 整个过程你完全感知不到，继续用

只有当 Refresh Token 也过期了（你 30 天没打开 App），才需要重新登录。

### 顺带提一下 CSRF

**CSRF（跨站请求伪造）**：简单说，就是你登录了银行网站，然后去一个恶意网站，那个网站悄悄用你浏览器里的银行 Cookie，向银行发了一个转账请求。

**为什么 Token 方案能防 CSRF：** 因为恶意网站虽然能触发你的浏览器发请求，但它读不到你存在 localStorage 里的 Token，也就没法在请求 Header 里加上 `Authorization: Bearer <token>`。

> 这也是为什么现代 SPA（单页应用）偏爱把 Token 存在 localStorage 而不是 Cookie——虽然有其他安全考量，但天然抵抗 CSRF。
