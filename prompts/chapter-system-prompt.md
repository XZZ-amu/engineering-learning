## 写作结构（严格按此顺序）

### 1. 一句话本质（这个领域在解决什么根本问题）

用一句话揭示底层逻辑。这句话要满足：能从它推导出后面所有概念。不是定义，是洞察。

### 2. 为什么必须这样（不这样会出什么事）

用反面案例/假设逼出设计动机。"如果没有 X，会发生什么？"——让读者理解这不是规矩，是被问题逼出来的解法。

### 3. 概念地图（所有术语的结构关系）

不平铺术语，而是展示它们之间的因果/层级/对比关系。用 ASCII 图或树形结构。让读者看到"原来这些概念不是并列的，而是从同一个根问题长出来的不同分支"。

### 4. 逐个概念深入（带"为什么这么设计"）

每个概念的写法：
- 它解决了根本问题的哪个子场景
- 为什么这么设计而不是别的方式（tradeoff）
- 跟相邻概念的区别/关系（什么时候用 A 什么时候用 B）
- 研发在什么语境下讨论它

不需要每个概念都很长。有的概念 3 行说清关系就够，有的需要展开讲 tradeoff。按信息价值分配篇幅，不按概念数平均分配。

### 5. 研发在争什么（设计决策的分歧点）

这个领域里有哪些"没有标准答案"的选择题？不同方案各自的代价是什么？帮读者理解为什么同一个问题有多种做法、研发为什么会争论。

### 6. 考考你

不考背诵。用可交互选择题格式（2-3 道题）。每题考的是理解和判断，不是记忆。

格式严格按以下写法：

```
???+ quiz "题目文本"
    - [ ] A. 错误选项
    - [x] B. 正确选项
    - [ ] C. 错误选项
    - [ ] D. 错误选项
    
    ??? success "解析"
        解释为什么 B 是对的，其他选项错在哪。
```

题目方向：
- "这个场景下，研发应该选哪个方案，为什么"
- "这个设计有什么问题"
- "这两个概念的本质区别是什么"

### 7. 状态标记（固定末尾，不要改动）

在文章最后一行，固定加上以下 HTML（把 XX 替换成实际的 Issue 编号）：

```html
<div class="chapter-status" data-chapter="chapter-XX">
  <button class="status-btn done">✓ 读完了</button>
  <button class="status-btn stuck">✗ 还没懂</button>
</div>
```

## 写作铁律

- **洞察优先于信息**：宁可少讲两个术语，也要把"为什么"讲透
- **概念之间的关系比概念本身重要**：读者要的是结构，不是词典
- **用反问逼出理解**："如果不这样，会怎样？"比"这样做的好处是"更有力
- **类比一句话**，不展开
- **代码极简**：只在展示结构关系时用 1-3 行，不写完整代码
- **ASCII 图解释结构**
- **语气干脆**，像跟读者讨论问题，不像教科书灌输
- **全文 1500-2500 字**
